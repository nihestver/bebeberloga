# CLAUDE.md — инструкции для Claude Code

Ты работаешь в open-source проекте **Bebeberloga**: self-hosted платформа общения с текстовыми и голосовыми каналами, видео, стримом экрана/окна/приложения, soundboard и сквозным шифрованием (E2EE на MLS, RFC 9420) для всего, включая стрим. Сервер на Go, crypto-core и media-engine на Rust, desktop-клиент на Electron + React/TypeScript.

Этот файл — context pack контура реализации (см. `docs/prompts/README.md`). Он действует в каждой сессии.

## Источники правды

1. `docs/spec/` — функциональная спецификация: `GLOSSARY.md` (термины и запретный список), `FEATURES.md` (функции и приоритеты M/S/C), `FLOWS/` (пошаговые сценарии), `SCREENS/` (экраны, `COMPONENTS.md`, `SHORTCUTS.md`), `PERMISSIONS.md` (права и роли).
2. `docs/adr/` — принятые решения. Решение из ADR не оспаривается в коде; если оно мешает задаче — остановись и предложи новый ADR.
3. `docs/protocol/` — Protobuf-схемы, gateway, REST, MLS-профиль, формат сообщений.
4. `docs/spec/ARCHITECTURE.md` — архитектура, E2EE-дизайн, стек, стрим, компромиссы E2EE (нумерация разделов совпадает с планом: «раздел 6.5» = §6.5 этого файла). `docs/PLAN.md` — рабочий документ аналитиков; его не читай (запрещено в `.claude/settings.json`).
5. `BRAND.md` — палитра, шрифты, тон текстов интерфейса; дизайн-токены для кода — `design/tokens/` (B8), базовые значения — `brand/tokens.css` (его не меняй).

Если спецификация молчит о поведении для пользователя — запиши вопрос в `docs/spec/OPEN-QUESTIONS.md` и не придумывай поведение «как в известных продуктах»; если без ответа нельзя продолжить — остановись. Технические допущения (структура кода, выбор библиотеки в рамках ADR) фиксируй в `STATUS.md` модуля.

## Clean room: обязательные правила

- Реализуй только по спецификации в `docs/`. Не открывай, не описывай и не воспроизводи сторонние продукты, их тексты, стили, иконки, звуки, звуки уведомлений, схемы API и имена полей.
- Не используй код и ассеты сторонних мессенджеров и их SDK, даже под свободной лицензией. Разрешённые зависимости перечислены в ADR и `LICENSING.md`; каждая новая зависимость — с обоснованием и проверкой лицензии.
- Запретный список в `docs/spec/GLOSSARY.md` двухуровневый: **уровень 1** (товарные знаки и фирменные названия) — нигде; **уровень 2** (чужая номенклатура API: guild, snowflake, @everyone и т. п.) — нельзя в коде, идентификаторах, API, БД и коммитах, но можно в текстах интерфейса (файлы локализации). Обычные слова интерфейса («сервер», «канал», «пригласить») использовать можно.
- Термины интерфейса — по `GLOSSARY.md` (в UI «сервер», «канал», «роль», «ветка»; в коде `community`, `channel`, `role`, `thread`).
- Каждое изменение в `crypto-core/`, `server/internal/mls/` и `media-engine/` записывается в `SECURITY-CHANGELOG.md` соответствующего модуля.

## Правила интерфейса

- Раскладка, порядок элементов, размеры и поведение экранов — строго по `docs/spec/SCREENS/`; в PR клиента — таблица «раздел SCREENS → файл → скриншот».
- Только компоненты дизайн-системы (`clients/web/src/ui`, каталог — `SCREENS/COMPONENTS.md`); цвета, шрифты, отступы — только дизайн-токены (`design/tokens/` → `clients/web/src/ui/tokens.css`).
- Тексты интерфейса — через i18n (RU, EN) в `clients/*/src/locales/` (только там clean-room хук разрешает слова уровня 2), в тоне `BRAND.md`; подписи из `SCREENS` можно улучшать, сохраняя смысл.
- Функции с пометкой (S) и (C) — за флагами, по умолчанию выключены.
- Если в `SCREENS` чего-то не хватает или есть противоречие — вопрос в `docs/spec/OPEN-QUESTIONS.md`, а не «как в известных приложениях».

## Правила кода

- **Go** (`server/`): Go 1.23+, `golangci-lint`, `go test -race`; интеграционные тесты через `testcontainers-go`. Пакеты `internal/{identity,community,messaging,mls,gateway,media,files,push,admin}` общаются через интерфейсы.
- **Rust** (`crypto-core/`, `media-engine/`): `clippy -D warnings`, `cargo deny`, `cargo audit`; `proptest` для MLS-сценариев, `cargo fuzz` для парсеров; ключи в памяти — `zeroize`; FFI через `uniffi` (Kotlin/Swift), `napi-rs` (Electron), `wasm-bindgen` (web).
- **TypeScript** (`clients/web`, `clients/desktop`): strict, `eslint` + `typescript-eslint`, `vitest`, Playwright e2e с двумя пользователями, обменивающимися E2EE-сообщениями.
- Protobuf-схемы в `proto/` — единственный источник моделей для Go/TS/Kotlin/Swift; не дублируй типы руками.
- Лицензионный заголовок SPDX в каждом файле (см. `LICENSING.md`). Коммиты — Conventional Commits с `Signed-off-by` (DCO).
- Команды в документации пиши без `sudo`.

## Инварианты E2EE (нарушать нельзя)

- Сервер и SFU никогда не получают ключи и открытый текст: ни сообщений, ни файлов, ни медиакадров, ни стрима.
- Нет режима «без E2EE» и отката на транспортное шифрование. При нехватке ресурсов снижается качество стрима, не шифрование.
- Одно устройство = один MLS-leaf; удаление устройства = commit во всех его группах.
- Push-уведомления не содержат текста — только id группы и сообщения.
- История видна всем, кто видит канал, включая новых участников и новые устройства (ADR-0015): сервер хранит шифртекст и ключи сообщений, обёрнутые ключом истории, но не получает ни ключей истории, ни текста.
- Лимит участников канала (по умолчанию 2 000) применяется сервером; сообщение в UI — о лимите участников, без упоминания шифрования.

## Как выполнять задачу

1. Прочитай ADR и файлы спецификации, которые касаются задачи. Напиши план до 10 пунктов и открытые вопросы — до кода.
2. Делай один модуль за раз с проверяемым результатом. Состояние длинной задачи — в `STATUS.md` каталога модуля: что сделано, что сломано, что дальше.
3. Тесты обязательны; укажи команду проверки и ожидаемый результат.
4. В конце — что сознательно отложено, и обновление документации (`docs/protocol/`, ADR), если контракт изменился.
5. Ревью на заимствования по `docs/cleanroom/REVIEW-CHECKLIST.md` — перед тем, как считать модуль готовым.
