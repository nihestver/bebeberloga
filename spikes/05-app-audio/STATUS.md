# S5 — спайк «звук приложения и захват видео»: состояние

Промпт: `docs/prompts/S5-app-audio.md`. Ветка `spike/S5-app-audio`. Запуск на стенде — `STAND.md`. Черновики `REPORT.md` и ADR-0033 написаны по полным прогонам macOS и Windows и по контейнеру Linux; раздел Linux на стенде дополняется после прогона на pc-stand.

## Сделано

- Каркас: отдельный пакет Cargo с программами `s5cap` (захват, разбор, самотест) и `s5src` (тестовый источник), `justfile`, `deny.toml`.
- Общая часть: единая монотонная шкала времени, запись WAV и журналов меток, анализатор (уровни тонов, разрывы шкалы времени, потери сэмплов по фазе тона, вспышки, рассинхрон) с пятью тестами на синтетических записях.
- macOS (MacBook Pro M4 Pro, macOS 26.4.1): окна с PID и иконкой, дерево процессов, процессы-клиенты CoreAudio, захват через ScreenCaptureKit, самотест из тринадцати сценариев. Числа — в `results/macos/`: `selftest-full.json` — полный прогон на 10 минут, `selftest-trial.json` — те же сценарии с основным прогоном на 30 с.
- Windows: код проходит `cargo clippy --target x86_64-pc-windows-msvc -- -D warnings` на Mac. **На стенде pc-stand 2026-11-25 прошли `build`, пробный прогон `trial` (187 с), повтор шести сценариев, полный прогон `selftest` (18 сценариев, основной — 10 минут, 810 с): 75 проверок выполнено, 2 не выполнено — и прогоны `wgc-rate` и `wgc-wait` (по три сценария WGC по 2 минуты, 368 и 366 с).** Захват идёт в физических пикселях, масштаб экрана пишется в журнал видео-меток; в прогон входят четыре сценария «звук при mute и при громкости 0».
- Linux: код собирается и проходит clippy в контейнере Debian 13. Звук проверен там же функционально — PipeWire 1.4.2 с пустым устройством вывода, без железа: линковка узлов дерева процессов, автоподключение узла, появившегося во время записи, исключение собственного процесса, monitor устройства вывода. Сводки — `results/linux-container/`. Там же проверены список окон X11 (с оконным менеджером) и чтение кадров из узла PipeWire на тестовом источнике кадров. **Переговоры с порталом ScreenCast до конца не проверены**; на железе не запускалось ничего.

## Найдено на macOS

- Звук приложения через ScreenCaptureKit включает дочерний процесс, запущенный до начала захвата, и не включает посторонний процесс и саму программу захвата — и с фильтром по окну, и с фильтром по приложению.
- **Процесс, запущенный после начала захвата, в звук не попадает**: ни через 34 с, ни после обновления фильтра потока на ходу. Помогает остановка и повторный запуск потока; разрыв звука при этом — 117–145 мс.
- **Провала можно избежать склейкой** (решение владельца по вопросу №71): второй поток звука запускается, пока первый ещё работает (130–140 мс), и стыкуется с первым по меткам времени. В шести прогонах — ни разрыва шкалы времени, ни потерянных сэмплов; фаза тона на стыке расходится не больше чем на 4,6° (меньше полутора сэмплов). Работает и с фильтром по окну, и с фильтром по приложению.
- **Кадры теряет захват, а не источник.** Источник рисует 60,0 к/с без пропусков (по его журналу кадров). ScreenCaptureKit с пределом частоты 60 к/с отдаёт 53,5–57,5 к/с, то есть 90–98 % кадров; с пределом 120 к/с отдаёт больше кадров, чем нарисовано (63,5–75 к/с, повторы), и тоже неравномерно. Экран стенда — 120 Гц.
- **Когда дисплей гаснет, кадры видео перестают приходить**, звук продолжается без разрывов. В первом полном прогоне дисплей был выключен 37 с: MacBook работал от батареи, владелец отошёл, и экран погас по простою — обычное поведение системы, не сбой. Самотест теперь удерживает дисплей. Решение владельца (вопрос №70): клиент не даёт экрану гаснуть, пока идёт стрим; если экран всё же выключился, зрители видят заглушку «Стрим приостановлен», звук продолжается.
- Окно «поверх остальных» лежит не в нулевом слое окон: отбор только по слою 0 его теряет.
- У потока без цикла событий нет пула авторелиза: без явного пула перечисление окон с иконками 1024×1024 занимает сотни мегабайт.
- Устройство вывода на этом Mac работает на 44,1 кГц; ScreenCaptureKit отдаёт запрошенные 48 кГц, стерео, float32, буферами по 960 кадров.

## Найдено на Windows (pc-stand, 2026-11-25)

Сводки — `results/windows/`: `selftest-full.json` — полный прогон, `selftest-wgc-rate.json` — сценарии WGC при 59 и 60 к/с, `selftest-wgc-wait.json` — WGC с пробуждениями потока захвата и без них, `selftest-trial.json` и `selftest-only.json` — пробный и повтор. Сырые журналы и записи забраны со стенда в `out/stand-windows/` (в git не хранятся). Подробности и таблицы — `REPORT.md`, раздел «Windows».

- Запуск работает как задумано: источник и посторонний процесс стартуют вне дерева программы захвата, окно найдено, PID совпал, размер — в физических пикселях при масштабе 125 %. У окна без собственной иконки берётся иконка исполняемого файла.
- **Звук приложения (process loopback): 10 минут без разрывов и потерь.** Снимается до регулятора громкости: тоны ровно на номинале при любой громкости, при mute и при громкости 0.
- **Loopback устройства вывода — после регулятора громкости и обработки драйвера**: уровень растёт с громкостью, при mute и громкости 0 — тишина, тон 440 Гц в 6,6 раза слабее тона 2000 Гц; свой процесс не исключается. По ответу владельца на вопрос №72 в продукт он не идёт: звук самого клиента в стрим не попадает никогда; когда исключить процессы клиента нельзя, стрим идёт без звука системы, стример видит сообщение.
- **Процесс, запущенный во время захвата, попадает в звук сам** через 0,1–0,2 с. В этот момент поток замирает на 11–19 мс без флага разрыва; в одном прогоне из трёх при этом потерян буфер 10 мс. Проверка «шкала времени без разрывов» в сценарии `late-child` поэтому не выполняется.
- **Рассинхрон на сырых метках критерий не проходит**: за 10 минут среднее 42,0 мс, p95 51,9 мс, максимум 57,5 мс. 29 мс из них — задержка вывода звука в самом тестовом источнике; от ожидаемого момента воспроизведения — среднее 9,0 мс, p95 17,1 мс. В сценарии `sync-compensated` (источник сам учитывает задержку) — p95 9,0 мс.
- **Разброс рассинхрона виден только на длинном отрезке**: момент отрисовки кадра ползёт относительно развёртки экрана с периодом 129 с, задержка видео ходит от 16 до 33 мс. За 30 с пробного прогона разброс был 1,1 мс, за 10 минут — 6,7 мс.
- **Кадры теряет WGC**: 94–97 % кадров источника при 60 к/с (одиночные пропуски, около трёх в секунду), 100 % при 30 к/с; DXGI и GDI — 99,7–100 %. Наименьший интервал обновления 1 мс недобор не убрал (90,1 %).
- **Гипотеза «недобор из-за равенства частоты источника и экрана» не подтвердилась** (прогон `wgc-rate`): источник 60 к/с — 95,9 %, источник 59 к/с — 96,4 %, источник 60 к/с с интервалом обновления 16,95 мс — 96,8 %. Пропуски одиночные, временем кадров источника не объясняются и в 49–94 % случаев отстоят друг от друга на число периодов экрана, кратное трём (50 мс).
- **Пробуждение потока захвата раз в 50 мс ни при чём** (прогон `wgc-wait`): без пробуждений — 95,9 и 96,1 %, с ними — 95,7 %; сетка 50 мс остаётся во всех трёх сценариях. Ввода человека в этом прогоне не было, звук источника — нули. Причина недобора не установлена; непроверенными остались окно, которое рисует видеокарта, размер пула кадров и чтение с видеокарты в обработчике кадра — это передано в S6.
- Метка кадра WGC — планируемый момент показа, кадр приходит на 13 мс раньше.
- Цепочки запасных методов звука и видео срабатывают.
- После полного прогона добавлены дополнительные сценарии `wgc-rate-60`, `wgc-rate-source-59`, `wgc-rate-limit-59` (в общий прогон не входят, рецепт `wgc-rate`) и строка «недобор кадров захвата» в таблице проверок.
- После прогона `wgc-rate` поток, создавший захват WGC, больше не просыпается раз в 50 мс: он спит, пока его не разбудит остановка. Для сравнения оставлен вариант с прежним ожиданием; сценарии `wgc-wait-none-1`, `wgc-wait-poll-50`, `wgc-wait-none-2` (рецепт `wgc-wait`). Флаг `--silent` у `s5cap selftest` и `s5src`: звуковые потоки работают, но отдают нули — для прогонов без записи звука; на слух не проверялся.
- Команда `env` на Linux сообщает, что объявляет портал ScreenCast в текущем сеансе (версия, виды источников) или почему он недоступен; проверено в контейнере без портала.

Помехи: в пробном прогоне громкость убавляли вручную (40 → 20 %), рядом работал наблюдатель агента стенда. Полный прогон шёл без ввода и наблюдателей при громкости 40 %; во время сценария `audio-endpoint-only` система сама запустила скрытый процесс настроек, на записи это не видно. В прогоне `wgc-rate` на 68-й секунде второго сценария был ввод человека; звук устройства вывода был выключен. Прогон `wgc-wait` шёл без ввода; системная служба за это время прочитала с диска 182 МБ.

## Найдено на Linux (контейнер, без железа)

- **Свойства `application.process.id` у узла может не быть.** У клиентов через слой ALSA и у клиентов самого PipeWire его нет: PID есть только у клиента узла (`pipewire.sec.pid`). У клиентов протокола PulseAudio наоборот: у узла `application.process.id` верный, а `pipewire.sec.pid` клиента — это PID службы `pipewire-pulse`. Спайк берёт свойство узла, а если его нет — свойство клиента.
- Порты узла приходят по одному: решать «моно это или стерео» по числу уже известных портов нельзя — получаются лишние связи. Сопоставление идёт только по имени канала порта.
- Узел, появившийся во время записи, подключается за 0,1 с. С клиентом ALSA в этот момент был один разрыв шкалы времени в 10,7 мс; с клиентом PipeWire разрывов не было. На железе перепроверить.
- Метку времени кадра источник видео прикладывает, только если запросить заголовок кадра; без запроса остаётся время прихода.
- Список окон X11 ведёт оконный менеджер: без него список пуст.
- Библиотека вывода звука тестового источника по умолчанию выбирает PipeWire; её путь через протокол PulseAudio со службой `pipewire-pulse` не запустился («server error: Invalid»). Узел клиента PulseAudio проверен утилитой `pacat`.

## Сломано / не получилось

- Проверка «звук процесса, запущенного во время записи» на macOS не проходит по построению (см. выше); сценарии без обновления и с обновлением фильтра оставлены в самотесте как подтверждение, поэтому самотест на macOS завершается с четырьмя невыполненными проверками.
- Самотест на Windows завершается с двумя невыполненными проверками: разрыв шкалы времени в `late-child` (поведение системы) и рассинхрон на сырых метках в `main` (тестовый источник не учитывает задержку своего вывода звука). Обе оставлены как есть: это результат, а не ошибка прогона.
- (исправлено) `cargo deny check licenses` не проходил из-за `target-lexicon` 0.13.5 под «Apache-2.0 WITH LLVM-exception» — зависимости времени сборки привязок PipeWire. Решением владельца от 2026-11-24 лицензия разрешена только для этого крейта: запись в `LICENSING.md`, исключение в `deny.toml`.

## Не проверено

- macOS 13–15 и Intel Mac: стенда нет.
- Linux без PipeWire (monitor-источник PulseAudio): не реализовано и не проверялось.
- Linux: приложения в песочнице (Flatpak, Snap) — совпадает ли их PID в свойствах узла с PID в `/proc`.
- Многоканальные источники на Linux: спайк связывает только левый, правый и моно-канал.
- Linux на железе — до прогона на pc-stand.
- Windows: причина недобора кадров WGC при 60 к/с (исключены частота источника, интервал обновления, ожидание потока захвата, ввод и звук); из чего складываются 35 мс между меткой звука и моментом воспроизведения; AMD и Intel, Windows 10, экран с частотой выше 60 Гц.

## Технические допущения

- Версии прямых зависимостей закреплены точно; `Cargo.lock` в git. Основные: `windows` 0.62.2, `objc2` 0.6.5 и крейты фреймворков 0.3.2, `pipewire` 0.10.1, `ashpd` 0.14.3, `x11rb` 0.14.0, `cpal` 0.18.2, `winit` 0.30.13, `softbuffer` 0.4.8, `hound` 3.5.1, `png` 0.18.1, `clap` 4.6.9.
- Спайк не входит в корневые `just lint`/`just test` и в CI; проверки — `just check` в каталоге спайка.
- Паники в коде спайка допустимы (правило `CLAUDE.md` о production-коде на спайки не распространяется); `SECURITY-CHANGELOG.md` не ведётся.
- Каталог `out/` с записями в git не хранится; в `results/` — только сводки `selftest.json` без заголовков окон, имён и путей.
- Тестовый источник на macOS запускается отдельным приложением (бандл `.app` собирается в каталоге прогона), на Windows — через `Win32_Process.Create`, чтобы не быть потомком программы захвата, на Linux — её потомком.
- Удержание дисплея: macOS — `caffeinate`, Windows — `SetThreadExecutionState`, Linux — портал Inhibit.
- Сценарии «mute и громкость 0» на Windows меняют состояние устройства вывода по умолчанию и возвращают его; прежнее состояние перед изменением пишется в файл каталога прогона.
- Отладочный контейнер для Linux (образ Rust на Debian 13 с пакетами PipeWire, виртуальный X-сервер с оконным менеджером) в репозиторий не входит.
- Переменная `S5_PW_VIDEO_NODE` — отладочный режим: видео читается из названного узла PipeWire без портала.
- Сторонние продукты и их код не открывались. Использованы документация Apple, Microsoft и PipeWire и исходники крейтов-привязок из реестра Cargo.
