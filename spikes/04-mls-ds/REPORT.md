# S4 — спайк: MLS Delivery Service на Go. Отчёт

Промпт: [`docs/prompts/S4-mls-ds.md`](../../docs/prompts/S4-mls-ds.md). Решение: [ADR-0018](../../docs/adr/0018-spike-s4-mls-ds.md). Код спайка — прототип, не продуктовый: аутентификации нет, устройство называет себя в теле запроса.

## Коротко

1. **Сервер на Go может быть Delivery Service и external sender без Rust.** Предложения Add/Remove, которые подписывает DS, побайтно совпадают с теми, что подписывает OpenMLS 0.9.2 тем же ключом. DS разбирает KeyPackage с проверкой обеих подписей, capabilities и срока, считает `KeyPackageRef`, совпадающий с Welcome OpenMLS, и читает открытый заголовок commit-а.
2. **Ответ на открытый вопрос ADR-0016 п. 4: «дельта состава» в `authenticated_data` commit-а.** Автор commit-а перечисляет там удалённые листья и добавленные пары `(лист, устройство)`. DS ведёт по дельте карту листьев: из неё берутся leaf index для Remove, лимит листьев и проверка, что в commit вошли все Remove. Получатели до merge сверяют дельту с фактическим действием commit-а и следят, чтобы лист автора не сменил credential. Предложения сервера привязаны к устройству через `authenticated_data` под его подписью, а новички сверяют состав с картой DS. Ложь, которую DS не видит, — перестановка устройств между листьями; её ловят получатели и новички, а восстановление рассинхрона — задача B02.
3. **1 000 одновременных входов в одну группу проходят за 2,4–3,6 с (p99) на одной машине** во всех режимах без длинного интервала батча. Рекомендуемый режим — «фронт + батч 1 с, max 100»: вход в группе без ожидающих Add — 26 мс; всплеск в 1 000 устройств — p50 1,8 с, p99 2,8 с; Welcome на устройство — 112 КБ.
4. **Батчинг интервалом сам по себе не нужен:** под нагрузкой commit-ы и так собирают все накопившиеся Add (1–2 commit-а на 1 000 входов). Нужны **ограничение пачки** (`max-batch`), **продолжение после commit-а** и **один назначенный коммитер**. Интервал дольше 1 с только добавляет задержку.
5. **Лимит участников по умолчанию (2 000, ADR-0005) снижать не нужно.** 4 000 одновременных входов (4 003 листа) прошли за 24,2 с при полностью загруженном стенде; Welcome на устройство — 392 КБ, обработка — 98 мс на M4 Pro. Жёсткий лимит листьев 5 000 оставить; DS соблюдает его точно и под конкуренцией.
6. **Security-ревью в три раунда нашло семь серьёзных дыр** — четыре в первом дизайне (переименование листа через UpdatePath, «ядовитый» KeyPackage, отмена опубликованного Add, Remove без привязки к устройству), две в исправлениях (гонка заявки с commit-ом, после которой бан не применялся, и взаимоблокировка commit-а с заявкой) и одну в третьем раунде (перекрёстная коллизия init ↔ encryption-ключей — ещё один вариант «ядовитого» KeyPackage). Все закрыты в спайке с регрессионными тестами. Третий раунд подтвердил хаос-тестом, что лимит участников не превышается и счётчики не «утекают». Два ограничения DS не устраняются на его стороне и записаны в ADR-0018 как требования к B02: DS один не может проверить, что Remove выполнен, и сверка состава с картой DS в спайке возможна только в той же эпохе.

## Как устроен прототип

```text
client/ (Rust, OpenMLS)                 ds/ (Go)                                 Postgres 16
  устройства, политика, дельта ──HTTP──▶ api → ds.Service ──pgx──────────────▶ key_packages, mls_groups,
  load: 1 000 входов + коммитеры          ├ mlswire: заголовки MLS, KeyPackage,   group_leaves, pending_ops,
  e2e: сценарии с подделками              │  подпись Add/Remove, дельта, Welcome   mls_handshakes, welcomes
                                          ├ батчер (тик), long-poll (notifier)
                                          └ cmd/emul: эмулятор клиентов без криптографии
```

Поток входа: `POST /groups/{g}/join` (в продукте — принятие приглашения, подтверждение устройства) → заявка в `pending_ops` → DS резервирует KeyPackage и публикует подписанный Add в текущей эпохе → онлайн-участники получают его long-poll-ом, проверяют и коммитят → DS принимает первый commit эпохи, сверяет дельту, обновляет карту листьев, сохраняет Welcome → новое устройство получает **свою** часть Welcome, входит и сверяет состав с картой DS.

### Дельта состава в `authenticated_data` (ответ на ADR-0016 п. 4)

```text
struct {
    uint8     version = 1;
    uint32    removed<V>;        // удалённые листья
    AddedLeaf added<V>;          // {uint32 leaf; opaque device_id<V>;} в порядке применения
} RosterDelta;

struct {                          // authenticated_data предложений сервера
    uint8     version = 1;
    opaque    device_id<V>;      // кого добавляет Add / кто стоит на листе Remove
} ProposalAAD;
```

`authenticated_data` открыт серверу и в `PrivateMessage`, и в `PublicMessage`, а для участников защищён AEAD или подписью. Индексы новых листьев детерминированы (RFC 9420 §12.1.1, §12.3): сначала Remove, затем каждый Add занимает самый левый пустой лист. Одна и та же функция (`AssignLeaves` в Go, `assign_leaves` в Rust) даёт одинаковый результат у автора, получателей и DS. Грамматика одна для Go и Rust: минимальные varint, непустой `device_id` в UTF-8.

| Кто | Что проверяет |
|---|---|
| Автор commit-а | Выбрасывает из очереди Add с негодным KeyPackage (срок, capabilities, повтор HPKE-ключа); строит дельту из очереди предложений, кладёт в AAD, после построения commit-а сверяет с фактическим (порядок Add задаёт openmls); сбрасывает AAD, чтобы он не утёк в следующее сообщение |
| DS | Удаляемые листья заняты, для каждого есть опубликованный Remove; все опубликованные Remove вошли в commit (`PROPOSALS_MISSING`); листья новых устройств — ровно ожидаемые по порядку (`BAD_DELTA`); у каждого добавленного устройства есть опубликованный Add (`UNAUTHORIZED_CHANGE`); лимит листьев; адресаты Welcome по `KeyPackageRef` — ровно добавленные устройства (`BAD_WELCOME`); размер AAD и число записей — до блокировки группы |
| Получатель | До постановки предложения в очередь: от `Sender::External(0)`, только Add или Remove, `device_id` из AAD совпадает с credential KeyPackage (Add) или с устройством на листе (Remove), срок KeyPackage ≤ 90 дней. До merge чужого commit-а: все Add/Remove — от сервера; все известные Remove сервера включены; лист автора (UpdatePath) и листы из Update не сменили credential; дельта совпадает с фактическим действием (`DeltaMismatch`) |
| Новичок | После Welcome: external sender группы = закреплённый ключ инстанса; состав из дерева = карта DS, если DS ещё в той же эпохе (в спайке сверка оппортунистическая — лжец может сделать второй commit; карта по эпохам — требование к B02/B05) |

**Чего DS не видит.** Если автор переставит устройства между новыми листьями, листья, набор устройств и адресаты Welcome останутся правильными. DS commit примет, получатели его отвергнут, а новички заметят расхождение дерева с картой DS: группа рассинхронизируется. Это частный случай уже известной проблемы «участник занимает эпоху мусорным commit-ом» (ADR-0016 п. 4); e2e показывает его явно. Процедуру восстановления описывает B02: получатель сообщает DS об отказе, DS помечает автора, участники выполняют external commit.

**DS один не может проверить, что Remove выполнен.** Дельта — слово автора, а содержимое commit-а зашифровано. Спайк держит Remove в состоянии «ждёт подтверждения» до commit-а другого устройства в новой эпохе, но второе ревью показало, что это не защита: отправитель внутри `PrivateMessage` для DS не аутентифицирован, и «подтвердить» можно запросом от имени другого устройства или мусорным commit-ом сообщника. Факт Remove должен опираться на сигнал честных клиентов, отвергших commit (требование к B02, ADR-0018 п. 2).

**Альтернатива, которую спайк отверг.** DS сам вычисляет листья, если все Add/Remove делает только он, а inline-изменения состава участникам запрещены. Это не покрывает commit создателя группы с начальным составом и external commit, а при зашифрованных commit-ах DS всё равно не знает, какие из его предложений вошли в commit. Дельта решает и то, и другое, а получатели её проверяют.

## Замеры

Все числа — после исправлений по итогам ревью.

### 1 000 одновременных входов в одну группу

Настоящие устройства OpenMLS; в группе 3 онлайн-участника (если не указано иное); медиана из 3 повторов (`results/load.md`). «Применено» — от заявки до обработанного Welcome у нового устройства. Обработка Welcome ограничена числом ядер (семафор), а очередь стенда на ядра в задержку не входит: у каждого устройства в жизни свой процессор. «Последний применил» — момент, когда вошло последнее устройство. Новичок после входа сверяет состав с картой DS, если DS ещё в той же эпохе: так сверились 31 830 из 46 491 входов во всех прогонах (в четверти прогонов — лишь 4–13 %: следом шёл второй commit), расхождений нет. Это и есть ограничение N7 — нужна карта по эпохам.

Сам DS проводит 1 000 входов в одну группу за ~1,20 с. Остальное в замерах с OpenMLS — работа клиентов: проверка Add, сборка commit-а, Welcome.

### Что дала доводка DS

Первая версия (построчный SQL; каждая заявка брала блокировку группы; Welcome целиком из базы на каждое устройство) на 1 000 входов «сразу» давала p50 5,4 с, p95 7,0 с. Удержание блокировки commit-ом — 402 мс, ожидание блокировки заявкой — p50 1,6 с, повторов Add — 1 674 (`results/baseline-rowwise.jsonl`). Что изменено:

1. Заявка на вход не берёт блокировку группы: лимит проверяет атомарный `UPDATE group_requests SET requested = requested + 1 … WHERE leaf_count + (requested − done) < leaf_limit` в отдельной строке счётчика заявок; строку commit-ов (`leaf_count`, `done`) она читает без блокировки.
2. Commit, публикация и повторы — множественными операторами (`unnest`, конвейер `pgx.Batch`): удержание блокировки 402 → десятки мс.
3. Welcome читается из базы один раз и держится в памяти. Каждому адресату DS отдаёт Welcome только с **его** записью `EncryptedGroupSecrets` (получатель ищет свою запись по `KeyPackageRef`, чужие ему не нужны). Доставка p50 1 750 → 20–25 мс при пачке 100 и 100–230 мс при пачке в 1 000; Welcome на 1 000 новичков — 302 → 186 КБ на устройство.
4. После commit-а следующая пачка публикуется сразу, не дожидаясь тика. Без этого `max-batch=100` при интервале 1 с ограничивал вход сотней устройств в секунду: 1 000 входов шли 10 с.

## Рекомендация по батчингу

1. **Режим DS: «фронт + батч».** Заявка в группе без ожидающих Add публикуется сразу. Пока Add ждут commit-а, новые заявки копятся, и следующая пачка уходит сразу после commit-а. Тик в 1 с — страховка для заявки, которая разминулась с commit-ом. Интервал дольше 1 с не нужен: он только добавляет задержку (батч 5 с → p50 ~6 с). Это уточняет меру ADR-0005 «батчинг proposal-ов в тихих каналах, ленивые коммиты»: ленивость нужна не заявке, а пачке.
2. **`max-batch` = 100.** Commit 6 КБ вместо 57 КБ, Welcome 112 КБ вместо 186 КБ, обработка Welcome 20 мс вместо 37 мс. Проверка одного Add почти в 6 раз дешевле (0,16 мс против ~0,93 мс). Последнее важно не только коммитеру: commit ссылается на предложения, поэтому **каждый** участник группы проверяет каждое Add.
3. **Remove не батчить.** Он публикуется сразу (от него зависит PCS), повторяется в каждой эпохе до commit-а, а commit без него не принимается. Опубликованный Add не отменяется — отменённый вход DS принимает и тут же удаляет.
4. **Один назначенный коммитер.** С 10 онлайн-участниками на 1–2 commit-а приходится 10–20 попыток: каждая проигравшая — это полная сборка commit-а впустую (до 250 мс CPU на 1 000 Add). Предложение для B02/B05: в `MlsUpdateRequested` DS называет одно устройство (например, давно онлайн и с наименьшим `leaf`), остальные ждут его commit-а 2–3 с и только потом коммитят сами. Один коммитер дал лучшую задержку среди сценариев на 1 000 входов.
5. **Сериализация в Postgres: блокировка строки группы.** `SELECT … FOR UPDATE` даёт в ~1,4 раза больше commit/с, чем `pg_advisory_xact_lock(hash)` (125 против 89 в эмуляторе при 10 коммитерах без пауз), не зависит от коллизий хэша и не требует второго пространства ключей. Обязательное правило порядка: commit, публикация и Remove берут строку группы → `pending_ops` → строку счётчиков commit-ов; заявка на вход строку группы не трогает — своя строка `pending_ops` → отдельная строка счётчика заявок (строку commit-ов она читает без блокировки). Спайк поймал две взаимоблокировки: заявка повышала `KEY SHARE` внешнего ключа до `UPDATE`, пока commit ждал `FOR UPDATE` (нагрузка, 2–3 заявки из 1 000 в каждом втором прогоне), и commit в advisory-режиме трогал `pending_ops` раньше строки группы (второе ревью, 8 из 60 раундов). А после исправления второй счётчик лимита в строке группы выстроил заявки и commit-ы в очередь друг за другом: 4 000 входов шли 46 с. Счётчик разнесён на две строки (заявки пишут «запрошено», commit-ы — «листья» и «закрыто»), внешний ключ `pending_ops → mls_groups` убран, страховка от N1 в публикации проверяет только кандидатов пачки по индексу — и время вернулось к ~24 с (19 с при пачке 500), а commit держит строку группы 41–72 мс (p95) во всех сценариях на 1 000 входов. Оставшийся предел — очередь заявок на строку своего счётчика (~1 000 заявок/с на группу, эмулятор).

## Рекомендация по лимиту участников

- **Лимит по умолчанию 2 000 участников (ADR-0005) и жёсткий лимит 5 000 листьев (ARCHITECTURE §4.3) оставить.** Узких мест, из-за которых ADR-0005 велит снижать лимит, спайк не нашёл. Всплеск из 4 000 одновременных входов в одну группу проходит за 24,2 с на одной машине с полностью загруженным CPU. В жизни такой всплеск — редкость (например, перенос сообщества), обычный вход — десятки миллисекунд.
- Цена на устройство растёт линейно с размером группы: Welcome ~100 Б на лист (392 КБ при 4 000 листьев), обработка Welcome ~25 мкс на лист на M4 Pro, на телефоне в 5–10 раз дольше (до ~1 с при 4 000). Это приемлемо до 5 000 листьев, но Welcome уже больше лимита события gateway (256 КиБ, GATEWAY.md): при группах от ~2 500 листьев все новички берут Welcome через REST. Отдельная раздача дерева (ADR-0016 «альтернативы») уменьшила бы Welcome, но не общий объём.
- DS считает лимит в **листьях**, то есть устройствах. Лимит «участников» (людей) — правило `community`/`channel` поверх него. При 2 000 участников и ~2,5 устройства на человека группа подходит к 5 000 листьям; DS отвечает `CHANNEL_MEMBER_LIMIT`, а интерфейс показывает «В канале достигнут лимит участников» (ADR-0005).

## Что выяснилось (важно для B02 и B05)

- **Форматы.** DS на Go читает открытые заголовки `PrivateMessage` и `PublicMessage`, KeyPackage и Welcome и подписывает предложения external sender. Объём — ~900 строк без внешних зависимостей (плюс ~120 строк сборщиков для эмулятора и тестов); разбор покрыт фаззерами (`just fuzz`). У отправителя `external` контекст группы в подпись не входит (RFC 9420 §6.1), поэтому DS не нужен GroupContext — но по той же причине подписанное предложение годится в любой ветке группы той же эпохи: довод против отката эпох при восстановлении рассинхрона.
- **`KeyPackageRef` — естественный ключ доставки Welcome.** DS считает его при загрузке пакета и сверяет адресатов Welcome с дельтой, так что клиенту не нужно отдельно перечислять получателей.
- **Welcome можно резать по адресатам на сервере.** Это экономит до 40 % трафика при пачке; формат RFC не меняется.
- **OpenMLS не даёт устройству закоммитить Remove самого себя** (`CannotRemoveSelf`). Реальная атака из ADR-0016 п. 4 — удаляемое устройство коммитит self-update, не обработав Remove. DS её отвергает (`REMOVAL_PENDING`, e2e шаг 3).
- **OpenMLS не даёт задать `authenticated_data` внешнему предложению** (`ExternalProposal::new_add` без AAD), а `set_aad` группы «залипает» на следующем сообщении. Для тестов клиента спайк подписывает external-предложения сам (`client/src/wire.rs`, 60 строк, побайтно равно openmls при пустом AAD); crypto-core (B03) должен принимать AAD явным параметром каждого вызова.
- **Повторы предложений.** Предложения живут одну эпоху, поэтому после каждого commit-а DS переиздаёт невошедшие. В режиме «сразу» без `max-batch` это от 0 до ~450 повторов на 1 000 входов, смотря как пачки совпали с commit-ами (в первой версии DS — 1 674), и каждый повтор проверяют все участники. С `max-batch` и с батчем повторов почти нет.
- **Проверка Add у участника** стоит 0,16–1 мс и зависит от длины очереди, всего за пачку из 1 000 — ~0,9 с на устройство. Если B02 захочет её удешевить, коммитер может включать Add inline (по значению). Тогда участники проверяют только commit, но теряют подпись сервера как доказательство, что вход разрешён. Спайк этот вариант не проверял.
- **Что видит DS** — в рамках модели угроз ARCHITECTURE §4.1: состав группы по устройствам (он и так известен серверу, потому что сервер решает, кому входить), эпохи, размеры, время. Дельта и AAD предложений не раскрывают ничего сверх этого. Ключей, текста и содержимого commit-ов у DS нет.

**Третий раунд** (N1, N2, N4, N5, N10 закрыты; утверждение про счётчики лимита подтверждено хаос-тестом — 8 прогонов, ~1 800 эпох, нарушений лимита и утечек нет; N6, N8, N9 доведены ниже)

|---|---|---|---|
| Н1 | «Ядовитый» KeyPackage через перекрёстную коллизию: init_key равен encryption_key листа (виден всем в дереве) или другого Add. DS и предфильтр пропускали, openmls отвергал commit, запасной путь выбрасывал невиновных (в PoC — все 5), Remove откладывался | средний | Исправлено: предфильтр клиента повторяет проверку openmls (ValSem101–104) — одно множество ключей с перекрёстными сравнениями, без удаляемых участников; на DS — общее пространство init- и encryption-ключей (`hpke_keys`). Точный поиск виновника — обязательное требование к B03 (`init_key_equal_to_member_encryption_key_is_dropped_alone`, `init_key_equal_to_other_add_encryption_key_is_dropped_alone`, `TestKeyPackageKeysUniqueAndLifetime`) |

**Точечная проверка исправления Н1.** Фильтр сверен с openmls 0.9.2, обхода DS нет; честные Add не выпадают. Найдено:

| № | Находка | Уровень | Что сделано |
|---|---|---|---|
| П1 | Тот же DoS через расширение листа, не указанное в capabilities: openmls проверяет его только при сборке commit-а, DS и фильтр клиента — нигде | средний | Исправлено: правило openmls (`LeafNode::validate_locally`) на DS при загрузке и в фильтре клиента (`leaf_extension_not_in_capabilities_is_dropped_alone`, `TestKeyPackageKeysUniqueAndLifetime`). Точный поиск виновника — главное требование к B03: предфильтр не исчерпывающий |
| П2 | Тесты защищали одно направление коллизии: 3 из 5 мутаций фильтра проходили | низкий–средний | Исправлено: пакеты, собранные вручную с произвольными ключами и расширениями; все 5 мутаций фильтра теперь роняют тесты (`encryption_key_equal_to_member_leaf_is_dropped_alone`, `cross_collision_in_reverse_order_drops_the_later_add`, `duplicate_init_key_only_is_dropped`, `init_key_equal_to_removed_member_key_is_kept`); на DS — дубль только encryption-ключа и коллизия внутри пачки |
| П3 | Формулировка ADR п. 4: перечень неполон, ValSem — нумерация openmls, а не RFC | низкий | Исправлено в ADR-0018 |
| П4 | Скрещённые одновременные загрузки давали взаимоблокировку вместо `INVALID_KEY_PACKAGE` | к сведению | Исправлено: ключи пачки вставляются одним оператором в отсортированном порядке |
| — | Срок добавленного пакета получатель проверяет по своим часам при обработке commit-а: устройство, обработавшее commit позже срока, застревает в старой эпохе (запас клиента в 60 с был неверен) | высокий для продукта | DS резервирует пакет с самым поздним сроком, клиент требует тот же остаток, что DS; ограничение и требование (граница ≥ горизонта офлайна, возврат external commit-ом) — в ADR-0018 п. 4 |

Остаётся и оговорено:

- Нет аутентификации: `device_id` в теле запроса не проверяется (в продукте — сессия устройства, B04). Чтение handshake-ов группы не ограничено её участниками.
- Credential — Basic с `device_id`; cross-signing ключом идентичности и проверка права на канал (роль Authentication Service на клиенте) — B02/B03.
- Ключи OpenMLS в памяти без `zeroize` (`MemoryStorage`, как в S1); ключ external sender DS генерируется при старте и нигде не хранится; его ротация — отдельная процедура B02 (клиент отвергает GroupContextExtensions от сервера). В `testdata/openmls/external_sender_seed.bin` лежит фиксированный тестовый seed (`[7; 32]`) для побайтовой сверки подписей, это не секрет; загрузчик ключа в B05 должен отвергать этот известный ключ.
- Доставка Welcome в спайке помечается при выдаче (после успешной сборки ответа); в продукте — подтверждение отдельным вызовом (REST.md `DELETE /mls/welcomes/{group_id}`).
- Процедуры восстановления рассинхрона нет; факт выполнения Remove DS проверить не может (N3); сверка состава только в той же эпохе (N7). GroupInfo и связка ключей истории в спайке не участвуют.
- Один процесс DS: long-poll будит `notifier` в памяти; в продукте — NATS (ARCHITECTURE §5.6). Кэш Welcome в памяти процесса; в продукте — Valkey или gateway.
- Взаимоблокировку из рекомендации п. 5 внутрипроцессный тест не воспроизводит; она ловится только нагрузкой по HTTP (`SCENARIOS="сразу, lock row" just load`).

## Как воспроизвести

Нужны Docker, Go 1.26+, Rust; `golangci-lint` v2 — для `just lint`. Из каталога `spikes/04-mls-ds`:

```bash
just test       # go test -race (Postgres через testcontainers) + cargo test
just e2e        # настоящие клиенты OpenMLS против DS: 26 проверок, режимы «сразу» и «батч 1 с»
just load       # матрица 1 000 входов × 12 сценариев × 3 повтора (~5 мин) → results/load.md
just load-big   # 4 000 входов (JOINERS=2000 just load-big — 2 000)
just emul       # потолок DS без криптографии → results/emul.md
just vectors    # пересоздать golden-векторы OpenMLS для тестов mlswire
just fuzz       # фаззинг разборщиков (6 целей), по 30 с на цель
just deps       # cargo deny, cargo audit, go-licenses
```
