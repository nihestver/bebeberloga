## 0. Соглашения

### 0.1 Нотация

Структуры, которые разбирают и клиент (Rust), и DS (Go), записаны на языке представления TLS в том виде, в каком его использует RFC 9420 §2.1: целые — big-endian, векторы `<V>` — с длиной в формате переменной длины RFC 9420 §2.1.2. **Правило проекта:** длина вектора кодируется минимальным числом байтов; разборщик отвергает неминимальную запись, лишние байты в конце структуры и неизвестную `version`. Одна и та же грамматика реализуется в Go и в Rust и проверяется общими тестовыми векторами (T10).

### 0.2 Идентификаторы

`user_id`, `device_id`, `channel_id`, `group_id` в REST и gateway — UUIDv7 строкой в нижнем регистре (ADR-0017). Внутри криптографических структур этого документа и в MLS `group_id` — **16 байт двоичного UUID** (RFC 9562). Перевод строки в байты принимает только каноническую строку из 36 символов в нижнем регистре; всё остальное — ошибка разбора. Сравнение идентификаторов — побайтное.

### 0.3 Метки и подписи приложения

Каждый вывод ключа, MAC, хэш и подпись проекта несёт метку `"bebeberloga/v1 " + назначение` (ASCII). Метки разных назначений не совпадают; полный список — §10.

Подписи приложения (не MLS):

```text
struct {
    opaque label<V>;      // "bebeberloga/v1 " + Label
    opaque content<V>;
} AppSignContent;

AppSign(sk, Label, Content)        = Ed25519-Sign(sk, AppSignContent)
AppVerify(pk, Label, Content, sig) = Ed25519-Verify(pk, AppSignContent, sig)
```

Конструкция повторяет приём `SignWithLabel` из RFC 9420 §5.1.2, но с собственным префиксом: подпись проекта никогда не совпадает по входу с подписью MLS тем же ключом.

## 1. MLS-профиль

### 1.1 Версия и ciphersuite

MLS 1.0 (`mls10`), ciphersuite 0x0001, credential Basic — других значений клиент и DS не принимают (ADR-0004 п. 1). Библиотека — `openmls` 0.9.x с `openmls_rust_crypto` и `openmls_basic_credential`, версии закреплены точно (ADR-0016 п. 1).

### 1.2 Ключ подписи устройства

У каждого устройства один долгоживущий ключ подписи Ed25519: им подписаны его листья во всех группах, KeyPackage и подписи проекта от имени устройства. Открытая часть — `Device.signature_pubkey`. Ключ подписан ключом идентичности пользователя (cross-signing, ARCHITECTURE §4.2) — §1.3. Устройство не меняет ключ подписи, пока существует; новый ключ — это новое устройство (§3).

### 1.3 Credential

Basic credential (RFC 9420 §5.3) несёт в поле `identity` сериализацию:

```text
struct {
    uint8  version = 1;
    opaque user_id[16];
    opaque device_id[16];
    opaque identity_signature[64];
} DeviceCredential;                       // 97 байт

struct {
    opaque user_id[16];
    opaque device_id[16];
    opaque signature_key<V>;              // ключ подписи листа (32 байта)
} DeviceBindingContent;

identity_signature = AppSign(identity_sk, "device binding", DeviceBindingContent)
```

Те же 64 байта лежат в `Device.identity_signature` (REST). Ключ идентичности в credential не входит: клиент всё равно сверяет его с известным ему ключом пользователя.

**Проверка листа (`CredCheck`).** Клиент выполняет её для каждого нового листа — в Add-предложении сервера, в начальном commit-е новой группы, для каждого листа дерева из Welcome и при пересоздании группы (§1.7, §1.8, §2.10):

1. credential — Basic; `identity` разбирается как `DeviceCredential` версии 1 ровно в 97 байт;
2. `AppVerify(IK(user_id), "device binding", {user_id, device_id, leaf.signature_key}, identity_signature)` — где `IK(user_id)` — ключ идентичности, которому клиент доверяет для этого пользователя (§3: закреплён при первой встрече и сверяется с `User.identity_pubkey`; смена ключа — SCREENS/07 §8);
3. устройство принадлежит `user_id`, подтверждено и не удалено (`GET /users/{id}/devices`, события `DeviceRemoved` своих устройств);
4. пользователь вправе быть в группе: канал и групповой чат — право `channel.see` и участие по данным сервера; звонок голосового канала или группового чата — участник звонка по данным сервера; **личная группа — только свой `user_id`**; **ЛС 1:1 и звонок в ней — только пара пользователей, которую клиент закрепил при создании разговора** (в личной группе, ЛС и звонке ЛС эту проверку делает клиент по своим данным, а не по ответу сервера — ревью безопасности Б-В2; повторное ревью, №6: иначе сервер подсадил бы в звонок ЛС устройство третьего пользователя с настоящим ключом идентичности);
5. `device_id` встречается в дереве не более одного раза.

Пункт 3 и пункт 4 для каналов, групповых чатов и их звонков опираются на данные сервера — это принятая граница доверия: сервер — Authentication Service (ARCHITECTURE §4.3); подмену ключей пользователя ловит проверка кода безопасности (§4), в v2 — Key Transparency.

### 1.4 KeyPackage

| Поле | Значение |
|---|---|
| `version`, `cipher_suite` | `mls10`, 0x0001 |
| `init_key` | новый X25519 на каждый пакет |
| `leaf_node.encryption_key` | новый X25519 на каждый пакет |
| `leaf_node.signature_key` | ключ подписи устройства (§1.2) |
| `leaf_node.credential` | Basic с `DeviceCredential` (§1.3) |
| `leaf_node.capabilities` | versions `[mls10]`, cipher_suites `[0x0001]`, extensions `[0xF0B1]` (§1.6), proposals `[]`, credentials `[basic]` |
| `leaf_node.leaf_node_source` | `key_package`, `lifetime`: `not_before = now − 1 ч`, `not_after = not_before + 90 сут` |
| `leaf_node.extensions`, `extensions` | пусто (пакетов «последней надежды» нет) |

- Пакеты загружает **только подтверждённое устройство**: до подписи ключом идентичности credential неполон. DS отвечает неподтверждённому `DEVICE_UNVERIFIED`.
- DS при загрузке проверяет всё из ADR-0018 п. 4 (подписи, версия, ciphersuite, capabilities, расширения листа, верхняя граница срока, уникальность HPKE-ключей) и дополнительно: `DeviceCredential` разбирается, `device_id` — устройство, загружающее пакет, `signature_key` = `Device.signature_pubkey`, `identity_signature` проверяется действующим ключом идентичности пользователя, остаток срока ≥ `KP_MIN_REMAINING`. Ошибка — `INVALID_KEY_PACKAGE`.
- DS удаляет пакеты, остаток которых упал ниже `KP_MIN_REMAINING`, и все пакеты устройств пользователя при смене его ключа идентичности.
- Склад: клиент держит `KP_STOCK` = 100 пакетов и пополняет до 100, когда их меньше `KP_REFILL_BELOW` = 50 (`GET /devices/me/key-packages`); проверяет после `Ready`, после каждого принятого Welcome и раз в час в сети. Вход в сообщество расходует по пакету на каждую группу каналов, поэтому запас крупный. Если пакетов нет, вход ждёт пополнения (§2.7), а не завершается ошибкой.
- Приватные ключи пакета клиент хранит до его использования или до `not_after`, затем стирает.

### 1.5 Конфигурация группы

| Параметр (имя в openmls) | Значение | Почему |
|---|---|---|
| Политика формата (`wire_format_policy`) | `PURE_CIPHERTEXT` | handshake участников всегда зашифрованы (ADR-0016 п. 2) |
| Дерево в Welcome (`use_ratchet_tree_extension`) | `true` | новичку не нужен отдельный запрос дерева (ADR-0016 п. 2) |
| Прошлые эпохи (`max_past_epochs`) | 0 | application-сообщений MLS в 1.0 нет: обычные сообщения шифруются ключом сообщения под ключом истории (§6.2.7); секреты прошлых эпох не хранятся |
| Окно порядка (`sender_ratchet_configuration`) | `out_of_order_tolerance = 5`, `maximum_forward_distance = 1000` | значения по умолчанию openmls, проверены в S1 |
| Паддинг (`padding_size`) | 0 | через MLS идут только commit-ы, их размер раскрывает лишь изменение состава, которое сервер и так знает; паддинг сообщений — на `SealedMessage` (§6.2.3) |
| Проверка срока листьев дерева при входе по Welcome | отключена (`JoinBuilder::skip_lifetime_validation`) | §1.8 |

Срок KeyPackage в Add-предложении при обработке commit-а openmls проверяет всегда, отключить нельзя (ADR-0018 п. 4) — на этом построен горизонт офлайна (§2.11).

### 1.6 Расширения GroupContext

Создатель группы задаёт ровно три расширения; после создания они не меняются, кроме замены ключа инстанса (§2.12).

1. **`external_senders`** — один элемент с индексом 0: ключ подписи DS инстанса (§2.12) и Basic credential с `identity = "bebeberloga/v1 instance"`. Клиент сверяет ключ с закреплённым ключом инстанса — при создании группы, при входе по Welcome и после каждого merge.
2. **`required_capabilities`** — extensions `[0xF0B1]`, proposals `[]`, credentials `[basic]`. Пакет без поддержки 0xF0B1 не войдёт в группу на уровне самой MLS.
3. **`group_binding`** (тип 0xF0B1, диапазон частного использования RFC 9420 §17.3) — привязка группы к каналу:

```text
struct {
    uint8  version = 1;
    opaque channel_id[16];
    uint8  kind;                      // 1 — чат канала (GROUP_KIND_CHAT), 2 — звонок (GROUP_KIND_CALL)
    opaque predecessor_group_id<V>;   // пусто или 16 байт: группа, которую эта заменяет (§2.10)
    uint64 predecessor_epoch;         // последняя согласованная эпоха предшественницы; 0, если её нет
    opaque continuity_tag<V>;         // пусто или 32 байта (§2.10.4)
} GroupBinding;
```

Привязка не даёт серверу выдать группу одного канала за группу другого и связывает пересозданную группу с предшественницей (§2.10). Значение `kind = 3` зарезервировано за личной группой пользователя (§6, решение Р5).

### 1.7 Политика клиента: что принимается

Клиент — Authentication Service для своих групп (ADR-0016 п. 3). Всё, что приходит от DS, недоверенное.

**Предложение от сервера — до постановки в очередь** (`store_pending_proposal`):
- отправитель — `External(0)`, ключ из `external_senders` = закреплённый ключ инстанса;
- тип — только Add или Remove; GroupContextExtensions, PSK, ReInit и любые другие — отвергаются;
- `authenticated_data` разбирается как `ProposalAAD` (§2.3);
- Add: `CredCheck` листа пакета (§1.3) и `ProposalAAD.device_id` = `device_id` из credential; срок пакета не больше `KP_LIFETIME_MAX`: `not_after − not_before ≤ 90 сут` и `not_after ≤ сейчас + 90 сут` — openmls верхнюю границу не проверяет (S1, риск 3); если у устройства уже есть лист — Add допустим только вместе с Remove этого листа в одном commit-е (возврат, §2.11);
- Remove: на указанном листе стоит устройство `ProposalAAD.device_id`.

**Отвергается всегда:** предложение от `new_member_proposal` (ADR-0016 п. 3, находка S1 Б1), external commit (отправитель `new_member_commit`, ADR-0019), предложения участников по ссылке (в 1.0 участники предложений не шлют).

**Чужой commit — до merge** (`StagedCommit`):
- все предложения по ссылке — от `External(0)` и ранее прошли проверки выше;
- предложения по значению допустимы только в двух случаях: Add в начальном commit-е новой группы (эпоха 0 → 1, автор — создатель, каждый лист проходит `CredCheck`) и GroupContextExtensions замены ключа инстанса (§2.12);
- commit содержит все Remove, которые сервер опубликовал и которые клиент видел в этой эпохе (ADR-0016 п. 4);
- лист автора в UpdatePath и листья из Update сохранили credential и `signature_key` побайтно (находка S4 Б1);
- `RosterDelta` в `authenticated_data` совпадает с фактическим действием commit-а (§2.3), флаги — с фактическим содержимым;
- после merge хэш состава дерева (§2.5) равен `Handshake.roster_hash` от DS.

Нарушение любого пункта: клиент **не** применяет commit (`clear`/отказ от staged commit), подаёт жалобу (§2.9) и ждёт; группа для него в состоянии «ошибка ключей» (SCREENS/08 §8).

**Свой commit:** применяется (`merge_pending_commit`) только после явного подтверждения DS — ответа `201` или побайтного совпадения с тем, что пришло в потоке группы (ADR-0018 п. 5). Реакция на коды отказа — §2.13.

### 1.8 Вход по Welcome

1. Welcome приходит от DS (`MlsWelcome`, `GET /mls/welcomes`) с `channel_id`, `kind`, `epoch`, `seq`.
2. Обработка с отключённой проверкой срока листьев дерева. Срок есть только у листьев, ни разу не обновлённых после Add (RFC 9420 §7.3 называет эту проблему). Срок листа уже проверен тогда, когда лист добавляли: openmls сверяет срок пакета при обработке commit-а с Add (§1.5), а DS не пропускает пакет на исходе (§2.4). После добавления срок ничего не защищает: он не отзывает ключи листа и не мешает тому, кто ими завладел. От украденного устройства защищает Remove (§2.8): пользователь удаляет устройство в настройках (SCREENS/07 §6), и сервер удаляет его из всех групп. Проверка срока при входе лишь закрыла бы вход всем новичкам из-за любого участника, добавленного больше `KP_MIN_REMAINING` назад и не делавшего commit-ов. Ограничение — нет PCS для украденного, но не удалённого устройства в большой группе — §8.2.
3. `group_binding` есть, версия 1, `channel_id` и `kind` равны присланным DS; `external_senders` — закреплённый ключ инстанса; `required_capabilities` — как в §1.6.
4. `CredCheck` (§1.3) для каждого листа дерева.
5. Хэш состава дерева (§2.5) равен хэшу DS для этой эпохи (`GET /mls/groups/{id}` или `GET /mls/groups/{id}/roster?epoch=`).
6. Если `predecessor_group_id` не пуст — проверки пересоздания (§2.10.6).
7. После успеха — `DELETE /mls/welcomes/{group_id}` (подтверждение доставки, ADR-0018 п. 8). При отказе клиент в группу не входит и подаёт жалобу на commit `seq` с причиной (§2.9). Для адресата Welcome она личная: DS вернёт устройство заново (§2.9.2), а если состояние группы снова не пройдёт проверки — клиент повторяет с паузами `RESYNC_BACKOFF` (§2.9.5). Исключение — `RECREATION_INVALID` на пересозданную группу (§2.9.1).

### 1.9 Ротация эпох

- **При смене состава** — каждый commit с Add или Remove открывает новую эпоху.
- **Плановая** — не реже раза в `ROTATION_PERIOD` = 24 ч на активной группе (в группе за последние 24 ч было хотя бы одно сообщение или handshake): DS шлёт `MlsUpdateRequested{REASON_SCHEDULED_ROTATION}` назначенному устройству (§2.6), оно делает commit без предложений с UpdatePath. Назначается устройство, чей последний commit в этой группе самый давний. Ротация обновляет секреты эпохи и путь коммитера, но не листья остальных: в группе на N листьев конкретный лист плановой ротацией обновляется в лучшем случае раз в N суток — в канале на 5 000 листьев раз в годы. На свежесть ключей конкретного листа она не рассчитана (§8.2).
- **Ручная** — «Обновить ключи канала» (`POST /channels/{id}/mls/rotate`, право `channel.edit`, SCREENS/06 §5.2) → `REASON_MANUAL`.
- Группы звонков следуют тем же правилам.

## 2. Delivery Service

### 2.1 Роль

DS упорядочивает handshake-сообщения по группе, хранит KeyPackage, Welcome и карту состава, подписывает Add и Remove как external sender, назначает коммитера, замораживает и сопровождает пересоздание группы.

DS **никогда** не создаёт commit, не получает ключей групп, не видит содержимого commit-ов и сообщений, не хранит и не публикует GroupInfo (ADR-0019). Ключ external sender DS применяет только для подписи Add и Remove (`PublicMessage`, RFC 9420 §6.2).

### 2.2 Что DS принимает

| Запрос | Требование | Отказ |
|---|---|---|
| `POST …/handshakes`, `kind = COMMIT` | `PrivateMessage`, `content_type = commit`, `group_id` и эпоха — текущие; отправитель — устройство из карты состава без ожидающего Remove, **назначенное DS на эту эпоху** (§2.6); группа не заморожена и не на проверке | `EPOCH_MISMATCH`, `NOT_DESIGNATED`, `NOT_GROUP_MEMBER`, `REMOVAL_PENDING`, `GROUP_FROZEN`, `GROUP_UNDER_REVIEW`, `BAD_MESSAGE` и проверки §2.4 |
| `POST …/handshakes`, `kind = PROPOSAL` | в 1.0 участники предложений не шлют | `UNAUTHORIZED_CHANGE` |
| `POST …/handshakes`, `kind = EXTERNAL_COMMIT` | не используется (ADR-0019) | `EXTERNAL_COMMIT_UNSUPPORTED` |
| Любой `PublicMessage` от клиента | — | `BAD_MESSAGE` (а `new_member_commit` — `EXTERNAL_COMMIT_UNSUPPORTED`) |
| `POST /channels/{id}/messages` | `SealedMessage` (§6.2), устройство в карте состава, `history_key_generation` — текущее поколение канала (fail-closed для устаревших поколений); во время проверки (§2.9.3) принимаются | `HISTORY_GENERATION_MISMATCH`, `NOT_GROUP_MEMBER`, `GROUP_FROZEN` |
| MLS application message (`PrivateMessage`, `content_type = application`) | в 1.0 не используется (§6.2.7) | `BAD_MESSAGE` |
| `POST …/handshakes/{seq}/ack` | только во время проверки commit-а `seq` (§2.9.3), от устройства, бывшего в карте в его базовой эпохе | `CONFLICT`, `NOT_GROUP_MEMBER` |

Повтор уже принятого commit-а (тот же блоб, эпоха на единицу меньше текущей) получает тот же ответ, что и первый, — и на быстром пути, и под блокировкой группы (ADR-0018 п. 5).

### 2.3 Грамматика `authenticated_data`

Обе структуры разбирают Go (DS) и Rust (crypto-core) по одной грамматике (§0.1).

```text
struct {
    uint8  version = 1;
    opaque device_id[16];             // кого добавляет Add / кто стоит на листе Remove
    uint32 history_from_generation;   // для Add — граница права на историю от сервера: только сужает (§6.3.7); для Remove — 0
} ProposalAAD;                        // authenticated_data предложений сервера, под подписью DS

struct {
    uint32 leaf;
    opaque device_id[16];
} AddedLeaf;

enum {
    none(0), rotate(1), break_new_member(2), break_enable(3), break_reset(4), break_recreate(5), break_disable(6), (255)
} HistoryChange;                      // §6.3.3

struct {
    uint8         version = 1;
    uint8         flags;              // бит 0 — заменён external_senders (§2.12); остальные 0
    HistoryChange history_change;     // начинает ли commit новое поколение ключа истории (§6.3.3)
    uint32        removed<V>;         // удалённые листья, строго по возрастанию
    AddedLeaf     added<V>;           // добавленные листья в порядке применения
} RosterDelta;                        // authenticated_data каждого commit-а участника
```

- Индексы новых листьев детерминированы (RFC 9420 §12.1.1, §12.3): сначала применяются Remove, затем каждый Add занимает самый левый пустой лист или расширяет дерево вправо. Одна функция назначения листьев у автора, получателей и DS (S4).
- Порядок Add в commit-е задаёт openmls; автор строит дельту после сборки commit-а и сверяет её с фактическим (S4). AAD передаётся в crypto-core параметром каждого вызова, без состояния в группе (ADR-0018, `set_aad` «залипает»).
- Commit без изменений состава несёт `RosterDelta` с пустыми списками.
- Значения `HistoryChange` в контракте (`mls.proto`) сдвинуты на единицу: `HISTORY_CHANGE_UNSPECIFIED = 0` занят правилом proto3, поэтому значение proto = значение в `RosterDelta` + 1 (`none(0)` ↔ `HISTORY_CHANGE_NONE = 1`, …, `break_recreate(5)` ↔ `HISTORY_CHANGE_BREAK_RECREATE = 6`, `break_disable(6)` ↔ `HISTORY_CHANGE_BREAK_DISABLE = 7`).
- DS проверяет `MAX_AAD` до блокировки группы.

### 2.4 Проверки commit-а

**DS** (ADR-0018 п. 2) отвергает commit, если:

| Проверка | Код |
|---|---|
| `authenticated_data` не разбирается как `RosterDelta` | `BAD_DELTA` |
| удаляемый лист пуст или для него нет опубликованного Remove | `UNAUTHORIZED_CHANGE` |
| в commit не вошли все опубликованные Remove | `PROPOSALS_MISSING` |
| листья добавленных устройств не те, что дают правила §2.3 | `BAD_DELTA` |
| для добавленного устройства нет опубликованного Add (кроме начального commit-а новой группы — там устройство должно быть допущено к каналу, а пакет зарезервирован этим создателем) | `UNAUTHORIZED_CHANGE` |
| Add устройства, у которого уже есть лист, без Remove этого листа | `BAD_DELTA` |
| превышен лимит листьев | `CHANNEL_MEMBER_LIMIT` |
| адресаты Welcome (по `KeyPackageRef`) не совпадают с добавленными устройствами, или пакет одного из них имеет остаток меньше `KP_MIN_REMAINING` | `BAD_WELCOME` |
| `flags` содержит неизвестный бит или бит 0 без запроса замены ключа инстанса | `BAD_DELTA` |
| при выключенной истории канала commit добавляет устройство нового пользователя (§6.3.3), а `history_change` — не разрыв (ревью Б-Н10: DS знает и настройку, и карту состава) | `BAD_DELTA` |
| настройка выключена, выключение ещё не записано в цепочке (последний разрыв настройки — не `break_disable`), а commit не несёт ни `break_disable`, ни `break_reset` (§6.3.3, повторное ревью №7) | `BAD_DELTA` |
| в commit-е есть Remove, кроме пары возврата того же `device_id`, а `history_change = none`; ссылка (§6.3.4) есть без `rotate` или нет при `rotate`; поколение связки (§6.3.5) не равно поколению после commit-а (у начального commit-а пересоздания — меньше `RecreationPlan.next_generation`, §2.10.5) | `BAD_DELTA` |

Принятый commit DS применяет к карте состава (§2.5), режет Welcome по адресатам (ADR-0018 п. 8) и рассылает `MlsHandshake` с `roster_hash`.

**Получатель** проверяет commit до merge по §1.7 и после merge — хэш состава.

### 2.5 Карта состава по эпохам

DS ведёт карту `лист → устройство` по дельтам и хранит её для каждой эпохи в пределах `HANDSHAKE_RETENTION` (достаточно журнала дельт). Хэш состава:

```text
struct {
    uint32 leaf;
    opaque device_id[16];
} RosterEntry;

struct {
    opaque      label<V> = "bebeberloga/v1 roster";
    opaque      group_id[16];
    uint64      epoch;
    RosterEntry entries<V>;           // все непустые листья по возрастанию leaf
} RosterHashInput;

roster_hash = SHA-256(RosterHashInput)
```

Клиент считает тот же хэш по своему дереву (`device_id` — из `DeviceCredential` каждого листа). Где он приходит от DS: `Handshake.roster_hash` для каждого commit-а (состав после него), `Group.roster_hash` (текущий), `GET /mls/groups/{id}/roster?epoch=` (полный список — для новичков, диагностики и пересоздания). Сверка — после каждого merge и после входа по Welcome (ADR-0018 п. 3). Несовпадение — жалоба `ROSTER_MISMATCH` (§2.9).

### 2.6 Назначенный коммитер

Commit делает одно устройство, которое называет DS (ADR-0018 п. 7): `MlsUpdateRequested{group_id, reason, designated_device_id, epoch}` уходит всем онлайн-устройствам группы, коммитит только названное. Остальные не коммитят, а ждут commit в потоке. Если commit этой эпохи не пришёл за `COMMIT_DESIGNATION_TIMEOUT` = 3 с, DS назначает следующего кандидата новым событием. Это уточняет ADR-0018 п. 7: вместо свободной гонки по таймауту — повторное назначение, чтобы десятки онлайн-участников не собирали commit впустую.

Порядок кандидатов (онлайн — есть открытая сессия gateway). Во всех пунктах действуют общие фильтры: устройство в группе и в сети, без ожидающего Remove, не участник открытой жалобы (§2.9). **Испытательный срок** (решение владельца по повторному ревью безопасности, ADR-0021): устройства пользователей, вступивших в сообщество меньше `DESIGNATION_PROBATION` = 7 сут назад, назначаются, только если других кандидатов в сети нет. Без этого свежий аккаунт получал бы назначение почти сразу: устройство без commit-ов в группе идёт в п. 4 первым. В ЛС и групповых чатах вне сообщества срока нет. Ещё позже идут устройства **отстранённых** пользователей (см. ниже). Итоговый порядок: сначала остальные кандидаты по пп. 1–4, затем пользователи на испытательном сроке, затем отстранённые; испытательный срок и отстранение не лишают права коммитить, а только опускают в конец.

1. **Add нового устройства D пользователя U после подтверждения** — устройство U, подтвердившее D (`POST /devices/{D}/verify`), если оно в группе и в сети: оно состоит во всех группах U, и новое устройство подключается сразу (FLOWS/02 ш. 4.4). Затем — другие устройства U в группе и в сети.
2. **Возврат устройства D пользователя U** (§2.11) — другие устройства U в группе и в сети.
3. **Пересоздание** — §2.10.4.
4. **Во всех остальных случаях и после исчерпания пп. 1–2** — остальные устройства группы; по возрастанию времени своего последнего commit-а в этой группе, затем по возрастанию `leaf`.

**DS принимает commit только от назначенного устройства** — от любого из устройств, назначенных на текущую эпоху (при повторных назначениях выигрывает первый принятый commit); от остальных — `NOT_DESIGNATED`. Исключение — начальный commit новой группы, который её создатель передаёт в `POST /mls/groups` (§2.10.5). Назначение не делает автора доверенным: его commit по-прежнему проверяют получатели (§1.7), а жалобы на него разбирает §2.9.

**Отстранение** (решения владельца по ревью безопасности, ADR-0021). Если жалоба на commit подтверждена по правилу 1 §2.9.3 — пожаловались не меньше двух пользователей, и их не меньше подтвердивших, — пользователь-автор commit-а `DESIGNATION_BAN` = 30 сут теряет **приоритет, но не право**: в любой группе инстанса его устройства назначаются коммитером — по любому пункту, в том числе создателем при пересоздании другой группы (§2.10.4), — только если других кандидатов в сети нет. Других причин отстранения нет: одиночная жалоба (правило 3 §2.9.3), застой (§2.9.6) и сбой в группе звонка (§5.1) вину автора подсчётом голосов не доказывают (третье ревью безопасности, №4, №5, №7). Отстранение — запись DS по `user_id`, а не по группе (повторное ревью безопасности, №4): пересоздание с новым `group_id` его не снимает, а подтверждение своего нового устройства отстранённому приоритета не возвращает.

Право остаётся, чтобы удаление устройства всегда доходило до commit-а — инвариант «удаление устройства = commit во всех его группах» (третье ревью безопасности, №3; clean room Н1): в ЛС, где собеседник не в сети, и в звонке, где в сети одни отстранённые, commit с Remove делает отстранённый. **В личной группе отстранения нет**: в ней только устройства самого пользователя, и навредить он может только себе. Честный пользователь замечает отстранение, только если пересоздание по его жалобе назначает создателем другого: в остальном его commit-ы делают другие, а без них — он сам.

В группе звонка таймаут — `COMMIT_DESIGNATION_TIMEOUT_CALL` = 1 с, а порядок кандидатов — §5.1. Устройство, не уложившееся в таймаут, уходит в конец очереди на 10 минут. Создатель новой группы канала (новый канал, ЛС, первый вход в звонок) делает её начальный commit без назначения; создателя при пересоздании назначает DS (§2.10.4).

Новое устройство загружает KeyPackage только после подтверждения (§1.4), поэтому DS публикует его Add, как только пакеты появятся (§2.7); подтвердившее устройство получает назначение в тот же момент.

### 2.7 Add

- **Публикация** — «фронт + батч» (ADR-0018 п. 6): заявка в группе без ожидающих Add публикуется сразу; пока Add ждут commit-а, заявки копятся и уходят пачкой до `MAX_BATCH` = 100 сразу после commit-а; тик `BATCH_TICK` = 1 с — страховка. **В группе звонка пачки нет**: каждая заявка публикуется сразу, а commit-ы идут не чаще раза в `CALL_COMMIT_MIN_INTERVAL` (§5.1).
- **Пакет** — пакет устройства с самым поздним `not_after`, остаток ≥ `KP_MIN_REMAINING`. Действует **только текущий зарезервированный пакет** устройства: commit, добавляющий устройство по пакету, который DS уже заменил (§2.7, «свежесть пакета»), DS отвергает (`BAD_WELCOME`); фильтр коммитера оставляет **не больше одного Add на `device_id`** — опубликованный последним (ревью Б-Н5). Иначе старый Add с остатком чуть больше порога и новый Add вместе дали бы два листа одного устройства.
- **Ожидание без срока.** Если в группе никого нет в сети, эпохи не идут и `MAX_ADD_EPOCHS` не срабатывает. Заявка на вход ждёт сколько угодно и снимается **только при потере доступа**: пользователь потерял `channel.see`, вышел, выгнан или забанен, устройство удалено, канал удалён.
- **Свежесть пакета по времени.** Тик DS проверяет пакет каждого ожидающего Add: когда остаток падает ниже `KP_REFRESH_AT` = 32 сут, DS резервирует свежий пакет устройства и публикует Add заново (старое предложение в очередях участников остаётся, но участник его отбросит фильтром, §1.7, а DS не примет Welcome по нему, §2.4). Если свежих пакетов нет — заявка ждёт загрузки (`awaiting_key_package`) и публикуется сразу после неё.
- **Эпохи без включения.** Если опубликованный Add не вошёл в commit за `MAX_ADD_EPOCHS` = 20 эпох (участники его отбрасывают), DS заменяет пакет другим пакетом устройства, а не снимает заявку; нет других — ждёт загрузки.
- **Отмена опубликованного Add** — DS принимает commit, Welcome не выдаёт и сразу публикует Remove нового листа (ADR-0018 п. 6).
- **Перепроверка членства после заявки** (S4 N1): после записи заявки на вход DS проверяет членство устройства ещё раз — заявка, разминувшаяся с commit-ом, который это устройство уже добавил, снимается; публикация и повтор Add снимают заявки устройств, уже стоящих в карте; Remove участника заменяет любую его заявку. Иначе вошедшему устройству остался бы «висящий» Add, и его Remove потом не записался бы.
- **«Липкий» бан** (S4 Н5, ADR-0018 «Последствия» для B05): заявка на вход несёт версию авторизации пользователя в канале (приглашение, права); бан и потеря доступа повышают её в той же строке, а публикация Add и снятие отмены требуют версию не старше текущей — проверка в той же транзакции. Заявка, проверенная до бана, после него не выполнится.
- **Предложения по значению** — только в начальном commit-е новой группы (§2.4).
- **Фильтр коммитера** — перед commit-ом клиент выбрасывает Add с негодным пакетом (ADR-0018 п. 4: остаток < `KP_MIN_REMAINING`, capabilities, расширения листа, совпадения ключей подписи и HPKE, в том числе перекрёстные) и коммитит остальное, а если не осталось ничего — commit без предложений, только со своим путём, чтобы DS видел ответ на назначение (§2.9.6); при отказе openmls находит виновника точно — по варианту ошибки или бисекцией (требование B03): один «ядовитый» пакет не должен выбивать пачку невиновных и откладывать Remove (S4 Б2, Н1, П1).

### 2.8 Remove

- Публикуется сразу, без батча; повторяется в каждой новой эпохе, пока commit не включит его в `RosterDelta`.
- С момента публикации DS не доставляет устройству новых сообщений и удаляет его недоставленные Welcome (S4 Н2); commit от устройства с ожидающим Remove — `REMOVAL_PENDING`; commit без опубликованного Remove — `PROPOSALS_MISSING`.
- Честные клиенты не применяют commit без объявленного Remove (§1.7) и жалуются (§2.9) — это и есть сигнал, на который опирается факт удаления (ADR-0018 п. 2).
- **Подтверждение.** Remove из commit-а эпохи E → E+1 считается выполненным, когда (а) устройство пользователя, отличного от автора commit-а, подтвердило commit (`ack` или commit поверх него, §2.9.2; application-сообщения не считаются — их поле `epoch` пишет сам клиент) и жалобы на этот commit нет, или (б) прошло `REMOVE_CONFIRM_WINDOW` = 24 ч без жалобы. До подтверждения повторный вход удалённого устройства получает `CONFLICT` (S4 Н4), кроме пары Remove + Add возврата (§2.11). Подтверждённая жалоба на commit (§2.9.3) отменяет «выполнено» и ведёт к пересозданию, где устройство исключено из состава (§2.10.3).

### 2.9 Жалоба на commit и проверка

Жалоба — сигнал честного клиента, что он не принял commit (ADR-0018 п. 2). Сам DS её проверить не может: содержимое commit-а зашифровано. Поэтому он смотрит, как на тот же commit отреагировали другие пользователи, и выбирает самое дешёвое лечение: вернуть одно устройство (§2.11) или пересоздать группу (§2.10). Безопасность от вердикта DS не зависит: честный клиент не применяет commit, который не прошёл его проверки, и не входит в группу, состояние которой их не проходит (§1.7, §1.8, §2.10.6). Вердикт решает только вопрос доступности — кто продолжает работу, а кто остаётся в состоянии «ошибка ключей».

`POST /mls/groups/{group_id}/disputes {seq, reason}` → `202`.

#### 2.9.1 Причины: личные и структурные

| `reason` | Вид | Что не так |
|---|---|---|
| `DISPUTE_REASON_DELTA_MISMATCH` | структурная | `RosterDelta` не совпадает с действием commit-а или флагами |
| `DISPUTE_REASON_MISSING_REMOVE` | структурная | нет объявленного сервером Remove |
| `DISPUTE_REASON_UNAUTHORIZED_ADD` | структурная | Add не прошёл `CredCheck` или не от сервера |
| `DISPUTE_REASON_LEAF_CREDENTIAL_CHANGED` | структурная | UpdatePath или Update сменили credential или ключ подписи листа |
| `DISPUTE_REASON_FORBIDDEN_PROPOSAL` | структурная | GroupContextExtensions (кроме §2.12), PSK, ReInit, ExternalInit, предложение участника |
| `DISPUTE_REASON_ROSTER_MISMATCH` | структурная | состав после merge не совпадает с картой DS |
| `DISPUTE_REASON_BINDING_MISMATCH` | структурная | `group_binding`, `external_senders` или `required_capabilities` не те |
| `DISPUTE_REASON_UNDECRYPTABLE` | личная | клиент обработал все предыдущие handshake группы, а commit его эпохи не расшифровывается или не проходит проверки MLS |
| `DISPUTE_REASON_KEY_PACKAGE_EXPIRED` | личная | срок пакета в Add истёк по часам клиента, хотя commit моложе `HORIZON` |
| `DISPUTE_REASON_RECREATION_INVALID` | структурная | пересозданная группа не прошла проверки §2.10.6 |
| `DISPUTE_REASON_HISTORY_ROTATION_MISSING` | структурная | нет обязательной ротации или разрыва ключа истории (§6.3.3) |
| `DISPUTE_REASON_HISTORY_LINK_INVALID` | структурная | ссылка цепочки не расшифровывается в предыдущий ключ (§6.3.4) |

**Структурные** причины касаются содержимого commit-а, а оно у всех получателей одно: DS раздаёт один блоб, одни и те же предложения и одну карту состава. Настоящий структурный дефект увидят все честные клиенты, которые обрабатывают commit. **Личные** причины обычно объясняются состоянием или часами самого клиента, но не всегда: «мусорный» commit — случайные байты с корректной дельтой — не расшифруется ни у кого.

Поэтому **действие DS определяет не вид причины, а подтверждение commit-а другими пользователями** (решение владельца по ревью безопасности, ADR-0021; §2.9.2). Вид причины остаётся для журнала и диагностики. Так же разбирается жалоба **адресата Welcome** (новичок или возвращающееся устройство, у которого Welcome не прошёл §1.8): жалоба относится к commit-у, создавшему Welcome.

#### 2.9.2 Что DS делает с жалобой

DS принимает жалобу от устройства, которое было в карте состава в базовой эпохе commit-а `E` (или адресата его Welcome), не является его автором и не имеет ожидающего Remove. Иначе — `NOT_GROUP_MEMBER` или `REMOVAL_PENDING`. Жалоба другого устройства **пользователя-автора** в голосах не учитывается: DS сразу возвращает это устройство (§2.11.2) — разлад между устройствами одного пользователя его собственная проблема (повторное ревью безопасности, №8: иначе `C` = `A` = 0, и правило 3 подтверждало бы жалобу автора на самого себя).

**Подтверждение.** Commit `c` подтверждает пользователь, устройство которого прислало `ack` (§2.9.3) или принятый поверх `c` commit, если этот пользователь — не автор `c` и не подавший жалобу, а устройство было в карте в эпохе `E` и не добавлено самим `c`. Подтверждением **не** считаются: `ack` и commit-ы пользователя-автора `c`, application-сообщения (их поле `epoch` пишет сам клиент, §6.2.8).

В группе звонка подсчёта голосов, проверки и заморозки нет — сбой ведёт к новой группе звонка (§5.1). Ниже — группы каналов, ЛС и групповых чатов.

**Голоса считаются при любой жалобе** (повторное ревью безопасности, №1). Короткого пути «`c` подтвердил хотя бы один другой пользователь — значит, жалоба личная» нет: при нём сообщник автора одним commit-ом поверх `c` переводил бы в личные жалобы всех честных клиентов, а их возвраты мог бы собрать только он сам — канал стоял бы навсегда. На жалобу (в пределах `DISPUTE_RATE`, **с любой причиной**, в том числе `UNDECRYPTABLE` и `KEY_PACKAGE_EXPIRED`) DS заводит подсчёт голосов по `c` (§2.9.3) — один на commit, следующие жалобы на тот же `c` входят в него:

1. **`c` — последний принятый commit группы** — проверка **с паузой** handshake (§2.9.3): спорный commit остаётся последним, и пересоздание будет точным. Commit-ы пользователя-автора поверх `c` его последним не отменяют: проверяется `c`, а при пересоздании они отбрасываются вместе с ним.
2. **Поверх `c` уже приняты commit-ы других пользователей** — подсчёт **без паузы**: handshake идёт дальше, решение — по тем же правилам §2.9.3, авторы commit-ов поверх `c` входят в `A`. Сюда попадает и «поздняя» жалоба устройства, вернувшегося через несколько дней: группа давно ушла дальше, `A` велико, жалоба отклоняется, и устройство возвращается.

Итог в обоих случаях: жалоба подтверждена — заморозка и пересоздание от базовой эпохи `c` (§2.10.1), все commit-ы поверх `c` отбрасываются вместе с ним; отклонена — возврат пожаловавшихся устройств (§2.11.2) в пределах `RESYNC_RATE`. До решения устройство не возвращается: если `c` «мусорный», commit возврата никто не соберёт — в эпохе после `c` нет ни одного устройства. Если `RECREATION_LIMIT` исчерпан — §2.9.4.

#### 2.9.3 Проверка

Пока идёт проверка commit-а `c` (эпоха `E` → `E+1`) с паузой:

- **Бюджет паузы** (ревью Б-Н7): суммарное время паузы handshake из-за проверок в группе — не больше `REVIEW_BUDGET` = 10 мин за скользящий час, сколько бы аккаунтов ни подавали жалобы. Сверх бюджета голоса считаются без паузы, как в §2.9.2 п. 2: решение то же, пересоздание — от базовой эпохи `c`. Так ожидающие Remove не задерживаются дольше бюджета.

- `Group.state = GROUP_STATE_REVIEW`, `Group.review_seq = seq(c)`; событие `MlsGroupStateChanged{state: REVIEW, review_seq}` членам группы, у подключающихся — `MlsPending.review_seq`.
- **DS приостанавливает только handshake**: не принимает commit-ы (`GROUP_UNDER_REVIEW`) и не публикует новые предложения; новые Add и Remove копятся и выйдут после решения (доставка сообщений устройству с ожидающим Remove прекращается сразу, как обычно, §2.8). Так спорный commit остаётся последним, и пересоздание будет точным.
- **Сообщения в эпохе `E+1` принимаются.** Немедленная заморозка сообщений не нужна: структурный дефект видят все честные клиенты, они commit не применят и в `E+1` писать не смогут. Принять дефект могут только сообщники автора или клиенты с устаревшими данными сервера (например, устройство отозвано секунду назад — такой Add DS погасит Remove-ом, §2.7). Заморозка сообщений никого бы не защитила, а одному участнику давала бы выключать канал.
- Каждое устройство группы, обработав `c`, отвечает: применило — `POST /mls/groups/{id}/handshakes/{seq}/ack`; не применило — жалобой с причиной из §2.9.1. Подключившиеся во время проверки отвечают после догона.

**Подсчёт без паузы** (§2.9.2 п. 2 и сверх бюджета): `Group.state` остаётся `GROUP_STATE_ACTIVE`, `Group.review_seq = seq(c)`, событие `MlsGroupStateChanged{state: ACTIVE, review_seq}`. Handshake принимается как обычно; устройства, применившие `c`, отвечают `ack` так же. Одновременно идёт не больше одной проверки с паузой; подсчёт по другим commit-ам — без паузы.

**Подсчёт.** `C` — различные пользователи (кроме пользователя автора `c`), устройства которых подали жалобу на `c` с любой причиной. `A` — различные пользователи (кроме автора и пользователей из `C`), устройства которых подтвердили `c` (§2.9.2): прислали `ack` или commit поверх `c`. В обоих множествах учитываются только устройства, бывшие в карте в эпохе `E`; устройства, добавленные самим `c`, не считаются.

**Решение принимается не раньше, чем через `REVIEW_WINDOW` = 30 с от начала проверки**, — ни подтверждение, ни отказ. Жалобы сообщников могут прийти через миллисекунды после публикации commit-а, раньше, чем остальные устройства успеют его обработать и ответить `ack`; решение по первым мнениям отдало бы пересоздание группы на 5 000 человек двоим. Пока идёт проверка, сообщения ходят (см. выше), поэтому ждать безопасно. По истечении окна, а затем при каждом новом мнении:

1. `|C| ≥ 2` и `|C| ≥ |A|` → **жалоба подтверждена**: заморозка и пересоздание (§2.10), автор `c` отстранён (§2.6). Ничья решается в пользу жалобы: вдвоём сообщники не перевесят двух честных. Это единственное правило, которое ведёт к отстранению.
2. `|A| ≥ 1` и п. 1 не выполнен → **жалоба отклонена**: `GROUP_STATE_ACTIVE`, отложенные предложения публикуются, каждому пожаловавшемуся устройству — возврат (§2.11.2). Решение окончательное.
3. `|C| = 1` и `|A| = 0` (жалуется один пользователь, остальные молчат):
   - группа не больше `SMALL_GROUP_LEAVES` = 50 листьев → жалоба подтверждена, но **без отстранения** автора (§2.6): одиночная жалоба не доказывает вину. В ЛС подтверждения не бывает вовсе: второй участник и есть автор; зато пересоздание группы из нескольких листьев стоит килобайты;
   - группа больше → проверка продолжается, пока не придёт мнение другого пользователя (тогда пп. 1–2), но не дольше `REVIEW_MAX` = 1 ч от начала; по истечении — жалоба подтверждена, тоже без отстранения. Ожидание ограничено часом, а пауза handshake в нём — остатком `REVIEW_BUDGET` (10 мин в час): сверх бюджета голоса считаются без паузы, и ожидающие Remove выходят.

#### 2.9.4 Сверх лимита пересозданий

Если подтверждённая жалоба потребовала бы пересоздания сверх `RECREATION_LIMIT`, а `c` подтвердил хотя бы один пользователь, кроме автора, группа **не замораживается**:
- `GROUP_STATE_ACTIVE`, `Group.recreation_deferred_until` — момент, когда окно лимита освободится;
- пожаловавшиеся устройства остаются в состоянии «ошибка ключей» (SCREENS/08 §8): спорный commit они не применили и не применят; остальные работают дальше;
- когда окно освободится, DS начинает пересоздание, если хотя бы одно пожаловавшееся устройство всё ещё в группе и так и не продвинулось дальше эпохи `E` (нет его `ack` и commit-ов после `E`). Точка согласия — базовая эпоха `c` (§2.10.1); commit-ы, принятые поверх него за это время, отбрасываются.
- **Если `c` не подтвердил никто, кроме автора** (`A` = ∅ — например, «мусорный» commit), в эпохе после `c` нет устройств, способных коммитить, а если `c` начал поколение ключа истории — и писать. Такую группу DS пересоздаёт **и сверх `RECREATION_LIMIT`**, сразу после решения (решение владельца по повторному ревью безопасности, ADR-0021: суточный простой канала не принимается; клиент — §2.10.8). Повтор требует другого аккаунта: автор отстранён на 30 сут на всём инстансе (§2.6), а свежий аккаунт не назначается, пока в сети есть другие кандидаты.

#### 2.9.5 Клиент

- Не принял чужой commit — не применяет его, подаёт жалобу с причиной из §2.9.1 (решение DS примет по голосам, §2.9.2) и показывает «ошибку ключей» (SCREENS/08 §8).
- Получил `MlsGroupStateChanged` с `review_seq` (проверка с паузой или подсчёт без паузы) и применил этот commit — отвечает `ack`.
- После отклонённой жалобы клиента возвращают в группу (§2.11.2), и он снова проверяет её состояние по §1.8 — теперь как адресат Welcome. Если дефект на месте (например, в дереве осталось устройство с опубликованным Remove), клиент в группу не входит, остаётся в «ошибке ключей» и повторяет возврат с паузами `RESYNC_BACKOFF` (1, 2, 4 … 24 ч). Новой структурной жалобы на тот же дефект он не подаёт: для адресата Welcome она личная (§2.9.1).
- **Злоупотребление.** DS записывает жалобы и `ack` с устройствами в журнал инстанса; ответ модерации — исключить участника. Оценка риска — §8.2.

#### 2.9.6 Застой

Застой — то, что жалобы могут не поймать: клиенты падают на commit-е молча, или жалоб нет по другой причине. Общее условие обоих видов застоя ниже: DS запросил commit (есть ожидающие предложения, в том числе возвраты, или ротация) и за `STALL_TIMEOUT` = 60 с (в группе звонка — `STALL_TIMEOUT_CALL` = 10 с) **не принял ни одного commit-а** группы (третье ревью безопасности, №5).

- **Отброшенный Add — не застой.** Назначенный, чей фильтр (§2.7) отбросил негодные Add, коммитит остальное, а если не осталось ничего — commit без предложений, только со своим путём: DS видит ответ на назначение. Негодный пакет — проблема входящего устройства, а не коммитера; DS заменяет такой пакет сам (§2.7). Иначе участник с «ядовитым» KeyPackage вызывал бы застой, отбросив который честный коммитер поступил правильно.
- **Застой к отстранению не ведёт** (§2.6): по молчанию нельзя отличить сломанный клиент от злонамеренного, а в звонке и малой группе назначение предсказуемо (третье ревью безопасности, №7).
- **В личной группе застоя нет** (третье ревью безопасности, №16; clean room Н1): все её устройства принадлежат одному пользователю, а порог `min(2, …)` в ней равен нулю. Телефон, который держит сессию в фоне и не коммитит, — не сбой; удаление устройства в личной группе коммитит любое другое устройство пользователя, когда появится в сети.

1. **После неподтверждённого commit-а.** Последний принятый commit `c` никто, кроме автора, не подтвердил (§2.9.2), а назначения за это время получили онлайн-устройства не менее `min(2, число других пользователей группы)` пользователей, кроме автора `c` (в ЛС — второго участника; повторное ревью безопасности, №8). DS замораживает группу и пересоздаёт её от базовой эпохи `c` (§2.10.1). Пересоздание считается в `RECREATION_LIMIT`, но выполняется и сверх него: после неподтверждённого commit-а писать и коммитить некому (§2.9.4, §2.10.8).
2. **Застой возвратов** (повторное ревью безопасности, №1). Возвраты (§2.11.2) устройств не менее `min(2, число других пользователей группы)` пользователей ждут commit-а, а назначения за это время получали устройства не больше чем одного пользователя: иначе один участник держал бы чужие возвраты сколько угодно. DS замораживает группу и пересоздаёт её **в пределах** `RECREATION_LIMIT`: писать остальные участники могут, а без отстранения молчащий иначе вызывал бы пересоздание сверх лимита раз за разом. Точка согласия — базовая эпоха самого раннего commit-а, который не подтвердил никто, кроме автора, а если таких нет — текущая эпоха (§2.10.1).

### 2.10 Пересоздание группы

Единственный способ устранить рассинхрон в 1.0 (ADR-0019 п. 5). Канал получает новую MLS-группу с новым `group_id`; история продолжается, потому что ключи истории принадлежат каналу (ADR-0015, §6).

#### 2.10.1 Когда

Поводов три, и у каждого своя причина `RecreationReason` в `Group.recreation_reason`, `RecreationPlan.reason` и `MlsGroupStateChanged`:

| Повод | `RecreationReason` | Точка согласия `E_a` |
|---|---|---|
| Жалоба подтверждена (§2.9.3) | `RECREATION_REASON_DISPUTE` | базовая эпоха спорного commit-а; commit-ы, принятые поверх него (подсчёт без паузы, §2.9.2 п. 2), отбрасываются |
| Застой после неподтверждённого commit-а (§2.9.6) | `RECREATION_REASON_DISPUTE` | базовая эпоха этого commit-а |
| Застой возвратов (§2.9.6) | `RECREATION_REASON_DISPUTE` | базовая эпоха самого раннего commit-а, не подтверждённого никем, кроме автора; если таких нет — текущая эпоха |
| Отложенное пересоздание после лимита (§2.9.4) | `RECREATION_REASON_DISPUTE` | базовая эпоха спорного commit-а |
| В личной группе не осталось устройств, кроме удаляемых (§6.5) | `RECREATION_REASON_PERSONAL_RESTORE` | последняя эпоха группы; создатель — устройство того же пользователя, восстановленное ключом восстановления, хотя в карте его не было |
| Потеря журнала DS (§2.10.10) | `RECREATION_REASON_JOURNAL_LOSS` | последняя эпоха, оставшаяся в журнале; клиенты могут быть дальше |

Других поводов нет: DS не пересоздаёт группу по своей инициативе и не чаще `RECREATION_LIMIT` (§2.10.8). Клиент отвергает `RECREATION_REASON_PERSONAL_RESTORE` для группы, у которой `kind ≠ 3` (не личная), и для личной группы чужого пользователя. Группы звонков так не пересоздаются: проверки, заморозки и лимита у них нет, при сбое DS заводит новую группу звонка (§5.1).

#### 2.10.2 Заморозка

DS в одной транзакции под блокировкой строки группы:
- ставит `Group.state = GROUP_STATE_FROZEN` и `Group.recreation_reason`;
- фиксирует последнюю согласованную эпоху `E_a` по таблице §2.10.1;
- перестаёт принимать handshake и сообщения (`GROUP_FROZEN`) и публиковать предложения;
- рассылает членам группы `MlsGroupStateChanged{group_id, channel_id, state: FROZEN, recreation_reason}`.

Клиенты показывают `Banner` «Не можем зашифровать: ждём обновления ключей канала…», поле ввода неактивно (SCREENS/08 §8). История читается — ключи истории у клиентов есть. Очередь неотправленных копится локально (§2.11.4).

#### 2.10.3 Целевой состав

DS вычисляет целевой состав `R` новой группы:

```text
R = карта(E_a)
  − устройства, для которых опубликован Remove (ожидающий в E_a или любой после E_a, включая «выполненный» спорным commit-ом)
  − устройства с отменённым входом
  − устройства, чьи пользователи потеряли доступ к каналу, и удалённые устройства
  + устройства с действующей заявкой на вход (включая добавленные спорным commit-ом)
```

**Начальный состав** (повторное ревью безопасности, №2): `R₀ = R ∩ карта(E_a)` — только устройства, которые были листьями старой группы в эпохе `E_a` и не удалены. Устройства `R − R₀` — новички, устройства после сброса ключей, Add спорного commit-а, возвращающиеся устройства (Remove пары возврата, §2.11.2, исключает старый лист, а Add пары остаётся заявкой) — в начальный commit не входят. DS публикует их заявки в новой группе сразу после её создания (§2.10.5 п. 5), и они входят обычным Add со всеми правилами §6.3.3 — разрывом `break_new_member` или `break_reset`, где он положен, — и мостом по §6.3.7. Иначе новичок при выключенной истории проходил бы через разрыв `break_recreate` всю открытую часть цепочки: ему достаточно было бы пожаловаться на свой Welcome. Цена — один commit (≈ RTT) задержки для этих устройств.

**Инвариант I11:** устройство с опубликованным Remove или отменённым входом в старой группе не входит в начальный состав новой. Изменения спорного commit-а, кроме этого правила, отбрасываются: его Remove выполняются (устройства не попадают в `R`), его Add снова становятся заявками.

При потере журнала DS не знает Remove, опубликованных после `E_a`; он вычитает из `R` всё, что знает из модулей `identity` и `community` (удалённые устройства, потерянный доступ), но эти данные могли откатиться вместе с базой. Поэтому I11 обязательно проверяют и создатель (выбрасывает из начального commit-а устройства, которые сам знает удалёнными, — DS принимает подмножество `R₀`), и каждый клиент (§2.10.6 п. 5).

#### 2.10.4 Кто создаёт новую группу

DS назначает создателя `MlsUpdateRequested{REASON_RECREATE, designated_device_id}`: устройство из `R₀`, в сети, принадлежащее пользователю, отличному от автора спорного commit-а (при застое возвратов — от пользователя, чьи устройства не коммитили); в первую очередь — подавшее жалобу; пользователи на испытательном сроке и отстранённые — в последнюю очередь (§2.6). Нет ответа за `RECREATE_DESIGNATION_TIMEOUT` = 30 с — следующий кандидат. Кандидат, у которого нет ключа `K_g0` (п. 4), назначение не выполняет и ждёт следующего. Нет кандидатов в сети — группа ждёт в заморозке, пока кто-то из них не появится.

Создатель:

1. `GET /mls/groups/{old}/recreation` → `RecreationPlan{old_group_id, channel_id, kind, last_agreed_epoch, history_key_generation, target_device_ids[], reason, next_generation}`; `target_device_ids` — начальный состав `R₀`.
2. `POST /mls/groups/{old}/recreation/key-packages` → по одному зарезервированному пакету на каждое устройство из `R₀`, кроме себя; `exhausted_device_ids` — у кого пакетов нет.
3. Проверяет каждый пакет: `CredCheck` (§1.3) и фильтр коммитера (§2.7). Негодные и отсутствующие пакеты не мешают: такие устройства станут заявками в новой группе.
4. Генерирует новый `group_id` (UUIDv7) и создаёт группу с расширениями §1.6: `group_binding{channel_id, kind, predecessor_group_id = old, predecessor_epoch = E_a, continuity_tag}`, где

   ```text
   struct {
       opaque label<V> = "bebeberloga/v1 recreation";
       opaque channel_id[16];
       opaque predecessor_group_id[16];
       uint64 predecessor_epoch;
       opaque group_id[16];
   } ContinuityInput;

   continuity_tag = HMAC-SHA256(sub(K_g0, "recreation"), ContinuityInput)    // sub — §6.3.2
   ```

   `K_g0` — ключ истории канала поколения `RecreationPlan.history_key_generation`, действовавшего в эпохе `E_a` (§6); его имеет каждый участник канала того времени, а у DS его нет. Тег доказывает, что новую группу создал участник канала, а не сервер. Для групп звонков тег пуст. Для причины `DISPUTE` `E_a` — всегда базовая эпоха спорного commit-а (§2.10.1), поэтому `K_g0` есть у всех участников того времени, включая пожаловавшихся: спорный commit мог начать новое поколение, но `g0` — поколение до него. Ключи истории хранятся бессрочно (§6.3.8).
5. Собирает **один** commit, добавляющий всех из `R₀` с годными пакетами (предложения по значению), с `RosterDelta` и Welcome.
6. `POST /mls/groups {channel_id, kind, group_id, ciphersuite, predecessor_group_id, initial_commit, welcomes[], history_key_bundle, history_key_generation}` — одним запросом, атомарно. Поколение — разрыв `break_recreate` без ссылки и без мостов: бывшие участники ключи уже имеют, остальные входят следующим Add (§6.3.10).
7. `201` → применяет свой commit. `GROUP_FROZEN` с `successor_group_id` — группу уже создал другой; свою выбрасывает. Другой отказ — выбрасывает и ждёт нового назначения.

#### 2.10.5 Ровно одна новая группа на канал

DS обрабатывает `POST /mls/groups` с `predecessor_group_id` в одной транзакции:
1. блокирует строку старой группы (`FOR UPDATE`);
2. проверяет: группа заморожена, преемника нет, запрашивающее устройство — одно из назначенных создателем этого пересоздания (§2.10.4: из `R₀`, не пользователь-автор спорного commit-а), иначе `NOT_DESIGNATED` (повторное ревью безопасности, №5: без этого автор «мусорного» commit-а сам создал бы новую группу с «мусорными» Welcome и сжёг бы лимит). Так же DS отвечает на `GET …/recreation` и `POST …/recreation/key-packages`. Исключение — `PERSONAL_RESTORE`: создатель — устройство того же пользователя, подтверждённое ключом восстановления (§6.5); в карте его нет, и `R₀` для него не проверяется. Если преемник уже есть — `GROUP_FROZEN{successor_group_id}`;
3. проверяет начальный commit: `PrivateMessage` эпохи 0 новой группы, присланный запрашивающим устройством (что отправитель — лист 0 с credential этого устройства, DS проверить не может — это проверяют входящие по Welcome, §1.8, §2.10.6); `RosterDelta.removed` пуст; добавленные устройства ⊆ `R₀` (устройство не из карты `E_a` — `BAD_DELTA`); поколение связки ≥ `RecreationPlan.next_generation` — создатель вправе взять больше (§6.3.10), иначе `BAD_DELTA`; адресаты Welcome — ровно добавленные устройства по пакетам, зарезервированным в п. 2 §2.10.4 (`BAD_WELCOME`); лимит листьев;
4. создаёт новую группу в эпохе 1 с картой состава, ставит старой `GROUP_STATE_SUPERSEDED` и `successor_group_id`, переключает `Channel.mls_group_id`;
5. удаляет заявки и недоставленные Welcome старой группы; устройства из `R`, не вошедшие в начальный commit (все `R − R₀` и устройства `R₀` без годного пакета), становятся заявками на вход в новую группу и публикуются сразу (§2.7).

После фиксации DS рассылает `MlsGroupStateChanged{group_id = old, state: SUPERSEDED, successor_group_id}` членам старой группы, `MlsWelcome` адресатам и `ChannelUpdated` видящим канал. Два одновременных создателя не создают двух групп: второй получает `GROUP_FROZEN` с преемником.

#### 2.10.6 Как клиент проверяет законность новой группы

Перед тем как войти по Welcome в группу с непустым `predecessor_group_id`, клиент проверяет всё из §1.8 и дополнительно:

1. **Привязка к каналу.** `group_binding.channel_id` = канал, `kind` = роль группы; `predecessor_group_id` = группа, которую клиент знает для этого канала (если знает); DS показывает её `SUPERSEDED` с `successor_group_id` = эта группа.
2. **Точка согласия** — по причине пересоздания (`MlsGroupStateChanged.recreation_reason`, `Group.recreation_reason` старой группы):
   - `DISPUTE`: эпоха клиента в старой группе может быть больше `predecessor_epoch` + 1, если поверх спорного commit-а успели принять commit-ы (подсчёт без паузы, §2.9.2 п. 2; отложенное пересоздание, §2.9.4): они отбрасываются вместе со спорным. Откат допустим по той же причине, что при `JOURNAL_LOSS`: все удаления, о которых знает клиент, остаются в силе (п. 5), а головное поколение новой группы больше известного клиенту (п. 4).
   - `JOURNAL_LOSS`: эпоха клиента может быть больше `predecessor_epoch` — откат эпох здесь допустим, сервер честно сообщает, что потерял хвост журнала. Цена отката — п. 5: все удаления, о которых знает клиент, остаются в силе.
3. **Тег непрерывности.** Если у клиента есть `K_g0`, `continuity_tag` проверяется; если тег пуст у группы чата или не сходится — отказ. Новое устройство без `K_g0` полагается на остальных.
4. **Состав.** `CredCheck` каждого листа; хэш состава = хэш DS для эпохи 1 новой группы. Головное поколение новой группы больше головного поколения, известного клиенту в этом канале (§6.3.10).
5. **Удалённые не вернулись** (I11 на клиенте). Ни один лист не принадлежит устройству, которое клиент знает удалённым из этой группы: для него клиент видел опубликованный сервером Remove (ожидающий или включённый в commit), его лист удалил commit, который клиент применил, и устройство после этого не добавлялось, или оно удалено по `GET /users/{id}/devices`. Клиент хранит эти сведения по каналу дольше жизни группы — именно на них держится защита от того, что сервер вернёт удалённое устройство под видом «потери журнала».
6. **Новых лиц нет** (повторное ревью безопасности, №2). Каждый лист новой группы — устройство, которое клиент сам видел листом старой группы и не знает удалённым (п. 5); клиент, отставший от `predecessor_epoch`, сначала догоняет старую группу до неё по журналу handshake. Лист, которого клиент в старой группе не видел, — отказ: новые устройства входят в новую группу только обычным Add — с политикой §1.7, разрывами §6.3.3 и уведомлениями SCREENS/07 §8. Пересоздание не может добавить устройство ни тихо, ни мимо правил истории.
7. **Лимит частоты** — §2.10.8.

Отказ по пп. 1–6 — жалоба `DISPUTE_REASON_RECREATION_INVALID` на новую группу; клиент в неё не входит и остаётся в состоянии «ошибка ключей». После входа клиент удаляет состояние старой группы, ключи истории сохраняет.

#### 2.10.7 Старая группа

- `GROUP_STATE_SUPERSEDED`: DS отвергает в неё handshake и сообщения (`GROUP_FROZEN` с `successor_group_id`) и больше не публикует в ней предложений.
- Предложения сервера из старой группы в новой недействительны: подпись external sender покрывает `group_id` и эпоху (RFC 9420 §6.1), DS их не переносит, клиент очищает очередь вместе со старым состоянием.
- Сообщения, уже сохранённые на сервере, остаются и читаются по ключам истории (§6.3). Сообщения, отправленные во время проверки под поколением, которое начал спорный commit, — §6.3.10.

#### 2.10.8 Лимит частоты

`RECREATION_LIMIT`: не больше одного пересоздания канала в час и трёх за скользящие 24 ч — по всем причинам вместе.

- **DS** сверх лимита группу не замораживает: она продолжает работать, а подтверждённая жалоба откладывается до освобождения окна (§2.9.4). Пересоздание из-за потери журнала сверх лимита тоже откладывается: группа, которой нужен откат, и так стоит у клиентов, ушедших дальше журнала. **Исключение** — группа, в которой писать и коммитить некому: подтверждённая жалоба на commit, который не подтвердил никто, кроме автора (§2.9.4), и застой после неподтверждённого commit-а (§2.9.6 п. 1). Её DS пересоздаёт и сверх лимита. Застой возвратов — в пределах лимита (§2.9.6 п. 2).
- **Клиент** ведёт свой журнал принятых пересозданий по каналу и не входит в новую группу сверх лимита, даже если DS её создал. Это защищает от сервера, который пересоздаёт группу раз за разом. Welcome клиент хранит и обрабатывает, когда окно освободится. **Исключение** — клиент, который сам стоит в этом канале в «ошибке ключей»: не применил последний полученный commit старой группы и подал на него жалобу или ждёт возврата. Такое пересоздание он принимает и сверх своего лимита — иначе суточный простой; все проверки §2.10.6 остаются. Работающих клиентов исключение не касается: против них лимит действует, как раньше.
- **Что видит пользователь сверх лимита.** Клиенты, не принявшие спорный commit или не вошедшие в новую группу, — `Banner` «Не можем зашифровать: ждём обновления ключей канала…» и неактивное поле ввода (SCREENS/08 §8); история читается; очередь неотправленных ждёт. Остальные участники работают как обычно.

#### 2.10.9 Цена при 5 000 листьях

Оценка по замерам S1 и S4. Размер листа с credential проекта — около 270 байт: в спайках лист занимал около 180 байт, credential проекта на ~90 байт длиннее.

| Что | Оценка | Источник |
|---|---|---|
| Начальный commit (4 999 Add по значению по ~380 байт + `RosterDelta` ~100 КБ) | ~2 МБ (меньше лимита handshake 4 МиБ) | KeyPackage 280 байт в S1 + credential |
| Welcome на одно устройство (дерево целиком) | 1–1,4 МБ (больше лимита события 256 КиБ — новички берут его через REST) | 100–180 байт на лист (S4, S1) + credential |
| Исходящий трафик DS на всех адресатов | 5–7 ГБ | 5 000 × размер Welcome |
| Сборка commit-а у создателя | ~1,3 с + ~0,8 с на проверку пакетов | 250 мс на 1 000 Add (S4), 0,16 мс на Add (S4) |
| Обработка Welcome у адресата | ~0,13 с на десктопе, до ~1,5 с на телефоне | ~25 мкс на лист (S4) |
| Расход KeyPackage | по одному на устройство | — |

Отсюда лимит частоты и правило «пересоздание только по подтверждённой жалобе» (§2.9.3); одиночная жалоба при живых участниках стоит возврата одного устройства — один commit и один Welcome. Отдельная раздача дерева уменьшила бы Welcome (ADR-0016 «Альтернативы»), но не общий объём: дерево нужно каждому.

#### 2.10.10 Потеря журнала DS

Если базу DS восстановили из резервной копии, хвост журнала групп потерян: клиенты могут стоять на эпохах, которых DS не знает.

- Оператор после восстановления запускает команду DS «журнал восстановлен из копии» (B16). Она открывает **окно восстановления** длиной `HORIZON`.
- В окне заявление члена группы, что его эпоха больше текущей эпохи DS, — commit с такой эпохой в заголовке или `POST …/resync` с `local_epoch` — учитывается как сигнал. Группа замораживается с причиной `JOURNAL_LOSS` и `E_a` = последней эпохой журнала, только когда такие заявления пришли от устройств **не менее двух разных пользователей** (ревью безопасности Б-С5): заявление не подписано, и один участник иначе вызывал бы пересоздания всех своих групп каждый день в течение окна. Поле `MessageMeta.epoch` сигналом не считается вовсе — его пишет сам клиент (§6.2.8). В группе из одного пользователя (личная группа) достаточно заявлений двух его устройств. Дальше — §2.10.3–§2.10.7: клиенты допускают откат эпох, но проверяют I11 по своим записям (§2.10.6 пп. 2 и 5).
- Вне окна такой запрос — личная проблема клиента: его возвращают в группу (§2.11.2). Поэтому одиночный клиент, соврав о своей эпохе, пересоздания не вызовет.
- Сообщения, сохранённые сервером в потерянном хвосте, потеряны вместе с ним; у клиентов остаются локальные копии.

### 2.11 Горизонт офлайна и возврат устройства

#### 2.11.1 Горизонт и срок KeyPackage

Получатель commit-а с Add проверяет срок пакета по своим часам в момент обработки (§1.5). DS гарантирует, что у каждого пакета в принятом commit-е остаток ≥ `KP_MIN_REMAINING` (§2.4, §2.7). Значит, устройство, обработавшее поток группы не позже чем через `KP_MIN_REMAINING` после commit-а, этот commit примет. Commit-ы, которые устройство пропустило, сделаны не раньше его последнего подключения. Отсюда:

```text
HORIZON = KP_MIN_REMAINING − 1 сут (запас на расхождение часов) = 30 сут
```

Устройство, отсутствовавшее меньше `HORIZON`, догоняет поток как обычно: DS хранит handshake и карту состава `HANDSHAKE_RETENTION` ≥ 31 сут.

#### 2.11.2 Кто применяет критерий

- **DS (основной).** При `Identify` новой сессии: если `now − Device.last_seen_at ≥ HORIZON` (`last_seen_at` — последняя аутентифицированная активность устройства), устройство «возвращается». `Ready.device_returning = true`; во всех группах устройства `MlsPending.returning = true`. DS публикует в каждой группе пару: Remove старого листа и Add со свежим пакетом (`ProposalAAD.device_id` одинаковый). Если у устройства пока нет свежих пакетов (DS удалил устаревшие), пара публикуется сразу после загрузки.
- Пара возврата не публикуется устройству, для которого опубликован Remove (`REMOVAL_PENDING`, ревью Б-Н1).
- **Клиент (запасной).** Если клиент не может обработать поток группы из-за нехватки состояния — `GET …/handshakes?after_seq=` вернул первый `seq` больше ожидаемого (журнал обрезан), срок пакета в commit-е старше `HORIZON` истёк, локальная база потеряна или восстановлена из копии, — он не пытается дальше и шлёт `POST /mls/groups/{id}/resync {local_epoch}` (`RESYNC_RATE`; `local_epoch` — последняя эпоха группы у клиента, нужна для §2.10.10). DS публикует ту же пару для этой группы. Если повторный вход снова не проходит проверки клиента (§1.8), клиент повторяет возврат с паузами `RESYNC_BACKOFF` (§2.9.5).

Для неудачи на commit-е моложе `HORIZON` при полном состоянии клиента — жалоба, а не возврат (§2.9).

#### 2.11.3 Что делает возвращающееся устройство

1. Получив `device_returning`, клиент **не обрабатывает** старые handshake групп с `returning`. Их MLS-состояние он стирает; ключи истории и локальную историю сохраняет.
2. Сразу загружает свежие пакеты (§1.4).
3. Показывает в этих каналах «Подключаемся к каналу…» (SCREENS/08 §1, §8; FLOWS/02 «Возвращение после долгого перерыва»).
4. Входит по Welcome с проверками §1.8 и догружает пропущенную историю: ключи поколений, начатых за время отсутствия, — по связке и мосту коммитера (§6.3.6–§6.3.7).

Пара Remove + Add — одна операция DS «возврат»: Remove не заменяет заявку устройства на вход (в отличие от обычного Remove, S4), коммитер включает обе части в один commit (§1.7, §2.4), блокировка повторного входа до подтверждения Remove (§2.8) к ней не применяется. Коммитер — предпочтительно другое устройство того же пользователя (§2.6).

#### 2.11.4 Очередь неотправленных

Сообщения из очереди (FLOWS/06 ш. 4, FLOWS/02 «Возвращение» ш. 3) **шифруются в момент отправки, а не при постановке в очередь.** `id` (UUIDv7) присваивается при наборе, как в FLOWS/06 ш. 1; если сообщение пролежало в очереди дольше 30 сут, при отправке клиент присваивает ему новый `id` — сервер не принимает `id` старше 30 сут от времени приёма (§6.2.8); до отправки текст лежит в локальной зашифрованной базе (§7). Причины:
- к моменту отправки эпоха, ключ истории и даже группа канала могут смениться (возврат, пересоздание, ротация);
- шифртекст, собранный заранее, всё равно пришлось бы перешифровывать;
- открытый текст в очереди защищён так же, как вся локальная история.

Повтор после `HISTORY_GENERATION_MISMATCH` (FLOWS/06 ш. 4) тоже шифрует заново — под текущим поколением ключа истории; смена эпохи без смены поколения повтора не требует (§6.2.8).

### 2.12 Ключ external sender инстанса

- **Закрепление.** Клиент получает ключ из `GET /instance` (`InstanceInfo.external_sender_key`) при первом входе на инстанс и закрепляет его вместе с адресом инстанса. Дальше он принимает только этот ключ или ключ, связанный с ним цепочкой замен.
- **Замена.** Новый ключ публикуется с записью `ExternalSenderKeyRotation{old_key, new_key, signature}`, где `signature = AppSign(old_sk, "external sender rotation", {old_key, new_key})`. `InstanceInfo.external_sender_rotations[]` — цепочка от первого ключа инстанса. Клиент проверяет цепочку от закреплённого ключа и закрепляет новый.
- **Перевод групп.** Клиент отвергает GroupContextExtensions от сервера (§1.7), поэтому группу переводит участник: DS шлёт назначенному устройству `MlsUpdateRequested{REASON_EXTERNAL_SENDER_ROTATION}`, оно делает commit с GroupContextExtensions по значению, где `external_senders = [новый ключ]`, а остальные расширения побайтно прежние, и ставит бит 0 в `RosterDelta.flags`. Получатели принимают такое предложение, только если бит стоит, меняется только `external_senders` и новый ключ связан цепочкой с закреплённым. DS по биту знает, что группа переведена, и дальше подписывает её предложения новым ключом.
- Пока группа не переведена, DS подписывает её предложения старым ключом; неактивные группы переводятся при первой активности. Старый закрытый ключ DS хранит, пока есть непереведённые группы.
- Загрузчик ключа DS отвергает известный тестовый ключ спайка S4 (ADR-0018). Хранение ключа и команда замены — B05 и B16.
- Компрометация ключа инстанса позволяет подписать замену; защита от этого — вне 1.0 (Key Transparency, ARCHITECTURE §4.10).

## 3. Идентичность и устройства

### 3.1 Ключ идентичности

- Ed25519. Seed — 32 байта из генератора случайных чисел ОС; создаётся на первом устройстве при регистрации (FLOWS/01 ш. 5).
- Открытая часть — `User.identity_pubkey`; публикуется `PUT /users/me/identity-key` вместе с блобом восстановления (§3.5).
- Seed хранится на **каждом подтверждённом устройстве** пользователя: любое из них подтверждает новое (FLOWS/02 ш. 4). Первое устройство создаёт seed, новое получает его при подтверждении (§3.4.3) или из блоба восстановления (§3.5). Хранение — локальная база (§7.4), в памяти — с обнулением.
- Применение — только подпись `device binding` (§1.3). В MLS ключ идентичности не участвует, в сеть открытым не уходит.
- Меняется только при «Начать заново» (§3.6).

### 3.2 Ключи собеседников: доверие при первой встрече

- Клиент закрепляет ключ идентичности каждого пользователя при первой встрече (профиль, список участников, лист группы) из `User.identity_pubkey`, со статусом «не проверен».
- Проверка кода безопасности или QR (§4.1, §4.2) ставит статус «проверен». Статус привязан к значению ключа: хранится тройка `(user_id, identity_key, verified_at)`. Синхронизация статуса между своими устройствами — через личную группу (§6.5; OPEN-QUESTIONS №7).
- Если сервер показывает другой ключ (`UserUpdated` с новым `identity_pubkey` или другое значение при запросе), клиент заменяет закреплённый ключ, сбрасывает статус и показывает предупреждение SCREENS/07 §8: системную заметку, а для проверенного собеседника — `Banner` Брусникой и значок Брусникой. Отправка не блокируется (ADR-0013 п. 3).
- `CredCheck` (§1.3) всегда сверяет подпись с текущим закреплённым ключом.

**Свой ключ на сервере** (ревью безопасности Б-С2). Каждое подтверждённое устройство пользователя сверяет свой ключ идентичности на сервере с открытым ключом из своего seed — после `Ready`, при `UserUpdated` о себе и раз в сутки в сети — и историю своих ключей (`GET /users/{свой id}/identity-keys`) со своей записью. Расхождение — тревога, если ему не предшествовал сброс, замеченный самим устройством (свой запрос сброса или `IdentityResetRequested`, на который оно не ответило отменой), **или если устройство после расхождения живо дольше `RESET_ALARM_GRACE` = 10 мин** (повторное ревью безопасности, №10): настоящий сброс удаляет все прежние устройства пользователя (§6.3.9 п. 4), и устройство, которое сервер оставил в сети при чужом ключе, — признак подмены, даже если запрос сброса был. Тревога: `Banner` «Ключ твоего аккаунта на сервере не совпадает с ключом этого устройства» (SCREENS/07 §8). Устройство ключами при этом ничего не делает, но собеседникам такую подмену видно по заметке «Ключи изменились» и коду безопасности. Подмену, о которой не знает ни одно устройство пользователя, так видит хотя бы он сам.
- Ограничение — доверие при первой встрече (§8.2 п. 3).

### 3.3 Ключ подписи устройства и его подпись

- При входе устройство создаёт ключ подписи (§1.2) и ключ HPKE истории (§6.3.6) и публикует `PUT /devices/me/keys {signature_pubkey, history_hpke_key, history_hpke_key_signature}`. Первое устройство и устройство, восстановленное ключом восстановления, сразу добавляют `identity_signature` (§1.3), потому что знают seed.
- Сервер проверяет `identity_signature` действующим ключом идентичности пользователя в `PUT /devices/me/keys` и `POST /devices/{id}/verify` (`SIGNATURE_INVALID`).
- После подтверждения устройство загружает KeyPackage (§1.4).

### 3.4 Подтверждение нового устройства

Участники: новое устройство N и старое подтверждённое O. Транспорт — `POST /devices/{id}/verification/messages {request_id, payload}` → событие `DeviceVerificationMessage{request_id, from_device_id, payload}`; сервер содержимое не разбирает, запрос живёт 10 минут (FLOWS/02). `payload`:

```text
enum {
    qr_response(1), pictures_commit(2), pictures_key(3), pictures_reveal(4), pictures_match(5), handover(6), stop(7), (255)
} VerificationMessageType;

struct {
    uint8                   version = 1;
    opaque                  request_id[16];
    VerificationMessageType type;
    select (VerificationMessage.type) {
        case qr_response: QrResponse;
        case pictures_commit: PicturesCommit;
        case pictures_key:    PicturesKey;
        case pictures_reveal: PicturesReveal;
        case pictures_match:  PicturesMatch;
        case handover:        Handover;
        case stop:            struct {};
    };
} VerificationMessage;
```

Оба устройства знают от сервера `user_id`, `device_id` и `signature_pubkey` друг друга (`DeviceAdded`, `GET /users/me/devices`). Эфемерные ключи X25519 `e_N`, `e_O` создаются заново для каждого запроса и стираются после него. Одна попытка сравнения на запрос: после «Нет» или ошибки нужен новый запрос (`POST /devices/me/verification/request`, частоту ограничивает сервер).

#### 3.4.1 QR

1. N показывает QR (SCREENS/07 §4), в байтовом режиме:

   ```text
   struct {
       uint8  version = 1;
       uint8  kind = 1;                // 1 — подтверждение устройства; 2 — проверка собеседника (§4.2)
       opaque user_id[16];
       opaque device_id[16];           // N
       opaque request_id[16];
       opaque signature_key[32];       // ключ подписи N
       opaque ephemeral_key[32];       // e_N
       opaque secret[16];              // s — случайный
   } DeviceQr;                         // 130 байт
   ```

2. O сканирует и проверяет: `user_id` — свой; `device_id` и `signature_key` совпадают с записью N у сервера; запрос действует. Иначе — остановка.
3. O создаёт `e_O` и вычисляет:

   ```text
   TH  = SHA-256(TLS{ label "bebeberloga/v1 verify qr transcript", DeviceQr, O.device_id[16], O.signature_key[32], e_O.public[32] })
   PRK = HKDF-Extract(salt = s, IKM = X25519(e_O, e_N.public))
   K   = HKDF-Expand(PRK, TLS{ label "bebeberloga/v1 verify qr key", TH }, 32)
   ```

4. O отправляет `QrResponse{o_device_id[16], o_signature_key[32], ephemeral_key[32], handover: Handover}` (§3.4.3) и вызывает `POST /devices/{N}/verify {identity_signature}`.
5. N вычисляет тот же `K` и принимает передачу (§3.4.3). Действие пользователя на O — само сканирование.

Сервер посредником стать не может: `s` и `e_N.public` передаются только через камеру.

#### 3.4.2 Шесть картинок

Это сравнение короткой строки аутентификации (short authenticated string, SAS) с обязательством: стороны сначала связывают себя обязательством на свои эфемерные ключи, затем раскрывают их, и пользователь сравнивает короткую строку, выведенную из общего секрета и транскрипта. Приём взят из открытых источников: S. Vaudenay, «Secure Communications over Insecure Channels Based on Short Authenticated Strings», CRYPTO 2005; ZRTP, RFC 6189 (обязательство хэшем до обмена ключами). Форматы, метки и порядок сообщений — собственные.

O инициирует сравнение (пользователь выбрал «Сравнить картинки»), поэтому O и связывает себя обязательством первым:

1. O → N: `PicturesCommit{o_device_id[16], o_signature_key[32], commit_hash[32]}`, где `commit_hash = SHA-256(TLS{label "bebeberloga/v1 verify pictures commit", e_O.public, nonce_O[16]})`.
2. N → O: `PicturesKey{ephemeral_key = e_N.public, nonce = nonce_N[16]}`. Картинок N пока не показывает («Ждём ответа…»).
3. O → N: `PicturesReveal{ephemeral_key = e_O.public, nonce = nonce_O}`. N сверяет `commit_hash`; несовпадение — `stop`.
4. Оба вычисляют:

   ```text
   TH     = SHA-256(TLS{ label "bebeberloga/v1 verify pictures transcript", request_id, user_id,
                         N.device_id, N.signature_key, O.device_id, O.signature_key,
                         commit_hash, e_N.public, nonce_N, e_O.public, nonce_O })
   PRK    = HKDF-Extract(salt = TH, IKM = X25519(e_O, e_N))
   digest = HKDF-Expand(PRK, "bebeberloga/v1 verify pictures", 5)   // первые 36 бит, старшие биты первыми
   picture_i = биты [6i, 6i+6) из digest, i = 0..5                  // индексы 0..63 в наборе §3.4.4
   ```

5. Оба показывают 6 картинок и спрашивают «Картинки совпадают?» (SCREENS/07 §4, ответ владельца OPEN-QUESTIONS №11). Устройство подтверждается, только когда «Да» нажато на **обоих**:
   - N: «Да» → `PicturesMatch{mac = HMAC-SHA256(HKDF-Expand(PRK, "bebeberloga/v1 verify pictures match", 32), TH)}`, затем «Ждём второе устройство…»;
   - O: после своего «Да» и проверки `PicturesMatch` от N → `handover` (§3.4.3) с ключом `K = HKDF-Expand(PRK, "bebeberloga/v1 verify pictures handover", 32)` и `POST /devices/{N}/verify`;
   - «Нет» на любом устройстве → `stop` на другое, ничего не передаётся; оба показывают «Картинки не совпали…».

   N принимает `handover`, только если на нём самом уже нажато «Да». `PicturesMatch` нужен не для защиты от посредника — посредник знает оба `PRK` и подделает его, — а чтобы O не подтвердил устройство, пока пользователь не сравнил картинки на N, и чтобы подтверждение было привязано к этому запросу.

Обязательство не даёт посреднику подобрать ключи: он выбирает свой ключ для O раньше, чем узнаёт ключ N, а свой ключ для N — раньше, чем видит раскрытие O. Совпадение 36 бит у посредника — 2⁻³⁶ за попытку, а попытка одна на запрос. `TH` включает ключи подписи обоих устройств: подмена любого даёт разные картинки.

#### 3.4.3 Передача ключа идентичности

```text
struct {
    opaque identity_seed[32];
    opaque identity_signature[64];   // подпись ключа N (§1.3) — та же, что O отправил в POST /devices/{N}/verify
} HandoverPlain;

struct {
    opaque nonce[24];
    opaque ciphertext<V>;            // XChaCha20-Poly1305(K, nonce, HandoverPlain, aad = TH)
} Handover;
```

N расшифровывает, выводит открытый ключ из seed и принимает передачу, только если он равен `User.identity_pubkey`, а `identity_signature` проверяется этим ключом для собственного `signature_key` N. Затем N сохраняет seed, ждёт `DeviceVerified` и загружает KeyPackage (§1.4). Иначе — `stop` и сообщение об ошибке подтверждения.

**Посредник.** Сервер, полностью вставший посредником в сравнение картинок, не получит ни подписи O, ни seed: картинки у O и N будут разными, и «Да» на обоих не нажмут. Подтверждение на обоих устройствах (OPEN-QUESTIONS №11) закрывает и обратную подделку — ложную передачу для N.

**Ограничение QR** (§8.2 п. 6): если QR сфотографирован, а сервер злонамерен, он может подсунуть N ложную передачу с поддельной идентичностью — на пути QR пользователь на N ничего не подтверждает. Seed O при этом не утекает: он зашифрован на `e_N`.

#### 3.4.4 Набор картинок

Размер набора выводится из нужной стойкости. Посредник, благодаря обязательству, получает одну попытку на запрос, и её успех — `N⁻⁶` при 6 картинках из набора в `N` штук; новые запросы ограничены по частоте (§3.4). Чтобы вероятность успеха одной попытки была не больше 2⁻³⁰, нужно `N ≥ 32`; с запасом взят `N = 64` — 6 бит на картинку, 36 бит на сравнение, 2⁻³⁶ за попытку.

Индексы 0–63; набор и порядок фиксированы версией сообщения (`version = 1`) и одинаковы на всех платформах, замена набора — новая версия. Сам набор — 64 различных изображения — рисует B08 (собственные или под свободной лицензией, ADR-0013 п. 8).

### 3.5 Ключ восстановления

#### 3.5.1 Формат

- 32 символа алфавита Crockford Base32 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (без I, L, O, U); на экране — 8 групп по 4 (SCREENS/07 §5).
- Первые 30 символов — секрет: 150 бит из генератора случайных чисел ОС. Последние 2 — контрольная сумма: первые 10 бит `SHA-256("bebeberloga/v1 recovery checksum" ‖ ASCII 30 символов секрета)`.
- Ввод: убрать пробелы, дефисы и переводы строк; к верхнему регистру; `I`, `L` → `1`, `O` → `0`; `U` — ошибка. Должно получиться ровно 32 символа с верной суммой; иначе «Ключ не подошёл. Проверь, нет ли лишних пробелов» без запроса к серверу.

#### 3.5.2 Ключ шифрования

```text
master     = Argon2id(password = ASCII 30 символов секрета, salt = 16 случайных байт, t = 3, m = 65 536 КиБ, p = 4, 32)
K_r        = HKDF-Expand(master, "bebeberloga/v1 identity backup key", 32)                    // ключ блоба (§3.5.3)
(rsk, RPK) = DeriveKeyPair(HKDF-Expand(master, "bebeberloga/v1 recovery hpke", 32))            // копия личной группы (§6.5)
```

Параметры — второй рекомендуемый вариант RFC 9106 §4. При 150 битах энтропии перебор невозможен и без Argon2id; он — запас на случай частичной утечки ключа (например, фотографии части листа). `master` — равномерный выход Argon2id, поэтому HKDF-Expand применяется к нему напрямую.

#### 3.5.3 Блоб на сервере

```text
struct {
    uint8  version = 1;
    uint32 argon2_t;
    uint32 argon2_m_kib;
    uint8  argon2_p;
    opaque salt[16];
    opaque nonce[24];
    opaque ciphertext<V>;            // XChaCha20-Poly1305(K_r, nonce, identity_seed[32], aad = RecoveryAAD)
} RecoveryBlob;                      // = encrypted_identity_key в REST

struct {
    opaque label<V> = "bebeberloga/v1 identity backup";
    opaque user_id[16];
    opaque identity_key[32];
    uint8  version;
    uint32 argon2_t;
    uint32 argon2_m_kib;
    uint8  argon2_p;
    opaque salt[16];
} RecoveryAAD;
```

- Клиент принимает параметры только в пределах `t ∈ [3, 10]`, `m ∈ [64 МиБ, 1 ГиБ]`, `p ∈ [1, 8]` и проверяет их до запуска Argon2id: сервер не может заставить клиент потратить гигабайты памяти.
- Восстановление (FLOWS/02 ш. 5): `GET /users/me/recovery-key/identity` (частоту ограничивает сервер) → Argon2id → расшифровка → открытый ключ из seed = `User.identity_pubkey` → подпись своего устройства → `POST /devices/{своё}/verify` → KeyPackage → Add. Любая ошибка после верной контрольной суммы — то же «Ключ не подошёл». Сервер о ключе ничего не узнаёт.

#### 3.5.4 Новый ключ восстановления

«Создать новый ключ» (SCREENS/07 §6): новый ключ, новая соль, новый блоб — `PUT /users/me/recovery-key`. Устройство, создавшее ключ, пишет в личный канал запись `PersonalSyncBody.recovery_key{device_id, created_at}` (§6.5); остальные свои устройства по ней показывают в «Устройствах», на каком устройстве и когда создан действующий ключ (SCREENS/07 §6, ревью Б-Н9). Отдельного уведомления нет. Ключ идентичности при этом не меняется: если старый ключ восстановления утёк и у того, кто его знает, есть старый блоб, seed скомпрометирован. Полная замена — только «Начать заново» (§8.2 п. 5).

### 3.6 «Начать заново»

Сброс ключа идентичности — отложенный, с возможностью отмены и без истории до сброса (ответы владельца №14, №15; FLOWS/02 ш. 6; SCREENS/07 §4, §5, §8). Протокол запроса, задержки и отмены и правило коммитера — §6.3.9. Коротко:
1. запрос `POST /users/me/identity-reset`; письмо на email аккаунта — всегда; при подтверждённом устройстве, бывшем в сети за 30 дней, — ожидание 24 ч с предупреждением на этих устройствах; отмена с любого из них или с самого запросившего устройства;
2. новое устройство создаёт ключ идентичности, подписывает свой ключ подписи, создаёт новый ключ восстановления (обязательный экран с проверкой) и применяет сброс `PUT /users/me/identity-key {reset_request_id, …}`; старый блоб восстановления и его копии личной группы перестают действовать;
3. сервер удаляет прочие устройства (Remove во всех группах, код 4109), их KeyPackage, записывает прежний ключ идентичности в историю ключей и рассылает `UserUpdated`; у собеседников закреплённый ключ меняется (§3.2);
4. новое устройство входит во все группы пользователя, но история до сброса ему недоступна нигде: коммитеры по смене ключа идентичности начинают разрыв `break_reset` и не отдают ему ключей до него (§6.3.9); старые сообщения пользователя у остальных проверяются по истории ключей (§6.2.6).

### 3.7 Удаление устройства

`DELETE /devices/{id}` → Remove во всех группах (§2.8); удалённое устройство при следующем подключении стирает базу и ключ в хранилище ОС (§7.4, FLOWS/02). Seed ключа идентичности удалённое устройство знало, и удаление его не меняет — §8.2 п. 4.

**Устройство, удалённое сбросом ключей** (ревью безопасности Б-С6; FLOWS/02 «Выход на устройстве» ш. 3; SCREENS/07 §8). Сервер сообщает ему причину: `SessionInvalid{REASON_DEVICE_REMOVED_BY_RESET, identity_reset}` (код закрытия 4109) и `DeviceRemoved{by_identity_reset}` другим своим устройствам. Такое устройство ничего не стирает молча, а спрашивает «Это был ты?»:
- «Да» — стирает базу и ключ в хранилище ОС, как при обычном удалении;
- «Нет» — сохраняет локальную базу и работает **только на чтение**: история, ключи истории и seed прежнего ключа идентичности остаются у него; писать оно не может — из групп его удалили — и предлагает сменить пароль.

Так сброс по одному паролю не уничтожает историю жертвы на её устройствах. Вернуть прежний ключ идентичности с такого устройства (оно хранит seed) — идея на после 1.0 (§8.2 п. 18).

### 3.8 Отпечаток ключа устройства

Кнопка «Отпечаток ключа» в «Устройствах» (SCREENS/07 §6) показывает отпечаток ключа подписи устройства: по нему пользователь сверяет, что сервер не подменил ключ этого устройства в списках других своих устройств и у собеседников.

```text
struct {
    opaque label<V> = "bebeberloga/v1 device fingerprint";
    opaque user_id[16];
    opaque device_id[16];
    opaque signature_key[32];
} DeviceFingerprintInput;

okm     = HKDF-Expand(HKDF-Extract(salt = "", IKM = DeviceFingerprintInput), "bebeberloga/v1 device fingerprint digits", 40)
group_i = uint40(okm[5i .. 5i+5], big-endian) mod 100 000, i = 0..7   // 8 групп по 5 цифр
```

Отпечаток считается по открытым данным одинаково на любом устройстве; где он показывается кроме «Это устройство» — решает SCREENS/07 §6. 40 цифр — около 133 бит: подобрать другой ключ с тем же отпечатком невозможно.

## 4. Код безопасности и код звонка

### 4.1 Код безопасности

```text
struct {
    opaque label<V> = "bebeberloga/v1 safety number";
    opaque user_id_1[16];
    opaque identity_key_1[32];
    opaque user_id_2[16];
    opaque identity_key_2[32];
} SafetyNumberInput;                 // пары упорядочены по user_id побайтно, меньший — первым

okm     = HKDF-Expand(HKDF-Extract(salt = "", IKM = SafetyNumberInput), "bebeberloga/v1 safety number digits", 60)
group_i = uint40(okm[5i .. 5i+5], big-endian) mod 100 000, i = 0..11   // пять цифр с ведущими нулями
```

- 12 групп по 5 цифр в сетке 3 × 4 (SCREENS/07 §7); одинаков у обоих собеседников.
- Меняется при смене ключа идентичности любого из двоих; от устройств не зависит — они подписаны ключом идентичности (§1.3).
- Чтобы совпасть с кодом при подменённом ключе, нужно ~2¹⁹⁹ попыток; даже первые 4 группы (≈ 66 бит) недостижимы. Смещение от взятия по модулю — меньше 10⁻⁷.
- «Коды совпадают» отмечает собеседника проверенным для текущего ключа (§3.2).

### 4.2 QR проверки собеседника

`struct { uint8 version = 1; uint8 kind = 2; opaque user_id[16]; opaque identity_key[32]; } ContactQr;` — 50 байт, свой ключ. Сканирующий сравнивает `identity_key` с закреплённым ключом этого пользователя: совпало — «проверен», нет — как «Не совпадают». Каждая сторона проверяет другую отдельно (SCREENS/07 §7: свой QR слева, камера справа).

### 4.3 Код звонка

```text
okm     = HKDF-Expand(HKDF-Extract(salt = group_id[16], IKM = epoch_authenticator),
                      TLS{ label "bebeberloga/v1 call code", uint64 epoch }, 30)
group_i = uint40(okm[5i .. 5i+5], big-endian) mod 100 000, i = 0..5
```

- `epoch_authenticator` — RFC 9420 §8.7, 32 байта для 0x0001; секрет эпохи, предназначенный как раз для такой сверки. Код показывается во вкладке «Шифрование» звонка рядом с эпохой (SCREENS/05 §2) и меняется при каждом входе и выходе.
- **Что доказывает:** все, у кого код совпал, находятся в одном состоянии группы — одна эпоха, одно дерево, один состав. Если сервер показывает участникам разные группы, коды разные.
- **Что не доказывает:** отсутствие лишнего устройства. Устройство, добавленное сервером и прошедшее `CredCheck`, — в том же состоянии, код у него тот же. Его видно в списке участников вкладки «Шифрование» со статусом проверки; сверять нужно и код, и список.
- Код — одностороннее значение от секрета со своей меткой; произнести его вслух безопасно.

## 5. Медиа

### 5.1 Группа звонка и быстрый вход

`GROUP_KIND_CALL`, одна на активный звонок; профиль — §1, `group_binding.kind = 2`. Эпоха меняется при каждом входе и выходе и не реже раза в сутки (§1.9).

**Вход** (FLOWS/07 ш. 3–4). Цель — первый звук не позже 1 с после клика при RTT до сервера до 100 мс.
- По `POST /channels/{id}/voice/join` сервер сразу резервирует KeyPackage устройства и публикует Add в группу звонка — **не дожидаясь** подключения клиента к SFU. Клиент параллельно подключается к SFU и ждёт Welcome; вход длится столько, сколько дольше из двух шагов.
- Первый вошедший создаёт группу сам (`call_group_exists: false`). Если в этот момент входит второй, а группы на DS ещё нет, DS держит его Add и публикует сразу после регистрации группы.
- Webhook SFU нужен только для сверки состава и Remove: `voice/leave` — Remove сразу; обрыв с SFU без переподключения за `CALL_RECONNECT_GRACE` = 30 с — Remove (FLOWS/07 «Переподключение»); устройство вошло в группу, но не подключилось к SFU за `CALL_SFU_JOIN_TIMEOUT` = 15 с — Remove. После последнего выхода DS удаляет группу.

**DS и gateway для групп звонка:**
- Add публикуется сразу, без накопления пачки (§2.7).
- Назначенный коммитер — устройство звонка, прошедшее общие фильтры §2.6: в сети, без ожидающего Remove, не участник открытой жалобы; устройства отстранённых пользователей — последними (§2.6). Среди остальных в первую очередь **не то, что сейчас стримит** (кодирование стрима занимает его CPU и исходящий канал), затем с наименьшей задержкой до сервера по heartbeat gateway, затем дольше всех в звонке. Эти правила действуют **среди прошедших испытательный срок** (`DESIGNATION_PROBATION`, §2.6): устройство пользователя, вступившего в сообщество меньше 7 сут назад, назначается, только если других кандидатов в звонке нет. Таймаут — `COMMIT_DESIGNATION_TIMEOUT_CALL` = 1 с.
- **Не чаще одного commit-а в `CALL_COMMIT_MIN_INTERVAL` = 250 мс.** DS назначает коммитера (`MlsUpdateRequested`) не раньше, чем через 250 мс после последнего принятого commit-а группы звонка. Одиночный вход в тихий звонок идёт без задержки: интервал к этому моменту давно прошёл. При всплеске (начало события: 100–200 человек за десяток секунд) Add, опубликованные за интервал, копятся в очередях участников и уходят одним commit-ом — до `MAX_BATCH` = 100. Так эпох со входами не больше 4 в секунду: за `MEDIA_KEY_OVERLAP` (2 с) их не больше 8, кольцо из 16 ключей не переполняется (§5.3 п. 5), отставший получатель за `MEDIA_KEY_HOLD` (500 мс) видит не больше двух эпох вперёд, отправитель успевает перейти на ключ (150 мс) до следующей эпохи, а commit-ы не гоняются за эпохой.
- **Remove — вне интервала** (ревью безопасности Б-С3). Если среди ожидающих предложений группы звонка есть Remove, DS назначает коммитера сразу, не дожидаясь `CALL_COMMIT_MIN_INTERVAL`: окно, в котором удалённый ещё может расшифровать медиа, не должно расти ради плавности входов. Заявки на вход, накопившиеся к этому моменту, уходят тем же commit-ом. Commit-ы с Remove идут с темпом RTT — при массовом выходе 5–10 эпох в секунду, — но ключи эпохи до такого commit-а получатель держит только `MEDIA_KEY_HOLD` (§5.3 п. 1), поэтому кольцо не переполняется и тогда (повторное ревью безопасности, №9).
- **Частота входа.** `voice/join` — не чаще `VOICE_JOIN_RATE` = раза в 2 с на устройство (`RATE_LIMITED{retry_after_ms}`, клиент повторяет сам): иначе цикл «вход — выход» одного участника гнал бы эпохи звонка с темпом RTT.
- DS обрабатывает commit-ы групп звонка вне тика батча; gateway ставит `MlsHandshake`, `MlsWelcome` и `MlsUpdateRequested` групп звонка в начало очереди отправки соединения (`seq` присваивается при отправке, порядок `seq` сохраняется).

**Бюджет входа** при RTT 100 мс (до сервера у всех):

| Шаг | Время | Нарастающим итогом |
|---|---|---|
| `voice/join`: запрос и ответ; Add опубликован | 1 RTT ≈ 100 мс | 100 мс |
| Add доходит до назначенного коммитера | ½ RTT ≈ 50 мс | 150 мс |
| Сборка commit-а (группа звонка — единицы и десятки листьев, S1) | < 5 мс | 155 мс |
| Commit → DS → принят | 1 RTT ≈ 100 мс | 255 мс |
| Welcome новичку и commit участникам — вне очереди | ½ RTT ≈ 50 мс | 305 мс |
| Обработка Welcome и commit-а, вывод ключей | < 5 мс | ≈ 310 мс |
| Параллельно: подключение новичка к SFU (ICE, DTLS) | 2–3 RTT после ответа `voice/join` | ≈ 300–400 мс |
| Новичка слышат остальные: он шифрует ключом новой эпохи сразу | — | ≈ 400 мс + буфер джиттера |
| Новичок слышит остальных: они переходят на новый ключ через `MEDIA_KEY_SWITCH_DELAY` | 150 мс | ≈ 550 мс + буфер джиттера |
| **Вход при всплеске:** ожидание окна commit-а (`CALL_COMMIT_MIN_INTERVAL`), commit с пачкой Add и Welcome с деревом на 200 листьев (~54 КБ, обработка ~5 мс, S4) | до 250 мс + ~10 мс | ≈ 0,8 с + буфер джиттера |

Запас до 1 с — на буфер джиттера (50–150 мс, ARCHITECTURE §6.5) и запуск звукового устройства. Цель «первый звук ≤ 1 с» — **при исправном назначенном коммитере**.

**Худший случай с одним сбоем:** назначенный коммитер не ответил, следующий назначается через `COMMIT_DESIGNATION_TIMEOUT_CALL` = 1 с — первый звук около 1,6 с.

**Сбой в группе звонка: новая группа вместо проверки** (повторное ревью безопасности, №3, ADR-0021; FLOWS/07 «Сбой смены ключа»). Проверка с паузой, подсчёт голосов, заморозка и отложенное пересоздание (§2.9–§2.10) в группе звонка не применяются: пока handshake стоит, опубликованный Remove не входит в commit, а честные отправители шифруют медиа ключом, который знает удалённый. Вместо этого:
- **Жалоба** на commit `c` группы звонка (любая причина §2.9.1): если на `c` пожаловались устройства не менее двух пользователей, кроме автора, или `c` пока не подтвердил ни один другой пользователь (`ack` или commit поверх, §2.9.2), — DS сразу заводит новую группу звонка. Если `c` уже подтвердил другой пользователь, а жалуется один, — возврат пожаловавшегося устройства (§2.11.2). Жалобы одного пользователя заводят новую группу не чаще `CALL_RESTART_RATE` = 3 раз за 10 мин в звонке; сверх — только возврат его устройства.
- **Застой** (§2.9.6, `STALL_TIMEOUT_CALL` = 10 с), в том числе опубликованный Remove, не вошедший в принятый commit за `STALL_TIMEOUT_CALL`, — тоже новая группа звонка.
- **Отстранения в звонке нет** — ни по жалобам, ни при застое (третье ревью безопасности, №4): в звонке нет подсчёта голосов, и два свежих аккаунта жалобами отстраняли бы любого честного коммитера на весь инстанс. Сбой ведёт только к новой группе звонка.
- **Новая группа звонка** — процедура §2.10.3–§2.10.7 со следующими отличиями: сообщений в группе звонка нет, поэтому замораживать нечего; `E_a` — базовая эпоха `c`, а при застое Remove — текущая эпоха; создателя DS назначает среди кандидатов этого раздела с таймаутом `COMMIT_DESIGNATION_TIMEOUT_CALL` = 1 с; `continuity_tag` пуст (у звонка нет ключей истории); `RECREATION_LIMIT` не применяется ни на DS, ни на клиенте. Начальный состав — `R₀` (§2.10.3): удалённые не входят, заявки входят следующим Add. Клиенты переходят в новую группу, не выходя из звонка, — около 1 с. Индексы ключей медиа в новой группе продолжают старую — `key_index = (predecessor_epoch + 1 + E) mod KEY_RING`, — чтобы первые эпохи новой группы не занимали слоты ключей, ещё нужных для приёма.

### 5.2 Ключ отправителя

```text
struct {
    opaque device_id[16];
    uint8  track_class;              // 1 — голос и камера; 2 — стрим (экран, окно, приложение и его звук)
    opaque encryptor_id[8];          // случайный идентификатор экземпляра шифратора
} MediaKeyContext;

media_key(device, class, encryptor_id, E) = MLS-Exporter("bebeberloga/v1 media", MediaKeyContext, 32)   // в эпохе E группы звонка
```

- **Ключ — на экземпляр шифратора** (ревью безопасности Б-С4, решение владельца, ADR-0021). Каждый запуск шифратора — в renderer, в media-engine, после перезапуска, перехода между нативным и Chromium-путём, переподключения к SFU — берёт новый случайный `encryptor_id` (8 байт) и шифрует свои треки ключом `media_key(своё, класс, encryptor_id, E)`. Внутри экземпляра уникальность IV обеспечивает его собственный счётчик, общий для всех его треков; между экземплярами IV не может совпасть под одним ключом, потому что ключи разные. Так совпадение IV исключено самой конструкцией, а не дисциплиной: например, в Chromium-пути видео стрима шифрует renderer, а звук приложения — media-engine, и это два разных ключа.
- `encryptor_id` открыт: отправитель публикует его в метаданных трека SFU (формат метаданных — B7, `MEDIA.md`). Получатель берёт его оттуда и выводит ключ для пары «отправитель, трек». Если сервер или SFU подставит ложный `encryptor_id`, кадры просто не расшифруются — ни утечки, ни подмены отправителя это не даёт. При смене эпохи ключи всех экземпляров выводятся заново (§5.3).
- Стрим публикует отдельный участник SFU (ARCHITECTURE §6.5) с классом 2. Процесс media-engine получает только ключи своих экземпляров шифратора класса 2 — ни exporter, ни ключей класса 1.
- Renderer (Chromium, encoded transforms) получает только готовые 32-байтные ключи по `(устройство, класс, encryptor_id, эпоха)` через фиксированную метку crypto-core; exporter наружу не выходит (ADR-0016 «Последствия»).
- Сервер задаёт идентичность участника SFU в токене (B7, `MEDIA.md`); она обязана однозначно задавать `device_id` и класс трека. Получатель выводит ключ по устройству MLS, соответствующему этой идентичности. Если сервер или SFU подменит идентичности, кадры не расшифруются: выдать себя за другого нельзя, получится только сбой.
- Участник комнаты SFU, которого нет в группе звонка, ключей не имеет и видит только шифртекст.

### 5.3 Смена ключа без разрывов

Цель (FLOWS/07): вход и выход участника не дают ни разрыва звука, ни фриза видео и стрима у остальных. Commit доходит до участников звонка почти одновременно, но не мгновенно: если отправитель перейдёт на новый ключ в момент своего merge, получатели, применившие commit на десятки миллисекунд позже, потеряют кадры — звук рвётся, видео стоит до ключевого кадра. Поэтому получатель готов к новому ключу раньше, чем отправитель начинает им пользоваться, а опоздавший получатель удерживает кадры, а не выбрасывает.

`key_index = E mod KEY_RING`, `KEY_RING` = 16 — размер кольца ключей KeyProvider (S2 подтверждает).

1. **Получатель** при merge commit-а, ведущего в эпоху `E+1`, сразу выводит ключи всех отправителей `E+1` и ставит их на индекс `(E+1) mod KEY_RING`. Ключи эпохи `E` остаются для приёма `MEDIA_KEY_OVERLAP` = 2 с, затем стираются. **Если commit удалил кого-то из звонка, ключи эпохи `E` остаются только `MEDIA_KEY_HOLD` = 500 мс** (повторное ревью безопасности, №9, №14): отправители на таком commit-е переходят на новый ключ сразу (п. 2), и дольше держать ключ, который знает удалённый, незачем — иначе удалённый ещё 2 с вставлял бы кадры, а кольцо переполнялось бы при массовом выходе.
2. **Отправитель** шифрует свои треки ключом новейшей эпохи, которую он применил не менее `MEDIA_KEY_SWITCH_DELAY` = 150 мс назад. Устройство, которое только что вошло и знает одну эпоху, шифрует ею сразу. Две смены эпохи подряд в пределах задержки отправитель проходит одним переходом. **Если commit удалил кого-то из звонка, отправитель переходит на ключ новой эпохи сразу при merge, без задержки** (ревью безопасности Б-С3): опоздавших получателей покрывает удержание кадров (п. 3).
3. **Кадр с неизвестным индексом.** Если индекс кадра впереди эпохи получателя (одна из следующих `KEY_RING / 2` эпох) и ключа для него ещё нет, получатель **удерживает** кадр — по отправителю и треку, по порядку, не дольше `MEDIA_KEY_HOLD` = 500 мс и не больше 64 кадров на трек — и расшифровывает удержанное, как только применит commit. По истечении удержания кадр отбрасывается. Кадр с индексом позади (ключ стёрт) отбрасывается сразу.
4. **Ключевой кадр.** Если видеокадры трека всё же отброшены, получатель запрашивает ключевой кадр (PLI) сразу, как только ключ для этого отправителя появился, — один запрос на смену ключа, в пределах ограничения ARCHITECTURE §6.5.
5. **Кольцо.** При `CALL_COMMIT_MIN_INTERVAL` (§5.1) эпох со входами не больше 4 в секунду, то есть не больше 8 за `MEDIA_KEY_OVERLAP`; эпохи до commit-ов с Remove держатся только `MEDIA_KEY_HOLD`, и при темпе до 10 в секунду занимают не больше 5 слотов — вместе не больше 13, кольцо из 16 ключей не переполняется. Если новая эпоха всё же занимает слот, ключу в котором меньше `MEDIA_KEY_OVERLAP` (сбой DS), старый ключ стирается досрочно; потерянное видео восстанавливает п. 4.
6. Удалённый в `E+1` отправитель новых ключей не получает; commit-ы группы звонка клиент обрабатывает в первую очередь.
7. **Пауза медиа при задержке Remove** (повторное ревью безопасности, №3; FLOWS/07 «Сбой смены ключа», SCREENS/05 §1). Если в группе звонка опубликован Remove, а commit с ним клиент не применил за `CALL_REMOVE_PAUSE` = 2 с, он приостанавливает отправку своих медиа — не шифрует ни одного кадра ключом, который знает удалённый, — и показывает «Обновляем ключи звонка…». Отправка возобновляется сразу после merge commit-а с этим Remove или входа в новую группу звонка (§5.1); приём не останавливается. Причина задержки не важна — сбой коммитера, DS или «ошибка ключей» самого клиента: окно, в котором удалённый расшифровывает медиа, ограничено на клиенте. 2 с — стартовое значение: S2 проверяет, что при одном сбое коммитера (около 1,4 с до commit-а с Remove) пауза не срабатывает.

В обычном случае все получатели применяют commit быстрее 150 мс после отправителя, и ни один кадр не теряется. Получатель, отставший до 500 мс, получает кадры с задержкой, но целиком. Теряют кадры только отставшие сильнее, и видео у них восстанавливается ключевым кадром сразу после merge. Удержание касается только зашифрованных кадров и ключей не раскрывает. Цена задержки перехода при Remove — §8.2 п. 10.

### 5.4 Формат кадра и качество: требования к S2, S6 и B12

Формат кадра и шифр — E2EE LiveKit (AES-GCM, подход SFrame, RFC 9605; ADR-0004 п. 4); ключи передаются в KeyProvider в режиме «ключ на участника». S2 обязан подтвердить:

1. ключ задаётся на участника, а не общий для комнаты;
2. ключ выбирается по треку (по `encryptor_id` из метаданных трека, §5.2), а не только по участнику; если KeyProvider LiveKit этого не умеет — шифрование кадров своим преобразованием (encoded transform в Chromium, свой шифратор в media-engine) с теми же ключами; nonce (IV) не повторяется внутри экземпляра шифратора — у аудио, видео и слоёв simulcast одного экземпляра;
3. встроенный в KeyProvider «храповик» при ошибке расшифровки выключен: ключи меняются только по эпохам;
4. размер кольца ключей;
5. KeyProvider принимает 32 байта ключевого материала (наш материал равномерно случаен — выход exporter);
6. нерасшифрованный кадр отбрасывается и никогда не воспроизводится как открытый.

7. смена ключа по §5.3 реализуема: задержка перехода отправителя, удержание кадров с неизвестным индексом, запрос ключевого кадра по появлению ключа; S2 подбирает `MEDIA_KEY_SWITCH_DELAY` и `MEDIA_KEY_HOLD` замером.

**E2EE не отключает и не ухудшает качество** (S2 — звонок и камера в Chromium, S6 — стрим на нативном пути media-engine):
- simulcast и SVC с переключением слоёв на SFU — SFU выбирает слой по открытым RTP-заголовкам и их расширениям, а не по зашифрованной полезной нагрузке;
- adaptive stream и dynacast;
- Opus in-band FEC, RED и DTX (для голоса; у звука стрима DTX выключен — ARCHITECTURE §6.5 п. 7);
- NACK и RTX, запросы ключевого кадра (PLI, FIR);
- аппаратное кодирование: шифрование идёт после кодирования и не заставляет переходить на программный энкодер;
- добавка E2EE к задержке — меньше 2 мс на кадр (ARCHITECTURE §6.5), отдельно для голоса, камеры и стрима 1080p60;
- вход и выход участника (и зрителя стрима) не дают у остальных ни разрыва звука, ни фриза видео (§5.3); время от клика до первого звука ≤ 1 с при RTT ≤ 100 мс (§5.1).

Если E2EE в LiveKit что-то из этого отключает или ухудшает — это пункт отчёта спайка с обходом. Молча снижать качество запрещено; отключать E2EE — тоже (ADR-0004 п. 6). Если обхода нет — остановка и новый ADR.

Если S2 покажет, что пп. 2, 3 или 7 не выполняются, B12 реализует шифрование кадров по RFC 9605 с теми же ключами.

### 5.5 `CallKeyBody`

В 1.0 не используется: ключи медиа выводятся только через exporter. Получатель тело `call_key` игнорирует.

### 5.6 Саундборд

Без E2EE: звуки — публичные ассеты сообщества и пользователя (ADR-0013 пп. 14, 17), команда `PlaySound` идёт через gateway, сервер знает, кто, какой звук и когда проиграл (ARCHITECTURE §8). Файлы звуков, как и аватары, не аутентифицируются. Звук саундборда не проходит через трек микрофона и его ключи.

## 6. Сообщения и ключи истории

Решения владельца Р1, Р2, Р4, Р5 и правило сброса ключей — [ADR-0020](../adr/0020-history-keys-message-format.md); он частично изменяет ADR-0015.

### 6.1 Схема

```text
отправитель                                  сервер хранит                       читатель (участник, новичок, новое устройство)
mk ← случайный 32 байта                      MessageMeta{                        K_g ← exporter (если был в эпохе начала g)
SealedMessage = AEAD(mk, конверт + подпись)    ciphertext = SealedMessage,           или связка эпохи + ссылки назад
wrapped = AEAD(wrap_key(K_g), mk)              wrapped_message_key,                  или мост от коммитера
                                               history_key_generation = g }      mk ← wrapped; конверт ← SealedMessage; подпись
```

Ключ истории канала `K_g` — симметричный ключ поколения `g`; сервер его не получает (ADR-0015). Обычное сообщение **не** идёт через MLS: его ключ лежит только под ключом истории (§6.2.7).

### 6.2 Сообщение

#### 6.2.1 Ключ сообщения

На каждое сообщение — `mk`, 32 случайных байта. Им шифруется конверт; ключи вложений лежат в конверте (`FileRef.key`).

#### 6.2.2 Контекст и подпись

```text
struct {
    opaque channel_id[16];            // канал; ЛС и групповой чат — тоже канал (MESSAGES.md)
    opaque message_id[16];            // UUIDv7 = MessageMeta.id
    opaque sender_user_id[16];
    opaque sender_device_id[16];
    uint32 history_key_generation;
} MessageContext;

signature = AppSign(sk устройства, "message", TLS{ MessageContext, opaque envelope<V> })
```

Подпись — ключом подписи устройства (§1.2), тем же, что подписан ключом идентичности. **Публичная ветка** (S) живёт в группе и в цепочке ключей истории своего канала-родителя (ARCHITECTURE §4.3): ключ поколения, подключи и связка выводятся с `channel_id` родителя (§6.3), а `MessageContext.channel_id` сообщения — это `id` самой ветки (ветка — тоже канал, MESSAGES.md). Приватная ветка — отдельная группа и отдельная цепочка со своим `channel_id`. Она привязывает конверт к каналу, `id`, отправителю и поколению: перенести сообщение в другой канал, под другой `id` или к другому автору нельзя.

#### 6.2.3 Шифртекст и паддинг

```text
struct {
    opaque envelope<V>;               // MessageEnvelope (envelope.proto)
    opaque signature[64];
    opaque padding<V>;                // нули
} SealedPlain;

struct {
    uint8  version = 1;
    opaque nonce[24];
    opaque ciphertext<V>;             // XChaCha20-Poly1305(mk, nonce, SealedPlain, aad = MessageAAD)
} SealedMessage;                      // = MessageMeta.ciphertext

MessageAAD = TLS{ label "bebeberloga/v1 message content", MessageContext }
```

**Паддинг — на внешнем шифртексте:** длина `padding` выбирается так, чтобы длина всего `SealedMessage` была кратна 256 байтам. Короткие сообщения неотличимы по размеру; накладные расходы — меньше 256 байт. Получатель отвергает ненулевой паддинг. Лимит 128 КиБ (MESSAGES.md §3) — на `SealedMessage`.

#### 6.2.4 Обёртка ключом истории

```text
struct {
    opaque nonce[24];
    opaque ciphertext<V>;             // XChaCha20-Poly1305(sub(K_g, "message key wrap"), nonce, mk, aad = WrapAAD)
} WrappedMessageKey;                  // = MessageMeta.wrapped_message_key, 73 байта

WrapAAD = TLS{ label "bebeberloga/v1 message key", MessageContext }
```

`sub` — подключ поколения (§6.3.2).

#### 6.2.5 Проверка на приёме

1. Ключ `K_g` поколения `MessageMeta.history_key_generation` есть (§6.3.8); нет — состояние «ждём ключ», через 24 ч — «Не удалось расшифровать это сообщение» (SCREENS/08 §10).
2. Снять обёртку, расшифровать `SealedMessage` (AAD из `MessageMeta`), проверить нулевой паддинг.
3. `MessageEnvelope.message_id = MessageMeta.id` (MESSAGES.md §6).
4. Подпись: устройство `MessageMeta.author_device_id` принадлежит `author_user_id`; его открытая запись (ключ подписи, `identity_signature`, `removed_at`) — у сервера навсегда (§6.2.8). Подпись `message` проверяется ключом подписи устройства; `identity_signature` устройства — ключом идентичности пользователя, **действовавшим в момент** `MessageMeta.created_at` (история ключей идентичности, §6.2.8); если устройство удалено — `created_at < removed_at`.
5. Смысловые проверки MESSAGES.md §6 (правка — только автором и т. д.).
6. Тело по месту и автору: `personal_sync` принимается только в своём личном канале и только от своего пользователя; `device_notice` — только от пользователя, названного в `DeviceNoticeBody.user_id`. Иначе сообщение отбрасывается (ревью безопасности Б-В2).

Любая ошибка в пп. 2–4 — сообщение не показывается: «Не удалось расшифровать это сообщение» (SCREENS/08 §10), запись в журнал клиента.

#### 6.2.6 Сообщение под прежним ключом идентичности

После «Начать заново» (§6.3.9) старые сообщения пользователя остаются в истории у других участников и у новичков; их устройства подписаны прежним ключом идентичности.
- Клиент принимает подпись, если прежний ключ есть в истории ключей пользователя у сервера и его период действия покрывает `created_at` сообщения (п. 4 §6.2.5). Если клиент сам закреплял этот ключ раньше (§3.2), он сверяет историю сервера со своей записью; расхождение — сообщение не показывается, как при неверной подписи.
- Показ: обычное сообщение того же пользователя — автор сообщения пользователь, а не ключ. В ленте на момент сброса стоит системная заметка «Ключи <имя> изменились» (SCREENS/08 §10): клиент ставит её по `valid_from` нового ключа, и видно, какие сообщения написаны до сброса. Статус «проверен» относится к ключу: проверка прежнего ключа не переносится на новый. Отдельной пометки у каждого сообщения нет (ответ владельца OPEN-QUESTIONS №16, SCREENS/08 §10).
- Сообщения устройства, удалённого раньше, показываются так же; отправленные после `removed_at` — отвергаются (п. 4).

#### 6.2.7 Почему без MLS-копии

ADR-0015 предполагал, что ключ сообщения идёт и в MLS-сообщении, и под ключом истории. MLS-копия не даёт ничего, что не даёт ключ истории:
- **forward secrecy и PCS** — нет: тот же `mk` лежит на сервере под `K_g`, и любой обладатель `K_g` его снимет; удалённые не получают `K_g` следующего поколения (§6.3.3) — ровно та же граница, что у эпохи;
- **авторство** — даёт подпись устройства (§6.2.2), и она работает и в истории, где MLS-подписи нет;
- **доставка без ключа истории** — не нужна: участник выводит ключ нового поколения сам при merge (§6.3.1);
- **принадлежность к группе** — проверяет сервер по карте состава и поколению (§6.2.8).

Цена MLS-копии — шифрование и обработка секретного дерева на каждое сообщение у каждого участника, хранение прошлых эпох (`max_past_epochs`) и повтор отправки при каждой смене эпохи. Поэтому обычные сообщения идут **без MLS-копии**, а `max_past_epochs = 0` (§1.5). MLS application message остаётся только для служебных конвертов вне истории; в 1.0 таких типов нет (§6.6), и DS application-сообщений MLS не принимает.

#### 6.2.8 Сервер

- `POST /channels/{id}/messages`: устройство в карте состава группы канала (`NOT_GROUP_MEMBER`); `history_key_generation` = текущее поколение канала, иначе `HISTORY_GENERATION_MISMATCH{current_generation}` — клиент догоняет commit-ы и повторяет. Смена эпохи без нового поколения (вход участника) отправку не прерывает. `epoch` в `MessageMeta` — эпоха отправителя, для диагностики.
- **Окно для `id`** (ревью безопасности Б-С7): время в UUIDv7 сообщения не раньше 30 сут (`MESSAGE_ID_WINDOW` = `HORIZON`) и не позже 5 мин относительно времени приёма; иначе `MESSAGE_ID_OUT_OF_WINDOW`. Порядок ленты задаёт `id`, и без окна участник мог бы вставить сообщение глубоко в прошлое ленты. Сообщение из очереди неотправленных, пролежавшее дольше 30 сут, при отправке получает новый `id` (FLOWS/06 ш. 1, §2.11.4).
- Сервер **навсегда** хранит открытые записи всех устройств — ключ подписи, `identity_signature`, ключ HPKE истории, время удаления — и историю ключей идентичности пользователя с периодами действия (`GET /users/{id}/devices?include_removed=true`, `GET /users/{id}/identity-keys`). Без них история перестала бы проверяться.

### 6.3 Ключи истории

#### 6.3.1 Поколение и его ключ

```text
K_g = MLS-Exporter("bebeberloga/v1 history key", TLS{ channel_id[16], uint32 g }, 32)   // в эпохе E_g
```

`E_g` — эпоха, которую открыл commit, начавший поколение `g`. Каждый участник, применивший этот commit, выводит `K_g` сам — ключ не рассылается, участники не ждут запроса. Поколение 1 начинается в эпохе 0 первой группы канала. Нумерация — по каналу, сквозная через пересоздания группы (§6.3.10); номер растёт на 1, при пересоздании может перескочить.

#### 6.3.2 Подключи

```text
sub(K_g, purpose) = HKDF-Expand(HKDF-Extract(salt = "", IKM = K_g),
                                TLS{ label "bebeberloga/v1 history subkey", opaque purpose<V>, channel_id[16], uint32 g }, 32)
purpose: "message key wrap" (§6.2.4), "link" (§6.3.4), "mention" (§6.4), "recreation" (§2.10.4)
```

Сам `K_g` ничего не шифрует.

#### 6.3.3 Когда начинается новое поколение

Автор commit-а указывает изменение в `RosterDelta.history_change` (§2.3):

| Значение | Когда | Ссылка назад |
|---|---|---|
| `none` (0) | ничего из ниже | — |
| `rotate` (1) | в commit-е есть Remove, кроме Remove пары возврата (тот же `device_id` удаляется и добавляется, §2.11: ключи у устройства и так есть; повторное ревью безопасности, №15); срок текущего поколения ≥ 30 сут | есть |
| `break_new_member` (2) | настройка «Новые участники видят историю» выключена, и commit добавляет устройство **нового пользователя** — у которого в группе нет других листьев, кроме удаляемых этим же commit-ом (в группе-преемнике, §6.3.10, учитываются и листья группы-предшественника в эпохе `predecessor_epoch`: участник старой группы, чьи устройства входят в новую следующим Add, новым не считается); возвращающееся устройство (тот же `device_id` удаляется и добавляется, §2.11) новым пользователем не делает | нет |
| `break_enable` (3) | настройку снова включили с начала текущего поколения (ответ владельца OPEN-QUESTIONS №10) | нет |
| `break_disable` (6) | настройку выключили; начальный commit группы канала, созданного с выключенной настройкой (повторное ревью безопасности, №7) | нет |
| `break_reset` (4) | commit добавляет устройство пользователя, чей ключ идентичности сменился (§6.3.9) | нет |
| `break_recreate` (5) | начальный commit пересозданной группы (§6.3.10) — всегда, независимо от состава | нет |

Если причин несколько, берётся первое по порядку: `break_reset`, `break_disable`, `break_new_member`, `break_enable`, `rotate`; начальный commit пересоздания — всегда `break_recreate`. Начальный commit новой группы нового канала или ЛС истории ещё не имеет, и разрыв в нём ничего не скрывает; канал, созданный с выключенной настройкой, начинается с `break_disable` — так значение настройки записано в цепочке с самого начала.

**Настройка по цепочке** (повторное ревью безопасности, №7; ARCHITECTURE §4.7). Выключение и повторное включение настройки «Новые участники видят историю» записаны в самой цепочке — разрывами `break_disable` и `break_enable`. Последний такой разрыв, который видели коммитер или получатель (`break_recreate` его не меняет), задаёт для них значение настройки **независимо от слов сервера**: после `break_disable` вход нового пользователя — разрыв `break_new_member`, пока в цепочке не появится `break_enable`. Сервер, сказавший «включено» без `break_enable`, разрыва не избежит. Сервер, сказавший «включено» и добившийся `break_enable`, откроет новичкам историю только с этого разрыва — с момента лжи: `break_enable` в условии 1 §6.3.7 — граница открытой части. Сказать «выключено» безопасно: это только сужает. Если выключение совпало с commit-ом, которому нужен `break_reset`, выключение записывает следующий commit (DS это проверяет, §2.4).

**Получатель до merge** проверяет обязательные изменения: Remove, кроме пары возврата, — изменение не `none`; новый пользователь при выключенной настройке (по данным сервера о канале или по цепочке) — разрыв; устройство пользователя U с ключом идентичности IK, если получатель видел у U другой ключ — где угодно: прежний закреплённый (§3.2), в листьях дерева, в подписях сообщений своей истории — и в цепочке после последнего такого наблюдения нет `SegmentReset` пользователя U с ключом IK (§6.3.5), — `break_reset` (повторное ревью безопасности, №11: раньше учитывались только наблюдения текущего сегмента, и сброс, скрытый сервером, проходил мимо получателей, видевших прежний ключ раньше). Следующее устройство пользователя после сброса (тот же новый ключ) нового разрыва не вызывает: `SegmentReset` с этим ключом уже записан в цепочке (ревью безопасности Б-С1). Недостаёт — структурная жалоба `DISPUTE_REASON_HISTORY_ROTATION_MISSING` (§2.9). Лишняя ротация или лишний разрыв допустимы: они только сужают видимость истории.

DS по `history_change` ведёт номер текущего поколения, время его начала и тип разрыва. Плановую ротацию (30 сут) и разрывы при выключении и повторном включении настройки он запрашивает `MlsUpdateRequested{REASON_SCHEDULED_ROTATION | REASON_HISTORY_SETTING}`.

#### 6.3.4 Ссылки

При `rotate` автор commit-а тем же запросом выгружает ссылку:

```text
struct {
    opaque nonce[24];
    opaque ciphertext<V>;             // XChaCha20-Poly1305(sub(K_g, "link"), nonce, K_prev, aad = LinkAAD)
} HistoryKeyLink;                     // в контракте — вместе с generation и previous_generation

LinkAAD = TLS{ label "bebeberloga/v1 history link", channel_id[16], uint32 g, uint32 prev }
```

`prev` — поколение, ключ которого лежит в ссылке: предыдущее поколение того же сегмента. Пересоздание начинается разрывом без ссылки (§6.3.10), поэтому ссылка между группами не бывает. Удалённые ключ `K_g` не получают — значит, и ссылкой назад воспользоваться не могут. Разрывы ссылки не имеют. Сервер хранит ссылки канала, пока хранит его сообщения. После merge каждый участник проверяет, что ссылка расшифровывается в его `K_prev`; иначе — структурная жалоба `DISPUTE_REASON_HISTORY_LINK_INVALID`.

#### 6.3.5 Связка

Связка — «голова» цепочки, зашифрованная для эпохи; её выгружает автор **каждого** commit-а тем же запросом (ADR-0015).

```text
struct {
    uint8  version = 1;
    uint32 head_generation;
    opaque head_key[32];              // K_head
    uint32 segment_start;             // первое поколение текущего сегмента (после последнего разрыва)
    HistoryChange segment_start_change; // чем начат текущий сегмент; none — начало канала (поколение 1)
                                        // в новой группе после пересоздания — break_recreate (§6.3.10)
    SegmentReset  segment_reset<V>;   // при break_reset: чьи сбросы начали сегмент — по элементу на пользователя; иначе пусто
} BundlePlain;

bundle_key_E = MLS-Exporter("bebeberloga/v1 history bundle", TLS{ channel_id[16] }, 32)          // в эпохе E
bundle       = { nonce[24], XChaCha20-Poly1305(bundle_key_E, nonce, BundlePlain, aad = BundleAAD) }
BundleAAD    = TLS{ label "bebeberloga/v1 history bundle", channel_id[16], uint32 head_generation, uint64 epoch }
```

```text
struct {
    opaque user_id[16];
    opaque identity_key_hash[32];     // SHA-256 нового ключа идентичности пользователя
} SegmentReset;                       // по элементу на каждого пользователя, чьё устройство после сброса добавил commit
```

`SegmentReset` записывает в саму цепочку, чьи сбросы ключей начали сегмент и с какими новыми ключами — по элементу на каждого пользователя: один commit может добавить устройства нескольких пользователей после сброса (повторное ревью безопасности, №12). Так получатели и следующие коммитеры знают, под каким ключом пользователь законно присутствует в сегменте, даже если сами сброса не видели (Б-С1).

`HistoryKeyBundle.generation` дублирует `head_generation` открыто: DS сверяет его с текущим поколением. Связка нужна тем, кто вошёл в эпохе позже начала поколения: вывести `K_g` из exporter прошлой эпохи они не могут. Связки хранятся для эпох в пределах `HANDSHAKE_RETENTION`.

#### 6.3.6 Мост

Мост — адресная доставка ключей истории конкретному устройству через разрыв цепочки. Его отдаёт автор того commit-а, которым устройство входит в группу, тем же запросом.

**Ключ HPKE истории устройства.** Отдельная пара X25519 устройства — не ключи MLS. Открытая часть публикуется вместе с ключом подписи (`PUT /devices/me/keys`) и подписана им:

```text
history_hpke_key_signature = AppSign(sk устройства, "history hpke key", TLS{ user_id[16], device_id[16], history_hpke_key[32] })
```

Коммитер проверяет подпись ключом подписи из credential добавляемого листа — сервер подменить ключ не может.

```text
struct {
    uint32        generation;         // последнее разрешённое поколение сегмента (§6.3.7)
    uint32        segment_start;      // первое поколение сегмента
    HistoryChange segment_start_change; // чем начат сегмент; none — начало канала
    SegmentReset  segment_reset<V>;   // при break_reset: чьи сбросы начали сегмент; иначе пусто
    opaque        key[32];
} BridgedKey;
struct { uint8 version = 1; BridgedKey heads<V>; } BridgePlain;   // по ключу на сегмент

struct {
    BridgePlain plain;
    opaque      committer_device_id[16];
    opaque      signature[64];       // AppSign(sk коммитера, "history bridge signature",
                                     //         TLS{ channel_id[16], group_id[16], device_id[16], uint64 epoch, BridgePlain })
} SignedBridge;

bridge = HPKE.SealBase(pkR = history_hpke_key устройства,
                       info = TLS{ label "bebeberloga/v1 history bridge", channel_id[16], group_id[16], device_id[16], uint64 epoch },
                       aad = "", pt = SignedBridge)
HPKE (RFC 9180): DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-128-GCM — те же примитивы, что у ciphersuite 0x0001
```

Устройство получает мост вместе с Welcome (`Welcome.history_bridge`), расшифровывает и **проверяет подпись коммитера** (ревью Б-Н2): HPKE в режиме Base не аутентифицирует отправителя, и без подписи сервер мог бы подложить мост с мусорными ключами и типами сегментов на открытый ключ устройства. `committer_device_id` обязан совпадать с подписантом GroupInfo в Welcome — автором commit-а, — а подпись проверяется его ключом подписи из дерева. Мост, ключ в котором противоречит уже известному устройству ключу того же поколения, отвергается целиком. `group_id` в подписи и `info` не даёт повторить устаревший мост после пересоздания, где эпохи начинаются заново (повторное ревью безопасности). Затем устройство проходит от каждого ключа по ссылкам вниз до начала его сегмента. Тип начала сегмента из связки или моста — слово участника, который эти ключи и так знает; получатель хранит его для своих будущих мостов (§6.3.7). Если сервер (`HistoryGenerationInfo.change`, `GET /channels/{id}/history-generations`) называет для сегмента более строгий тип — проходимый только по присутствию (`break_new_member`, `break_disable`) вместо проходимого, — получатель берёт более строгий: это только сужает его будущие мосты (повторное ревью безопасности).

#### 6.3.7 На что имеет право входящее устройство

Право на историю выводит **коммитер из собственных наблюдений**. Значение сервера `ProposalAAD.history_from_generation` право только сужает — расширить его нельзя.

**Что коммитер наблюдает и хранит** (локальная база, §7.4), по каждому каналу:
- **тип начала каждого сегмента**, ключи которого у него есть: из `RosterDelta.history_change` commit-а, начавшего сегмент, если он этот commit применял; иначе — из связки или моста, через которые получил ключи (`segment_start_change`, §6.3.5–§6.3.6). Тип берётся из самой цепочки, а не из текущего значения настройки на сервере;
- **присутствие:** для каждого поколения, в котором коммитер сам был участником, — пользователи, чьи устройства стояли в дереве группы хотя бы в одной эпохе этого поколения;
- **ключи идентичности пользователей:** какие ключи и в каких поколениях он видел — в листьях дерева (credential, §1.3), в подписях сообщений своей истории (§6.2.5), закреплённый ключ (§3.2).

**Правило.** Входит устройство D пользователя U с ключом идентичности IK(D). Поколение g, ключ которого есть у коммитера, разрешено D, если выполнены все три условия:
1. **Видимость.** g лежит в открытой части цепочки — от текущего сегмента назад через `rotate`, `break_reset` и `break_recreate` до сегмента, начатого `break_enable` или началом канала, включительно; если по дороге встретился `break_new_member` или `break_disable`, открытой части нет. **Или** коммитер сам видел устройства U в дереве группы в поколении g. Сегменты, начатые разрывом при выключенной истории (`break_new_member`, `break_disable`), проходят только по присутствию.
2. **Ключ идентичности.** В поколении g и после него коммитер не видел у U ключа идентичности, отличного от IK(D), — ни закреплённого, ни в листьях, ни в подписях сообщений, ни в `SegmentReset` сегментов. Видел другой ключ где угодно — все поколения до последнего такого наблюдения закрыты (§6.3.9). **Плюс история ключей сервера:** если у U есть прежний ключ, отличный от IK(D), с `valid_until`, то закрыты все поколения, начатые раньше этого `valid_until`. Время начала поколения — `started_at` из `GET /channels/{id}/history-generations` (время приёма DS commit-а, начавшего поколение; тот же источник времени, что `valid_until`). История сервера может право только сузить: скрыв её, сервер не откроет того, что закрыли наблюдения.
3. **Сужение сервером.** g ≥ `history_from_generation`.

Ключ поколения по ссылкам открывает все предыдущие поколения своего сегмента. Поэтому мост несёт для каждого сегмента ключ последнего поколения из ряда разрешённых поколений, **непрерывного от начала сегмента**; сегмент, первое поколение которого не разрешено, в мост не идёт — точность права равна сегменту. Текущий сегмент устройство получает со связкой целиком (§6.3.5). По условиям 1–2 он разрешён всегда, когда §6.3.3 не требует разрыва: вход нового пользователя при выключенной истории и сменившийся ключ идентичности сами начинают новый сегмент. Условие 3 к текущему сегменту не применяется: законное значение сервера всегда лежит на границе сегментов (вход пользователя, повторное включение настройки).

**Что из этого следует:**
- новое или вернувшееся после горизонта устройство участника при выключенной истории (№9) — поколения, в которых коммитер видел этого участника: с момента его входа;
- новичок при включённой истории — открытая часть цепочки, включая сегменты за чужими сбросами;
- новичок при выключенной истории — этот commit сам разрыв, моста нет;
- устройство после сброса ключей — только поколения после последнего наблюдения прежнего ключа (§6.3.9);
- сервер, назвавший `history_from_generation` меньше права по наблюдениям, ничего не добавит; больше — сузит мост.

Коммитер, сам вошедший позже, отдаёт меньше, чем положено: наблюдений присутствия за время до его входа у него нет (§8.2 п. 15). Поэтому назначенный коммитер при Add — по возможности другое устройство того же пользователя (§2.6): у него есть и ключи, и наблюдения.

Так одним правилом покрыты: новое устройство участника при выключенной истории (№9), устройство, вернувшееся после горизонта (§2.11), новички и новые устройства других участников в каналах, где был разрыв из-за сброса чужих ключей (§6.3.9). Личная группа для №9 не нужна.

#### 6.3.8 Как читается история

1. Участник, применивший commit с новым поколением, выводит `K_g` из exporter (§6.3.1) и проверяет ссылку (§6.3.4).
2. Новичок или новое устройство после Welcome: связка эпохи Welcome (`GET /mls/groups/{id}/history-key-bundle?epoch=`) → `K_head` → ссылки вниз до начала сегмента (`GET /channels/{id}/history-key-links`) → мост из Welcome → головные ключи прежних сегментов → их ссылки.
3. История — `GET /channels/{id}/messages?before=` порциями. Сообщения поколений до права устройства сервер не отдаёт (при выключенной настройке — ADR-0015 п. 3), а если отдал, клиент их не показывает (SCREENS/08 §10).
4. Ключи истории хранятся в локальной базе (§7.4) и не удаляются при выходе устройства из группы — только вместе с базой.

#### 6.3.9 Сброс ключей («Начать заново»)

**Правило** (ответ владельца OPEN-QUESTIONS №15): история, написанная до сброса, на новых ключах недоступна нигде — в ЛС, групповых чатах и каналах.
- **Решает клиент коммитера, а не флаг сервера.** Ключ идентичности пользователя считается сменившимся, если коммитер видел у него другой ключ **где угодно** — закреплённый (§3.2), в листьях дерева группы (сюда же входят прежние листья, которые удаляет этот же commit) или в подписях его сообщений в своей истории (§6.3.7). Тогда коммитер начинает поколение `break_reset` и в мост этому устройству не кладёт ни одного поколения до последнего наблюдения прежнего ключа. История ключей у сервера (`GET /users/{id}/identity-keys`) смену только добавляет: поколения, начатые до `valid_until` прежнего ключа, закрыты и для коммитера без наблюдений (§6.3.7 п. 2). Коммитер записывает в связку и мосты `SegmentReset` — чей сброс начал сегмент. Получатели требуют `break_reset` по своим наблюдениям прежнего ключа, пока после них в цепочке нет `SegmentReset` с новым ключом (§6.3.3).
- После сброса у пользователя не остаётся других устройств: commit, добавляющий новое, удаляет прежние. Поэтому при выключенной истории это ещё и вход нового пользователя — разрыв `break_new_member` и ни одного ключа до него, независимо от наблюдений коммитера (§6.3.3).
- **Разрыв не лишает истории других.** Будущие новички и новые устройства остальных участников проходят разрыв `break_reset` мостом (§6.3.7). Новые устройства самого пользователя после сброса — только с этого разрыва.
- Личная группа пользователя после сброса — новая, с новым каналом (§6.5): прежняя личная история тоже недоступна.

**Отложенный сброс** (FLOWS/02 ш. 6, SCREENS/07 §4, §8):
1. Новое устройство: `POST /users/me/identity-reset` → `IdentityResetRequest`. Сервер **всегда** отправляет письмо на email аккаунта (FLOWS/02 ш. 6.1; clean room К3). Если у пользователя есть подтверждённое устройство, бывшее в сети за последние 30 дней, — `IDENTITY_RESET_STATE_PENDING`, `applies_at = now + 24 ч`, и сервер рассылает этим устройствам `IdentityResetRequested`. Иначе — сразу `READY`.
2. Отмена — `DELETE /users/me/identity-reset` → `CANCELLED`, событие `IdentityResetCancelled`:
   - с подтверждённого устройства — «Это не я»: сессия запросившего устройства отзывается (SCREENS/07 §8);
   - с самого запросившего устройства — «Отменить сброс» (SCREENS/07 §4, clean room К4): его сессия остаётся, и оно возвращается к выбору способа подтверждения;
   - если новое устройство за это время подтвердили другим способом — запрос отменяется сам;
   - **лимит после «Это не я»** (ответ владельца OPEN-QUESTIONS №19; FLOWS/02 ш. 6, SCREENS/07 §4): новый запрос сброса для аккаунта — не раньше чем через 24 ч и не больше 3 запросов за 7 сут (`RESET_REQUEST_LIMIT`); иначе `IDENTITY_RESET_LIMITED{retry_after_ms}`, и новое устройство показывает «Сброс ключей сейчас недоступен…». Письмо уходит на каждый принятый запрос.
3. После `applies_at` (или сразу при `READY`) новое устройство создаёт ключ идентичности, новый ключ восстановления — обязательный экран с проверкой (ответ владельца №14, SCREENS/07 §5) — и вызывает `PUT /users/me/identity-key {reset_request_id, identity_pubkey, encrypted_identity_key, recovery_public_key}`. Принимается только от устройства, запросившего этот сброс (`requested_by_device_id`, ревью Б-Н1), иначе `PERMISSION_DENIED`; раньше срока — `IDENTITY_RESET_PENDING{retry_after_ms}`.
4. Сервер применяет сброс: удаляет прочие устройства (Remove во всех группах) с признаком «удалено сбросом» — они спрашивают «Это был ты?», а не стирают базу молча (§3.7), — удаляет их KeyPackage и старый блоб восстановления, записывает прежний ключ идентичности в историю с `valid_until`, рассылает `UserUpdated`.

Задержка защищает от того, кто знает только пароль. От злонамеренного сервера историю защищает не задержка, а правило коммитера выше.

#### 6.3.10 Пересоздание группы и ключи истории

- **Новая группа всегда начинается разрывом `break_recreate` без ссылки назад.** Создатель (§2.10.4) начинает поколение `RecreationPlan.next_generation` (§2.10.4) и ссылку на прежнее поколение не выгружает. Ссылка отдала бы текущий сегмент старой группы каждому, кто получит связку новой группы, без проверки его права — в том числе тем, кому положен разрыв: новому пользователю при выключенной истории и устройству после сброса ключей (находка ревью безопасности Б-В1). Сервер мог бы вызвать это сам, объявив потерю журнала.
- **Бывшие участники** ключи прежних поколений уже имеют — им ничего не передаётся.
- **Заявки старой группы** (`R − R₀`: новички, устройства после сброса ключей, возвращающиеся устройства) в начальный commit не входят (§2.10.3) и входят в новую группу следующим обычным Add: разрыв — по §6.3.3, мост — по §6.3.7, как в любой группе (повторное ревью безопасности, №2). Поэтому начальный commit мостов не несёт, а `break_recreate` в условии 1 §6.3.7 проходим, как `break_reset`: право каждого будущего входящего решается при его собственном Add.
- **Проверка у входящих по Welcome** (дополняет §2.10.6): связка новой группы имеет `segment_start_change = break_recreate` и `segment_start = head_generation`; иначе — отказ и жалоба `DISPUTE_REASON_RECREATION_INVALID`. Ссылкой, выводящей из начала сегмента, клиент не пользуется никогда (§6.3.8).
- **Номер поколения.** DS выдаёт в `RecreationPlan.next_generation` номер больше всех известных ему, включая поколение спорного commit-а. Создатель берёт `max(next_generation, своё головное поколение + 1)`: после потери журнала DS может не знать поколений, которые у клиентов уже есть, и номера совпали бы (Б-С5). Входящий по Welcome отвергает новую группу, если её головное поколение не больше головного поколения, известного ему в этом канале (`DISPUTE_REASON_RECREATION_INVALID`).
- `continuity_tag = HMAC-SHA256(sub(K_g0, "recreation"), ContinuityInput)` (§2.10.4), `g0 = RecreationPlan.history_key_generation`.
- **Поколение спорного commit-а** — отдельный сегмент. Сообщения, отправленные во время проверки под поколением, которое начал спорный commit, читают применившие его. Будущим входящим этот сегмент отдаёт мостом по §6.3.7 коммитер, у которого есть его ключ. Устройства, бывшие в группе и commit не применившие, его не получают: окно — не дольше проверки (§2.9.3, §8.2 п. 16).

### 6.4 mention-hint

```text
hint = первые 16 байт HMAC-SHA256(sub(K_g, "mention"), TLS{ label "bebeberloga/v1 mention hint", uint8 kind, opaque id[16] })
kind: 1 — пользователь, 2 — роль
```

- Отправитель кладёт в `MessageMeta.mention_hints` хинт каждого упомянутого пользователя и роли под поколением сообщения, в случайном порядке (MESSAGES.md §4).
- Секрет хинта — подключ поколения, а не эпохи (решение Р4): эпоха меняется при каждом входе, и офлайн-участник не смог бы зарегистрировать хинты за пропущенные эпохи — их секретов у него нет. Ключи пропущенных поколений у него есть (§6.3.8).
- **Регистрация одним запросом за все каналы:** `PUT /users/me/mention-hints {entries[]{channel_id, generation, hints[]}}` — хинт своего `user_id` и своих ролей для каждого канала и поколения. Клиент отправляет её после нового поколения в любом канале, смены ролей, входа в канал и возвращения, объединяя изменения за несколько секунд.
- **Задним числом:** хинт, пришедший позже сообщения, сервер сопоставляет с уже сохранёнными сообщениями того же канала и поколения и пересчитывает бейджи и счётчики упоминаний.
- Сервер хранит хинты участника по каналу для текущего и предыдущего поколений и для поколений, где у участника есть непрочитанные сообщения.
- Что узнаёт сервер: кого упомянули — ради этого хинт и нужен (адресное уведомление); остальные участники этого не узнают. Сервер видит число упоминаний в сообщении и совпадение хинтов внутри поколения.

### 6.5 Личная группа пользователя и резервная копия

- **Личный канал** — `CHANNEL_TYPE_PERSONAL`, один на пользователя, создаётся при регистрации первым устройством; группа `GROUP_KIND_PERSONAL` (`group_binding.kind = 3`); участники — все подтверждённые устройства пользователя (Add при подтверждении, назначенный коммитер — подтвердившее устройство). Отстранения и застоя в личной группе нет (§2.6, §2.9.6). Настройки видимости истории нет: история видна всем устройствам пользователя.
- **Содержимое** — сообщения с телом `PersonalSyncBody` (envelope.proto): статусы проверки собеседников `{user_id, identity_key, verified, at}` (§3.2, ответ владельца №7), «доверять этому домену» (SCREENS/08 §3), запись о создании ключа восстановления `{device_id, created_at}` (§3.5.4). Это обычные сообщения личного канала (§6.2); действует последнее **по `id`** — UUIDv7 автора, подписанный в `MessageContext` (§6.2.5). Время в `id` ограничено окном §6.2.8 (не больше 5 мин вперёд), а писать в личный канал могут только свои устройства, поэтому запись с `id` из будущего перебьёт следующие не дольше чем на 5 мин. Время приёма `created_at` ставит сервер, и порядок по нему позволил бы серверу переставлять записи — например, откатить «снять проверку» (повторное ревью безопасности, №13; решение владельца меняет порядок, выбранный по Б-В2). Принимаются только от своего пользователя (§6.2.5 п. 6).
- **Состав личной группы** проверяет клиент: в ней допустимы только листья своего `user_id` (§1.3 п. 4). Устройство чужого пользователя, добавленное сервером в скрытый канал, иначе подделало бы статус «проверен» и обесценило код безопасности.
- **Резервная копия на ключ восстановления** (решение Р5):
  - из ключа восстановления выводится пара HPKE: `master = Argon2id(...)` (§3.5.2), `(rsk, RPK) = DeriveKeyPair(HKDF-Expand(master, "bebeberloga/v1 recovery hpke", 32))` (RFC 9180 §7.1.3, X25519);
  - `RPK` подписан ключом идентичности: `AppSign(identity_sk, "recovery hpke key", TLS{ user_id[16], RPK[32], uint64 created_at_ms })` — `RecoveryPublicKey` у сервера (`GET /users/me/recovery-key`). Устройство проверяет подпись до шифрования: сервер не подставит свой ключ;
  - автор каждого commit-а личной группы, начавшего новое поколение, тем же запросом выгружает `PersonalBackup{generation, blob}`, где `blob = HPKE.SealBase(RPK, info = TLS{ label "bebeberloga/v1 personal backup", user_id[16], uint32 g }, aad = "", pt = SignedBackup)`, а `SignedBackup = { opaque key[32]; opaque device_id[16]; opaque signature[64] }`, `signature = AppSign(sk устройства, "personal backup signature", TLS{ user_id[16], uint32 g, key[32] })`. Восстанавливающее устройство принимает копию, только если подпись проверяется ключом подписи устройства своего пользователя, подписанного восстановленным ключом идентичности (ревью Б-Н2): сервер не подложит свой ключ поколения;
  - **восстановление без старых устройств:** устройство, подтверждённое ключом восстановления (§3.5), выводит `rsk`, берёт последнюю копию (`GET /users/me/personal-backup`), получает `K_g` и по ссылкам — всю личную историю. Если в личной группе не осталось устройств, кроме удаляемых, оно пересоздаёт её (§2.10, причина `RECREATION_REASON_PERSONAL_RESTORE`, `continuity_tag` от восстановленного ключа); иначе ждёт Add от вернувшегося устройства;
  - **смена ключа восстановления** (§3.5.4): устройство шифрует текущее поколение личной группы на новый `RPK` и выгружает вместе с новым блобом (`PUT /users/me/recovery-key`); прежние копии сервер удаляет.
- После сброса ключей (§6.3.9) — новый личный канал; копия прежнего недействительна вместе с прежним ключом восстановления.

### 6.6 Служебные конверты и устаревшие типы

- MLS application message — только для служебных конвертов вне истории; в 1.0 таких нет, DS их не принимает.
- `HistoryKeysBody` в 1.0 не используется: ключи поколений выводятся из exporter (§6.3.1), доставка через разрыв — мостом (§6.3.6). Получатель тело игнорирует.
- `CallKeyBody` не используется (§5.5).
- `FileKeyBody` (повторная выдача ключа вложения) — обычное сообщение по §6.2.

### 6.7 Что видит сервер

Номера поколений, их начало и тип разрыва (кто вошёл при выключенной истории, чей ключ сменился); размер сообщения с точностью до 256 байт; число упоминаний и совпадение хинтов внутри поколения; размеры мостов; наличие резервной копии личной группы. Ключей истории, ключей сообщений и открытого текста — нет.

## 7. Файлы и локальное хранилище

### 7.1 Ключ файла и подключи

- На каждое вложение — ключ `Kf`, 32 случайных байта, в `FileRef.key` внутри зашифрованного конверта.
- Один `Kf` на все объекты вложения, у каждого объекта — свой подключ:

  ```text
  object_key = HKDF-Expand(HKDF-Extract(salt = "", IKM = Kf), TLS{ label "bebeberloga/v1 file object", uint8 kind }, 32)
  kind: 1 — файл; 2 — превью (второй blob, ARCHITECTURE §4.5); 3 — миниатюра FileRef.thumbnail
  ```

- Каждый `object_key` шифрует ровно один объект.

### 7.2 Формат зашифрованного объекта

```text
struct {
    opaque magic[4] = "BBFE";
    uint8  version = 1;
    uint8  kind;
    uint8  chunk_size_log2 = 20;     // 1 МиБ
    opaque nonce_prefix[19];         // случайный
} FileHeader;                        // 26 байт, в начале blob-а

nonce_i = nonce_prefix ‖ uint32(i) ‖ uint8(last)              // 24 байта; last = 1 только у последнего чанка
chunk_i = XChaCha20-Poly1305(object_key, nonce_i, plaintext_i, aad = FileHeader)
blob    = FileHeader ‖ chunk_0 ‖ … ‖ chunk_{n−1}
```

- `plaintext_i` — по 1 МиБ, последний — от 0 до 1 МиБ; пустой файл — один пустой последний чанк. Размер blob-а: `26 + len + 16·n`, `n = max(1, ⌈len / 2²⁰⌉)`.
- Это конструкция STREAM (Hoang, Reyhanitabar, Rogaway, Vizár, 2015): счётчик ловит перестановку и выпадение чанков, флаг последнего — усечение и дописывание, AAD — подмену заголовка.
- Получатель отвергает неизвестные `magic`, `version`, `chunk_size_log2` и данные после последнего чанка; расшифровывает и показывает потоково, чанк за чанком, а конец файла признаёт только по чанку с `last = 1`.
- Миниатюра `FileRef.thumbnail` (≤ 8 КиБ) — объект вида 3 из одного чанка внутри конверта: контракт B1 требует шифровать её ключом файла.

### 7.3 Хэши

- `FileRef.ciphertext_hash` = `Attachment.ciphertext_hash` = BLAKE3-256 от всего blob-а; `FileRef.content_hash` = BLAKE3-256 от открытого файла. BLAKE3 задан контрактом B1: он быстрый на больших файлах; крейт `blake3` (CC0-1.0 OR Apache-2.0) — B3 вносит в `LICENSING.md`.
- Клиент после скачивания сверяет `ciphertext_hash` до расшифровки (подмену и порчу видно сразу) и `content_hash` — после. Ошибка — «Файл повреждён или ключ недоступен» (FLOWS/06).
- Сервер видит размер blob-а и хэш шифртекста — метаданные; `content_hash` лежит внутри конверта.

### 7.4 Локальная база

- SQLite + SQLCipher 4, одна база на пару «инстанс, аккаунт» на устройстве. Ключ базы `K_db` — 32 случайных байта, создаётся при первом запуске и задаётся как готовый ключ (без вывода из пароля). Хранится в хранилище ОС: Keychain на macOS (только это устройство, доступ после первой разблокировки), DPAPI текущего пользователя на Windows, Secret Service (libsecret) на Linux. Electron `safeStorage` допустим только с настоящим хранилищем: режим хранения в открытом виде (на Linux — `basic_text`) запрещён.
- **Linux без хранилища ключей** (ответ владельца OPEN-QUESTIONS №12, SCREENS/07 §10): `K_db` оборачивается ключом из пароля этого устройства и хранится рядом с базой:

  ```text
  struct {
      uint8  version = 1;
      uint32 argon2_t;               // 3
      uint32 argon2_m_kib;           // 262 144 (256 МиБ)
      uint8  argon2_p;               // 4
      opaque salt[16];
      opaque nonce[24];
      opaque ciphertext<V>;          // XChaCha20-Poly1305(K_pw, nonce, K_db, aad = DeviceKeyAAD)
  } DeviceKeyWrap;

  K_pw         = Argon2id(пароль устройства в UTF-8 после NFC, salt, t, m, p, 32)
  DeviceKeyAAD = TLS{ label "bebeberloga/v1 device password", user_id[16], device_id[16],
                      version, argon2_t, argon2_m_kib, argon2_p, salt }
  ```

  Память больше, чем у ключа восстановления (§3.5.2): пароль придумывает человек, и при краже файлов перебор упирается только в Argon2id; 256 МиБ — около секунды на десктопе один раз при запуске. Неверный пароль — ошибка AEAD → «Пароль не подошёл». Пароль на сервер не уходит. «Не помню пароль» — выход на устройстве: база и `DeviceKeyWrap` стираются, сервер удаляет устройство из групп, после входа это новое устройство (SCREENS/07 §10). Ограничение — §8.2 п. 9.
- SQLCipher: параметры версии 4 по умолчанию (AES-256-CBC и HMAC-SHA512 на страницу), `cipher_memory_security = ON`, `secure_delete = ON`.
- В базе: состояние MLS (`StorageProvider` openmls, ADR-0016 п. 6), seed ключа идентичности, ключ подписи устройства, закрытые ключи KeyPackage, ключи истории (§6), расшифрованные сообщения и индекс FTS5 (ARCHITECTURE §4.9), очередь неотправленных (§2.11.4), закреплённые ключи и статусы проверки (§3.2), записи об удалениях (§2.10.6 п. 5), журнал пересозданий (§2.10.8), наблюдения коммитера по каналам — типы начала сегментов, присутствие пользователей по поколениям, ключи идентичности, виденные у пользователей (§6.3.7).
- Вне базы на диске — только зашифрованные объекты (скачанные blob-ы как есть, расшифровка на лету). Открытый файл появляется только по явному «Сохранить» пользователя. В журналах и аварийных дампах нет секретов и открытого текста.
- Копия базы на другом компьютере бесполезна: ключ — в хранилище ОС этого устройства.
- Отключённое устройство («Это устройство отключено», FLOWS/02) удаляет базу (с `secure_delete`, затем сам файл) и запись в хранилище ОС.

### 7.5 Граница процессов Electron

- crypto-core работает в main-процессе (napi-rs, ADR-0016 п. 5). Renderer получает расшифрованное содержимое для показа и ключи медиа отправителей (§5.2) — больше ничего: ни seed, ни состояния MLS, ни exporter.
- Процесс media-engine получает только ключи своих экземпляров шифратора стрима (§5.2).
- Секреты в памяти — в обнуляемых буферах, у объектов с ключами нет отладочного вывода (ADR-0016 «Последствия»).

### 8.2 Принятые ограничения

1. **Доступность при злонамеренных commit-ах и жалобах** (§2.6, §2.9, §2.10.8). Конфиденциальность ни в одном сценарии не страдает: честный клиент не применяет commit, не прошедший его проверки, и не входит в группу, состояние которой их не проходит. Страдает доступность канала. Назначение коммитером — не препятствие само по себе: его можно получить по желанию, подтвердив своё новое устройство (§2.6 п. 1). Препятствия — испытательный срок (`DESIGNATION_PROBATION` 7 сут в сообществе: свежий аккаунт не назначается, пока в сети есть другие кандидаты) и отстранение (`DESIGNATION_BAN` 30 сут на всём инстансе после первой жалобы, подтверждённой по правилу 1: отстранённый назначается, только если других кандидатов в сети нет). При 5 000 листьях:
   | Сценарий | Что происходит | Наибольшая цена |
   |---|---|---|
   | Назначенный злонамеренный участник присылает «мусорный» или дефектный commit | Никто, кроме автора, commit не подтверждает; на жалобы честных — проверка с паузой (§2.9.2 п. 1). Если commit начал поколение, **писать в канал не может никто**, пока нет решения: ≥ 30 с; в большой группе без мнений других пользователей — до `REVIEW_MAX` 1 ч. Затем пересоздание — и сверх `RECREATION_LIMIT`, раз писать некому (§2.9.4); если пожаловались не меньше двух пользователей — автор отстранён на 30 сут на всём инстансе | Каждый повтор — новый аккаунт, проживший в сообществе 7 сут и ещё не отстранённый; 5–7 ГБ исходящего трафика DS на каждое пересоздание. Суточного простоя канала нет |
   | Сообщник автора подтверждает дефектный commit (`ack` или commit поверх) | Голоса считаются всегда (§2.9.2): пожаловавшихся честных пользователей больше — жалоба подтверждена, пересоздание от базовой эпохи спорного commit-а, commit-ы сообщника отбрасываются | Как в строке выше, но аккаунтов двое; если пересоздание сверх лимита, а commit подтверждён сообщником, — оно откладывается (§2.9.4), и до освобождения окна (≤ 24 ч) «ошибка ключей» только у пожаловавшихся |
   | Сообщник против одного честного жалобщика | Жалоба отклонена (`A` ≥ 1, `C` < 2); честный клиент при возврате видит дефект в состоянии группы, не входит и остаётся в «ошибке ключей», повторяя возврат с паузами. Если так ждут возвраты ≥ 2 пользователей, а коммитить могут устройства одного, — застой возвратов и пересоздание (§2.9.6) | Потеря доступности для одного клиента |
   | Ложные жалобы на подтверждённые commit-ы | Подсчёт без паузы (§2.9.2 п. 2): другие пользователи подтвердили — жалоба отклонена через 30 с, жалобщику возврат: один commit и один Welcome 1–1,4 МБ; поколения ключа истории возврат не меняет (§6.3.3), хинты упоминаний не перерегистрируются | `DISPUTE_RATE` — на устройство и группу, а устройств у пользователя сколько угодно: ~35 МБ Welcome в сутки на каждое; сообщения не страдают |
   | Ложные жалобы на последний, ещё не подтверждённый commit | Проверка с паузой до 30 с: handshake стоит, сообщения идут; другие подтверждают — жалобщику возврат | Пауза handshake не больше `REVIEW_BUDGET` 10 мин в час на группу, сколько бы аккаунтов и устройств ни жаловались, — до 4 ч в сутки; сверх бюджета голоса считаются без паузы |
   | Два сговорившихся участника против принимающих | Пересоздание, пока жалующихся не меньше принявших, не раньше 30 с | ≤ 3 пересоздания в сутки на канал |
   | Маленькая группа (≤ 50 листьев), включая ЛС | Одиночная жалоба без подтверждения — пересоздание после 30 с, без отстранения автора; жалобы других устройств самого автора в голосах не считаются. В ЛС второй участник, не коммитя возвраты первого, вызывает застой уже по одному другому пользователю | ≤ ~0,7 МБ на пересоздание |
   | Участник держит чужие возвраты, не коммитя | Застой возвратов (§2.9.6): через 60 с заморозка и пересоздание без отстранения, в пределах `RECREATION_LIMIT` | ≤ 3 пересоздания в сутки на канал; если и в новой группе коммитить может только он, возвраты снова ждут — лечение модерацией |
   | Участник держит чужие возвраты, отбрасывая их Add как негодные | Commit-ы идут, поэтому застоя нет (§2.9.6); DS заменяет пакет (§2.7), а возвраты коммитят другие назначенные по очереди п. 4 §2.6 | Возвраты ждут, пока в сети нет других коммитеров; лечение модерацией |
   | Жалобы в звонке на честного коммитера | Новая группа звонка за ≈ 1 с, без отстранения (§5.1) | ≤ `CALL_RESTART_RATE` новых групп на пользователя |

   Против злоупотребления — назначение только одного устройства, испытательный срок, отстранение по пользователю на всём инстансе (§2.6), журнал жалоб и подтверждений на DS и модерация (исключить участника). В публичном сообществе исключённый может вернуться с новым аккаунтом, но такой аккаунт 7 сут не получает назначений, пока в сети есть другие кандидаты, а каждый отстранённый аккаунт 30 сут на всём инстансе назначается только последним. Отстранение лишает приоритета, а не права, поэтому удаление устройства доходит до commit-а и в группе, где в сети одни отстранённые (§2.6). Пересоздания по всем причинам ограничены `RECREATION_LIMIT` на канал, кроме тех, без которых канал стоял бы для всех.
2. **Нет PCS для украденного, но не удалённого устройства в большой группе.** Ключи листа устройства (HPKE-ключ листа и ключ подписи) действуют, пока само устройство не сделает commit в группе. Плановая ротация обновляет путь одного коммитера в сутки (§1.9), то есть конкретный лист в канале на 5 000 листьев — раз в годы. Тот, кто скопировал состояние устройства, читает новые эпохи всех его групп, пока устройство не удалят (Remove, §2.8) или оно само не закоммитит в группе. Защита в 1.0 — удаление незнакомых и потерянных устройств (SCREENS/07 §6).

   **Оценка периодических Update** (каждое устройство раз в 30 дней делает commit со своим UpdatePath) в группе на 5 000 листьев:
   | Величина | Оценка |
   |---|---|
   | Commit-ов на группу | 5 000 / 30 ≈ 167 в сутки (≈ 7 в час) |
   | Размер commit-а | ~2 КБ в заполненном дереве (13 уровней × ~85 байт HPKE + лист ~270 байт + подписи); до сотен КБ в дереве с пустыми родителями после крупных пачек Add (S1: 83 КБ при 1 000 листьях) |
   | Исходящий трафик DS | 167 × 5 000 × 2 КБ ≈ 1,7 ГБ в сутки на группу в заполненном дереве; на порядки больше, пока дерево не заполнится |
   | На устройство | ≈ 0,3 МБ и 0,5–1,7 с CPU в сутки на группу |
   | Побочные эффекты | +167 эпох в сутки: связка ключей истории на каждый commit (§6.3.5), очередь назначенного коммитера; отправку сообщений смена эпохи не прерывает (§6.2.8) |

   Периодические Update помогают, только если состояние устройства скопировали, а само устройство осталось у владельца и продолжает работать; от устройства, которое украли целиком, защищает только Remove. При цене ~1,7 ГБ в сутки на каждый крупный канал и лишних эпохах это **вариант на после 1.0**: например, Update только от устройств, чей лист не обновлялся дольше 30 дней, и только в группах, где устройство активно.
3. **Сервер как Authentication Service.** Сервер решает, кто чей ключ и кто имеет доступ, и этим может:
   - **в любой момент**, а не только при первой встрече, подменить ключ идентичности пользователя у собеседников, выдав подмену за сброс ключей: задержка 24 ч и письмо (§6.3.9) — на стороне того же сервера, а клиент смену ключа не блокирует (ADR-0013 п. 3). Видно: заметка «Ключи <имя> изменились» в группах до 50 участников, баннер у проверивших собеседника, тревога на устройствах самого пользователя (§3.2), код безопасности (§4.1);
   - добавить устройство вымышленного пользователя обычным Add (§1.3, пп. 3–4). При включённой истории — а это значение по умолчанию — такой «призрак» получает всю видимую историю канала, а не только будущие сообщения; в каналах больше 50 участников — без заметки. Видно: список участников и вкладка «Безопасность», список участников звонка (§4.3).
   Key Transparency — v2 (ARCHITECTURE §4.10).
4. **Seed ключа идентичности — на каждом подтверждённом устройстве.** Взломанное устройство может подписать новые устройства пользователя; чтобы зарегистрировать устройство, нужна сессия (пароль). Удаление устройства ключ идентичности не меняет; при краже устройства вместе с паролем — «Начать заново» (§3.6).
5. **Новый ключ восстановления не меняет ключ идентичности** (§3.5.4).
6. **Подтверждение по QR:** если QR сфотографирован, злонамеренный сервер может подсунуть новому устройству ложную идентичность, но не получить настоящую (§3.4.3). При сравнении картинок это закрыто подтверждением на обоих устройствах.
7. **Код звонка не выявляет лишнее устройство** (§4.3).
8. **Слабее forward secrecy истории** (ADR-0015): ключ поколения открывает все сообщения поколения на сервере, а головной ключ сегмента по ссылкам — и все прежние поколения сегмента (§6.3.4). Удалённые теряют доступ к новым поколениям, но не к тем, что уже знали.
9. **Пароль устройства на Linux без хранилища ключей** (§7.4): тот, кто скопировал файлы профиля, может перебирать пароль офлайн; защита — только стойкость пароля и Argon2id (256 МиБ). На устройствах с хранилищем ОС этого риска нет.
10. **Удалённый из звонка и смена ключа медиа** (§5.1, §5.3). Remove в группе звонка идёт вне интервала commit-ов, а на commit-е с Remove отправители переходят на новый ключ сразу при merge. Удалённый может расшифровать медиа, пока отправитель не применит commit с его удалением: назначение коммитера, один RTT на commit и доставка — плюс 1 с на каждый сбой назначенного коммитера. Проверки жалоб, заморозки и лимита пересозданий в группе звонка нет: сбой ведёт к новой группе звонка примерно за 1 с (§5.1), и ничто на DS не задерживает Remove на десятки секунд. Сверху окно ограничено **на клиенте**: если commit с опубликованным Remove не применён за `CALL_REMOVE_PAUSE` = 2 с, отправитель приостанавливает свои медиа (§5.3 п. 7). SFU в модели угроз не доверенный, поэтому окно не опирается на то, что SFU перестаёт пересылать удалённому. **Цены, принятые владельцем** (FLOWS/07, ADR-0021): получатель, отставший от отправителя больше чем на `MEDIA_KEY_HOLD` (500 мс) в момент выхода участника, теряет кадры до своего merge — видео восстанавливается ключевым кадром (§5.3 п. 4); при сбое смены ключа дольше 2 с отправка медиа стоит до нового ключа («Обновляем ключи звонка…», SCREENS/05 §1).
11. **Ложь о текущем значении настройки** (§6.3.3, §6.3.7). Значение «Новые участники видят историю» хранит сервер, но выключение и включение записаны в цепочке разрывами `break_disable` и `break_enable` (повторное ревью безопасности, №7). После `break_disable` коммитер и получатели считают историю выключенной по цепочке: ложь «включено» не избавит от разрыва при входе нового пользователя, а добившись `break_enable`, сервер откроет новичкам историю только с этого разрыва — с момента лжи. Прежние сегменты коммитер отдаёт по типам разрывов в цепочке и по своим наблюдениям присутствия, а не по настройке. Остаётся граница доверия к самой настройке: если сервер не дал записать выключение — не запросил разрыв, а коммитер о выключении не знал, — для цепочки история так и осталась включённой, и новичок получит открытую часть, как при включённой настройке. DS, принявший commit без `break_disable` после выключения, нарушает свою проверку (§2.4); заметить это может администратор, выключивший настройку, по типу разрыва в своей цепочке.
12. **Неотрицаемость.** Подпись устройства в каждом сообщении (§6.2.2) делает сообщения неотрицаемыми для всех, кто видит историю: любой обладатель ключей истории может показать третьему лицу, что сообщение подписало устройство автора, а устройство подписано его ключом идентичности.
13. **Авторство под прежним ключом идентичности** (§6.2.6): клиент, никогда не видевший прежний ключ пользователя, доверяет истории ключей сервера. Подделать сообщение сервер всё равно не может — у него нет ключей истории, — но злонамеренный участник вместе с сервером может приписать сообщение вымышленному прежнему ключу. Клиенты, закрепившие прежний ключ, такую подделку видят. Key Transparency — v2.
14. **Сброс, скрытый сервером, у коммитера без единого наблюдения** (§6.3.9). При честном сервере коммитер без наблюдений закрывает поколения до сброса по истории ключей сервера (§6.3.7 п. 2). Остаётся случай, когда сервер **скрыл** сброс и из истории ключей, а у коммитера нет ни одного наблюдения пользователя под прежним ключом — он вошёл в группу, когда прежних листьев пользователя там уже не было, не видел подписанных им сообщений, не закреплял его ключ и не получал `SegmentReset` с ним. В больших каналах с ленивой подгрузкой истории такие коммитеры — не редкость. Тогда при включённой истории новое устройство получит открытую часть цепочки — то же, что любой новый участник канала; при выключенной — ничего, потому что вход без других листьев — разрыв `break_new_member`. Получатели, видевшие прежний ключ в любом сегменте, такой commit отвергнут (нет `break_reset`, §6.3.3), но **отказ не отзывает уже выданные связку и мост**: история к этому моменту уже у устройства.
15. **Мост — от коммитера** (§6.3.7): сегменты, которых у коммитера нет, в мост не попадут — потеря доступности истории, не конфиденциальности. Поэтому коммитером при Add предпочтительно назначается устройство того же пользователя (§2.6).
16. **Сообщения спорной эпохи** (§6.3.10): отправленные во время проверки под поколением, начатым спорным commit-ом, читают применившие его и будущие входящие, которым этот сегмент отдаст мостом коммитер с его ключом. Устройства, бывшие в группе и commit не применившие, их не прочитают; окно — не дольше проверки.
17. **Тип разрыва цепочки — метаданные** (§6.7): сервер узнаёт, кто вошёл при выключенной истории и чей ключ идентичности сменился.
18. **Сброс ключей по одному паролю** (§3.6, §6.3.9). Если устройства жертвы не были в сети 30 дней (тогда сброс без задержки) или предупреждение за 24 ч пропущено, тот, кто знает только пароль, применит сброс: прежние устройства удаляются, блоб восстановления удалён, ключ идентичности сменился — ключ восстановления жертвы больше ничего не открывает, а новое устройство истории до сброса не получит. Историю на руках у жертвы сохраняет только её устройство, удалённое сбросом, при ответе «Нет» (§3.7) — на чтение. Вернуть прежний ключ идентичности с такого устройства — идея на после 1.0. Обратная сторона (повторное ревью безопасности, №16): устройство, удалённое сбросом, больше не стирает себя само — вор, у которого такое устройство с исходным клиентом, ответит «Нет» и сохранит базу на чтение. Отметки «потеряно» в «Начать заново» не будет (ответ владельца OPEN-QUESTIONS №18): её поставил бы и тот, кто знает только пароль, и снова стёр бы историю жертвы. Вор и так держит устройство с его данными, а изменённый клиент не стирает себя и при обычном удалении. Принятое ограничение.
19. **Подделка истории задним числом после кражи ключей** (§6.2.5–§6.2.6). Вор, у которого есть ключ подписи удалённого устройства, ключи истории его времени и seed, вместе с сервером может вставить в старые поколения «подлинные» сообщения от имени этого устройства: `created_at` и `removed_at` — поля сервера. Принятое ограничение. Без сервера участник может сдвинуть своё сообщение в прошлое ленты не дальше окна `id` — 30 сут (§6.2.8).
20. **Раздвоение сообщения отправителем вместе с сервером** (ревью Б-Н3). Шифр конверта не привязан к ключу сообщения, и отправитель вместе с сервером может показать разным читателям разный подписанный текст под одним `id`. Привязка к ключу этого не закрыла бы: отправитель и так может подписать два разных конверта с одним `id`, а сервер — раздать их разным читателям. Жалоба с подписанным фрагментом (ARCHITECTURE §8) остаётся доказательством авторства того, что видел жалующийся. Принятое ограничение.
21. **Медиа без аутентификации отправителя внутри группы** (ревью Б-Н8). Ключ медиа каждого отправителя выводит любой участник группы звонка (§5.2), поэтому участник вместе с сервером или SFU может публиковать кадры под чужой идентичностью. От посторонних медиа защищено; удалённый может вставлять кадры под ключом прежней эпохи ещё `MEDIA_KEY_HOLD` (500 мс) после commit-а со своим удалением, а вместе с SFU — под чужой идентичностью (повторное ревью безопасности, №14). Подписи кадров в 1.0 нет. Принятое ограничение.

## 9. Публичный API crypto-core

Контракт для B3. Привязки: napi-rs для Electron, uniffi для мобильных (ADR-0016 п. 5). Общие правила:
- все функции — методы объекта `Core`, открытого над локальной базой (§7.4); состояние MLS и ключи живут в базе, наружу не выходят;
- `authenticated_data` и прочий контекст передаются параметрами каждого вызова, без состояния в группе (ADR-0018);
- секреты, которые всё же выходят наружу (ключ восстановления для показа, ключи медиа), — в обнуляемых буферах; у объектов с ключами нет отладочного вывода; входные буферы из FFI копируются;
- сеть crypto-core не трогает: функции возвращают блобы и запросы, клиент отправляет их по REST и gateway;
- ошибки — стабильные коды без фрагментов входа.

**Коды ошибок:** `INVALID_INPUT` (разбор, формат, неизвестная версия), `SIGNATURE_INVALID`, `DECRYPT_FAILED`, `KEY_UNAVAILABLE{generation}` (нет ключа истории — «ждём ключ»), `POLICY_VIOLATION{reason}` (`reason` — значение `DisputeReason`, клиент подаёт с ним жалобу, §2.9), `STATE_MISSING` (нужен возврат, §2.11.2), `EPOCH_MISMATCH`, `DUPLICATE` (повтор уже обработанного), `RECREATION_LIMIT` (§2.10.8), `VERIFICATION_FAILED` (обязательство, картинки, передача — §3.4), `RECOVERY_KEY_INVALID{checksum}` (§3.5), `STORAGE`, `INTERNAL`.
