## 0. Соглашения

### 0.1 Нотация

Структуры, которые разбирают и клиент (Rust), и DS (Go), записаны на языке представления TLS в том виде, в каком его использует RFC 9420 §2.1: целые — big-endian, векторы `<V>` — с длиной в формате переменной длины RFC 9420 §2.1.2. **Правило проекта:** длина вектора кодируется минимальным числом байтов; разборщик отвергает неминимальную запись, лишние байты в конце структуры и неизвестную `version`. Одна и та же грамматика реализуется в Go и в Rust и проверяется общими тестовыми векторами (T10).

### 0.2 Идентификаторы

`user_id`, `device_id`, `channel_id`, `group_id` в REST и gateway — UUIDv7 строкой в нижнем регистре (ADR-0017). Внутри криптографических структур этого документа и в MLS `group_id` — **16 байт двоичного UUID** (RFC 9562). Перевод строки в байты принимает только каноническую строку из 36 символов в нижнем регистре; всё остальное — ошибка разбора. Сравнение идентификаторов — побайтное.

### 0.3 Метки и подписи приложения

Каждый вывод ключа, MAC, хэш и подпись проекта несёт метку `"bebeberloga/v1 " + назначение` (ASCII). Метки разных назначений не совпадают; полный список — §10.

Подписи приложения (не MLS):

```text
struct {
    opaque label<V>;      // "bebeberloga/v1 " + Label
    opaque content<V>;
} AppSignContent;

AppSign(sk, Label, Content)        = Ed25519-Sign(sk, AppSignContent)
AppVerify(pk, Label, Content, sig) = Ed25519-Verify(pk, AppSignContent, sig)
```

Конструкция повторяет приём `SignWithLabel` из RFC 9420 §5.1.2, но с собственным префиксом: подпись проекта никогда не совпадает по входу с подписью MLS тем же ключом.

## 1. MLS-профиль

### 1.1 Версия и ciphersuite

MLS 1.0 (`mls10`), ciphersuite 0x0001, credential Basic — других значений клиент и DS не принимают (ADR-0004 п. 1). Библиотека — `openmls` 0.9.x с `openmls_rust_crypto` и `openmls_basic_credential`, версии закреплены точно (ADR-0016 п. 1).

### 1.2 Ключ подписи устройства

У каждого устройства один долгоживущий ключ подписи Ed25519: им подписаны его листья во всех группах, KeyPackage и подписи проекта от имени устройства. Открытая часть — `Device.signature_pubkey`. Ключ подписан ключом идентичности пользователя (cross-signing, ARCHITECTURE §4.2) — §1.3. Устройство не меняет ключ подписи, пока существует; новый ключ — это новое устройство (§3).

### 1.3 Credential

Basic credential (RFC 9420 §5.3) несёт в поле `identity` сериализацию:

```text
struct {
    uint8  version = 1;
    opaque user_id[16];
    opaque device_id[16];
    opaque identity_signature[64];
} DeviceCredential;                       // 97 байт

struct {
    opaque user_id[16];
    opaque device_id[16];
    opaque signature_key<V>;              // ключ подписи листа (32 байта)
} DeviceBindingContent;

identity_signature = AppSign(identity_sk, "device binding", DeviceBindingContent)
```

Те же 64 байта лежат в `Device.identity_signature` (REST). Ключ идентичности в credential не входит: клиент всё равно сверяет его с известным ему ключом пользователя.

**Проверка листа (`CredCheck`).** Клиент выполняет её для каждого нового листа — в Add-предложении сервера, в начальном commit-е новой группы, для каждого листа дерева из Welcome и при пересоздании группы (§1.7, §1.8, §2.10):

1. credential — Basic; `identity` разбирается как `DeviceCredential` версии 1 ровно в 97 байт;
2. `AppVerify(IK(user_id), "device binding", {user_id, device_id, leaf.signature_key}, identity_signature)` — где `IK(user_id)` — ключ идентичности, которому клиент доверяет для этого пользователя (§3: закреплён при первой встрече и сверяется с `User.identity_pubkey`; смена ключа — SCREENS/07 §8);
3. устройство принадлежит `user_id`, подтверждено и не удалено (`GET /users/{id}/devices`, события `DeviceRemoved` своих устройств);
4. пользователь вправе быть в группе: канал — право `channel.see` по данным сервера; ЛС — участник разговора; звонок — участник голосового канала;
5. `device_id` встречается в дереве не более одного раза.

Пункты 3–4 опираются на данные сервера — это принятая граница доверия: сервер — Authentication Service (ARCHITECTURE §4.3); подмену ключей пользователя ловит проверка кода безопасности (§4), в v2 — Key Transparency.

### 1.4 KeyPackage

| Поле | Значение |
|---|---|
| `version`, `cipher_suite` | `mls10`, 0x0001 |
| `init_key` | новый X25519 на каждый пакет |
| `leaf_node.encryption_key` | новый X25519 на каждый пакет |
| `leaf_node.signature_key` | ключ подписи устройства (§1.2) |
| `leaf_node.credential` | Basic с `DeviceCredential` (§1.3) |
| `leaf_node.capabilities` | versions `[mls10]`, cipher_suites `[0x0001]`, extensions `[0xF0B1]` (§1.6), proposals `[]`, credentials `[basic]` |
| `leaf_node.leaf_node_source` | `key_package`, `lifetime`: `not_before = now − 1 ч`, `not_after = not_before + 90 сут` |
| `leaf_node.extensions`, `extensions` | пусто (пакетов «последней надежды» нет) |

- Пакеты загружает **только подтверждённое устройство**: до подписи ключом идентичности credential неполон. DS отвечает неподтверждённому `DEVICE_UNVERIFIED`.
- DS при загрузке проверяет всё из ADR-0018 п. 4 (подписи, версия, ciphersuite, capabilities, расширения листа, верхняя граница срока, уникальность HPKE-ключей) и дополнительно: `DeviceCredential` разбирается, `device_id` — устройство, загружающее пакет, `signature_key` = `Device.signature_pubkey`, `identity_signature` проверяется действующим ключом идентичности пользователя, остаток срока ≥ `KP_MIN_REMAINING`. Ошибка — `INVALID_KEY_PACKAGE`.
- DS удаляет пакеты, остаток которых упал ниже `KP_MIN_REMAINING`, и все пакеты устройств пользователя при смене его ключа идентичности.
- Склад: клиент держит `KP_STOCK` = 100 пакетов и пополняет до 100, когда их меньше `KP_REFILL_BELOW` = 50 (`GET /devices/me/key-packages`); проверяет после `Ready`, после каждого принятого Welcome и раз в час в сети. Вход в сообщество расходует по пакету на каждую группу каналов, поэтому запас крупный. Если пакетов нет, вход ждёт пополнения (§2.7), а не завершается ошибкой.
- Приватные ключи пакета клиент хранит до его использования или до `not_after`, затем стирает.

### 1.5 Конфигурация группы

| Параметр (имя в openmls) | Значение | Почему |
|---|---|---|
| Политика формата (`wire_format_policy`) | `PURE_CIPHERTEXT` | handshake участников всегда зашифрованы (ADR-0016 п. 2) |
| Дерево в Welcome (`use_ratchet_tree_extension`) | `true` | новичку не нужен отдельный запрос дерева (ADR-0016 п. 2) |
| Прошлые эпохи (`max_past_epochs`) | 2 | сообщение, отправленное перед быстрой серией commit-ов, ещё расшифровывается; связь с чтением истории — §6 |
| Окно порядка (`sender_ratchet_configuration`) | `out_of_order_tolerance = 5`, `maximum_forward_distance = 1000` | значения по умолчанию openmls, проверены в S1 |
| Паддинг (`padding_size`) | §6 | зависит от формата сообщения (Р1) |
| Проверка срока листьев дерева при входе по Welcome | отключена (`JoinBuilder::skip_lifetime_validation`) | §1.8 |

Срок KeyPackage в Add-предложении при обработке commit-а openmls проверяет всегда, отключить нельзя (ADR-0018 п. 4) — на этом построен горизонт офлайна (§2.11).

### 1.6 Расширения GroupContext

Создатель группы задаёт ровно три расширения; после создания они не меняются, кроме замены ключа инстанса (§2.12).

1. **`external_senders`** — один элемент с индексом 0: ключ подписи DS инстанса (§2.12) и Basic credential с `identity = "bebeberloga/v1 instance"`. Клиент сверяет ключ с закреплённым ключом инстанса — при создании группы, при входе по Welcome и после каждого merge.
2. **`required_capabilities`** — extensions `[0xF0B1]`, proposals `[]`, credentials `[basic]`. Пакет без поддержки 0xF0B1 не войдёт в группу на уровне самой MLS.
3. **`group_binding`** (тип 0xF0B1, диапазон частного использования RFC 9420 §17.3) — привязка группы к каналу:

```text
struct {
    uint8  version = 1;
    opaque channel_id[16];
    uint8  kind;                      // 1 — чат канала (GROUP_KIND_CHAT), 2 — звонок (GROUP_KIND_CALL)
    opaque predecessor_group_id<V>;   // пусто или 16 байт: группа, которую эта заменяет (§2.10)
    uint64 predecessor_epoch;         // последняя согласованная эпоха предшественницы; 0, если её нет
    opaque continuity_tag<V>;         // пусто или 32 байта (§2.10.4)
} GroupBinding;
```

Привязка не даёт серверу выдать группу одного канала за группу другого и связывает пересозданную группу с предшественницей (§2.10). Значение `kind = 3` зарезервировано за личной группой пользователя (§6, решение Р5).

### 1.7 Политика клиента: что принимается

Клиент — Authentication Service для своих групп (ADR-0016 п. 3). Всё, что приходит от DS, недоверенное.

**Предложение от сервера — до постановки в очередь** (`store_pending_proposal`):
- отправитель — `External(0)`, ключ из `external_senders` = закреплённый ключ инстанса;
- тип — только Add или Remove; GroupContextExtensions, PSK, ReInit и любые другие — отвергаются;
- `authenticated_data` разбирается как `ProposalAAD` (§2.3);
- Add: `CredCheck` листа пакета (§1.3) и `ProposalAAD.device_id` = `device_id` из credential; если у устройства уже есть лист — Add допустим только вместе с Remove этого листа в одном commit-е (возврат, §2.11);
- Remove: на указанном листе стоит устройство `ProposalAAD.device_id`.

**Отвергается всегда:** предложение от `new_member_proposal` (ADR-0016 п. 3, находка S1 Б1), external commit (отправитель `new_member_commit`, ADR-0019), предложения участников по ссылке (в 1.0 участники предложений не шлют).

**Чужой commit — до merge** (`StagedCommit`):
- все предложения по ссылке — от `External(0)` и ранее прошли проверки выше;
- предложения по значению допустимы только в двух случаях: Add в начальном commit-е новой группы (эпоха 0 → 1, автор — создатель, каждый лист проходит `CredCheck`) и GroupContextExtensions замены ключа инстанса (§2.12);
- commit содержит все Remove, которые сервер опубликовал и которые клиент видел в этой эпохе (ADR-0016 п. 4);
- лист автора в UpdatePath и листья из Update сохранили credential и `signature_key` побайтно (находка S4 Б1);
- `RosterDelta` в `authenticated_data` совпадает с фактическим действием commit-а (§2.3), флаги — с фактическим содержимым;
- после merge хэш состава дерева (§2.5) равен `Handshake.roster_hash` от DS.

Нарушение любого пункта: клиент **не** применяет commit (`clear`/отказ от staged commit), подаёт жалобу (§2.9) и ждёт; группа для него в состоянии «ошибка ключей» (SCREENS/08 §8).

**Свой commit:** применяется (`merge_pending_commit`) только после явного подтверждения DS — ответа `201` или побайтного совпадения с тем, что пришло в потоке группы (ADR-0018 п. 5). Реакция на коды отказа — §2.13.

### 1.8 Вход по Welcome

1. Welcome приходит от DS (`MlsWelcome`, `GET /mls/welcomes`) с `channel_id`, `kind`, `epoch`, `seq`.
2. Обработка с отключённой проверкой срока листьев дерева. Причина: срок есть только у листьев, ни разу не обновлённых после Add (RFC 9420 §7.3 называет эту проблему), и участник, добавленный больше `KP_MIN_REMAINING` назад и не делавший commit-ов, иначе закрыл бы вход всем новичкам. Свежесть ключей листьев обеспечивает ротация эпох (§1.9), а срок KeyPackage в Add проверяется при commit-е.
3. `group_binding` есть, версия 1, `channel_id` и `kind` равны присланным DS; `external_senders` — закреплённый ключ инстанса; `required_capabilities` — как в §1.6.
4. `CredCheck` (§1.3) для каждого листа дерева.
5. Хэш состава дерева (§2.5) равен хэшу DS для этой эпохи (`GET /mls/groups/{id}` или `GET /mls/groups/{id}/roster?epoch=`).
6. Если `predecessor_group_id` не пуст — проверки пересоздания (§2.10.6).
7. После успеха — `DELETE /mls/welcomes/{group_id}` (подтверждение доставки, ADR-0018 п. 8). При отказе клиент в группу не входит и подаёт жалобу на commit `seq` с причиной (§2.9).

### 1.9 Ротация эпох

- **При смене состава** — каждый commit с Add или Remove открывает новую эпоху.
- **Плановая** — не реже раза в `ROTATION_PERIOD` = 24 ч на активной группе (в группе за последние 24 ч было хотя бы одно сообщение или handshake): DS шлёт `MlsUpdateRequested{REASON_SCHEDULED_ROTATION}` назначенному устройству (§2.6), оно делает commit без предложений с UpdatePath. Назначается устройство, чей последний commit в этой группе самый давний: так по очереди обновляются ключи листьев всех активных устройств.
- **Ручная** — «Обновить ключи канала» (`POST /channels/{id}/mls/rotate`, право `channel.edit`, SCREENS/06 §5.2) → `REASON_MANUAL`.
- Группы звонков следуют тем же правилам.

## 2. Delivery Service

### 2.1 Роль

DS упорядочивает handshake-сообщения по группе, хранит KeyPackage, Welcome и карту состава, подписывает Add и Remove как external sender, назначает коммитера, замораживает и сопровождает пересоздание группы.

DS **никогда** не создаёт commit, не получает ключей групп, не видит содержимого commit-ов и сообщений, не хранит и не публикует GroupInfo (ADR-0019). Ключ external sender DS применяет только для подписи Add и Remove (`PublicMessage`, RFC 9420 §6.2).

### 2.2 Что DS принимает

| Запрос | Требование | Отказ |
|---|---|---|
| `POST …/handshakes`, `kind = COMMIT` | `PrivateMessage`, `content_type = commit`, `group_id` и эпоха — текущие; отправитель — устройство из карты состава без ожидающего Remove; группа не заморожена | `EPOCH_MISMATCH`, `NOT_GROUP_MEMBER`, `REMOVAL_PENDING`, `GROUP_FROZEN`, `BAD_MESSAGE` и проверки §2.4 |
| `POST …/handshakes`, `kind = PROPOSAL` | в 1.0 участники предложений не шлют | `UNAUTHORIZED_CHANGE` |
| `POST …/handshakes`, `kind = EXTERNAL_COMMIT` | не используется (ADR-0019) | `EXTERNAL_COMMIT_UNSUPPORTED` |
| Любой `PublicMessage` от клиента | — | `BAD_MESSAGE` (а `new_member_commit` — `EXTERNAL_COMMIT_UNSUPPORTED`) |
| `POST /channels/{id}/messages` | `PrivateMessage` с `content_type = application` текущей эпохи группы канала (fail-closed для устаревших эпох — ADR-0018 «Последствия» для B05); формат — §6 | `EPOCH_MISMATCH`, `NOT_GROUP_MEMBER`, `GROUP_FROZEN` |

Повтор уже принятого commit-а (тот же блоб, эпоха на единицу меньше текущей) получает тот же ответ, что и первый, — и на быстром пути, и под блокировкой группы (ADR-0018 п. 5).

### 2.3 Грамматика `authenticated_data`

Обе структуры разбирают Go (DS) и Rust (crypto-core) по одной грамматике (§0.1).

```text
struct {
    uint8  version = 1;
    opaque device_id[16];             // кого добавляет Add / кто стоит на листе Remove
} ProposalAAD;                        // authenticated_data предложений сервера, под подписью DS

struct {
    uint32 leaf;
    opaque device_id[16];
} AddedLeaf;

struct {
    uint8     version = 1;
    uint8     flags;                  // бит 0 — заменён external_senders (§2.12); бит 1 — §6; остальные 0
    uint32    removed<V>;             // удалённые листья, строго по возрастанию
    AddedLeaf added<V>;               // добавленные листья в порядке применения
} RosterDelta;                        // authenticated_data каждого commit-а участника
```

- Индексы новых листьев детерминированы (RFC 9420 §12.1.1, §12.3): сначала применяются Remove, затем каждый Add занимает самый левый пустой лист или расширяет дерево вправо. Одна функция назначения листьев у автора, получателей и DS (S4).
- Порядок Add в commit-е задаёт openmls; автор строит дельту после сборки commit-а и сверяет её с фактическим (S4). AAD передаётся в crypto-core параметром каждого вызова, без состояния в группе (ADR-0018, `set_aad` «залипает»).
- Commit без изменений состава несёт `RosterDelta` с пустыми списками.
- DS проверяет `MAX_AAD` до блокировки группы.

### 2.4 Проверки commit-а

**DS** (ADR-0018 п. 2) отвергает commit, если:

| Проверка | Код |
|---|---|
| `authenticated_data` не разбирается как `RosterDelta` | `BAD_DELTA` |
| удаляемый лист пуст или для него нет опубликованного Remove | `UNAUTHORIZED_CHANGE` |
| в commit не вошли все опубликованные Remove | `PROPOSALS_MISSING` |
| листья добавленных устройств не те, что дают правила §2.3 | `BAD_DELTA` |
| для добавленного устройства нет опубликованного Add (кроме начального commit-а новой группы — там устройство должно быть допущено к каналу, а пакет зарезервирован этим создателем) | `UNAUTHORIZED_CHANGE` |
| Add устройства, у которого уже есть лист, без Remove этого листа | `BAD_DELTA` |
| превышен лимит листьев | `CHANNEL_MEMBER_LIMIT` |
| адресаты Welcome (по `KeyPackageRef`) не совпадают с добавленными устройствами, или пакет одного из них имеет остаток меньше `KP_MIN_REMAINING` | `BAD_WELCOME` |
| `flags` содержит неизвестный бит или бит 0 без запроса замены ключа инстанса | `BAD_DELTA` |

Принятый commit DS применяет к карте состава (§2.5), режет Welcome по адресатам (ADR-0018 п. 8) и рассылает `MlsHandshake` с `roster_hash`.

**Получатель** проверяет commit до merge по §1.7 и после merge — хэш состава.

### 2.5 Карта состава по эпохам

DS ведёт карту `лист → устройство` по дельтам и хранит её для каждой эпохи в пределах `HANDSHAKE_RETENTION` (достаточно журнала дельт). Хэш состава:

```text
struct {
    uint32 leaf;
    opaque device_id[16];
} RosterEntry;

struct {
    opaque      label<V> = "bebeberloga/v1 roster";
    opaque      group_id[16];
    uint64      epoch;
    RosterEntry entries<V>;           // все непустые листья по возрастанию leaf
} RosterHashInput;

roster_hash = SHA-256(RosterHashInput)
```

Клиент считает тот же хэш по своему дереву (`device_id` — из `DeviceCredential` каждого листа). Где он приходит от DS: `Handshake.roster_hash` для каждого commit-а (состав после него), `Group.roster_hash` (текущий), `GET /mls/groups/{id}/roster?epoch=` (полный список — для новичков, диагностики и пересоздания). Сверка — после каждого merge и после входа по Welcome (ADR-0018 п. 3). Несовпадение — жалоба `ROSTER_MISMATCH` (§2.9).

### 2.6 Назначенный коммитер

Commit делает одно устройство, которое называет DS (ADR-0018 п. 7): `MlsUpdateRequested{group_id, reason, designated_device_id, epoch}` уходит всем онлайн-устройствам группы, коммитит только названное. Остальные не коммитят, а ждут commit в потоке. Если commit этой эпохи не пришёл за `COMMIT_DESIGNATION_TIMEOUT` = 3 с, DS назначает следующего кандидата новым событием. Это уточняет ADR-0018 п. 7: вместо свободной гонки по таймауту — повторное назначение, чтобы десятки онлайн-участников не собирали commit впустую.

Порядок кандидатов (онлайн — есть открытая сессия gateway):

1. **Add нового устройства D пользователя U после подтверждения** — устройство U, подтвердившее D (`POST /devices/{D}/verify`), если оно в группе и в сети: оно состоит во всех группах U, и новое устройство подключается сразу (FLOWS/02 ш. 4.4). Затем — другие устройства U в группе и в сети.
2. **Возврат устройства D пользователя U** (§2.11) — другие устройства U в группе и в сети.
3. **Пересоздание** — §2.10.4.
4. **Во всех остальных случаях и после исчерпания пп. 1–2** — устройства группы в сети, без ожидающего Remove, не участники открытой жалобы (§2.9); по возрастанию времени своего последнего commit-а в этой группе, затем по возрастанию `leaf`.

Устройство, не уложившееся в таймаут, уходит в конец очереди на 10 минут. Создатель новой группы канала (новый канал, ЛС, первый вход в звонок) делает её начальный commit без назначения; создателя при пересоздании назначает DS (§2.10.4).

Новое устройство загружает KeyPackage только после подтверждения (§1.4), поэтому DS публикует его Add, как только пакеты появятся (§2.7); подтвердившее устройство получает назначение в тот же момент.

### 2.7 Add

- **Публикация** — «фронт + батч» (ADR-0018 п. 6): заявка в группе без ожидающих Add публикуется сразу; пока Add ждут commit-а, заявки копятся и уходят пачкой до `MAX_BATCH` = 100 сразу после commit-а; тик `BATCH_TICK` = 1 с — страховка.
- **Пакет** — пакет устройства с самым поздним `not_after`, остаток ≥ `KP_MIN_REMAINING`.
- **Ожидание без срока.** Если в группе никого нет в сети, эпохи не идут и `MAX_ADD_EPOCHS` не срабатывает. Заявка на вход ждёт сколько угодно и снимается **только при потере доступа**: пользователь потерял `channel.see`, вышел, выгнан или забанен, устройство удалено, канал удалён.
- **Свежесть пакета по времени.** Тик DS проверяет пакет каждого ожидающего Add: когда остаток падает ниже `KP_REFRESH_AT` = 32 сут, DS резервирует свежий пакет устройства и публикует Add заново (старое предложение в очередях участников остаётся, но участник его отбросит фильтром, §1.7, а DS не примет Welcome по нему, §2.4). Если свежих пакетов нет — заявка ждёт загрузки (`awaiting_key_package`) и публикуется сразу после неё.
- **Эпохи без включения.** Если опубликованный Add не вошёл в commit за `MAX_ADD_EPOCHS` = 20 эпох (участники его отбрасывают), DS заменяет пакет другим пакетом устройства, а не снимает заявку; нет других — ждёт загрузки.
- **Отмена опубликованного Add** — DS принимает commit, Welcome не выдаёт и сразу публикует Remove нового листа (ADR-0018 п. 6).
- **Предложения по значению** — только в начальном commit-е новой группы (§2.4).
- **Фильтр коммитера** — перед commit-ом клиент выбрасывает Add с негодным пакетом (ADR-0018 п. 4: остаток < `KP_MIN_REMAINING`, capabilities, расширения листа, совпадения ключей подписи и HPKE, в том числе перекрёстные) и коммитит остальное; при отказе openmls находит виновника точно (требование B03).

### 2.8 Remove

- Публикуется сразу, без батча; повторяется в каждой новой эпохе, пока commit не включит его в `RosterDelta`.
- С момента публикации DS не доставляет устройству новых сообщений и удаляет его недоставленные Welcome (S4 Н2); commit от устройства с ожидающим Remove — `REMOVAL_PENDING`; commit без опубликованного Remove — `PROPOSALS_MISSING`.
- Честные клиенты не применяют commit без объявленного Remove (§1.7) и жалуются (§2.9) — это и есть сигнал, на который опирается факт удаления (ADR-0018 п. 2).
- **Подтверждение.** Remove из commit-а эпохи E → E+1 считается выполненным, когда (а) устройство пользователя, отличного от автора commit-а, отправило application-сообщение или commit в эпохе ≥ E+1 и жалобы на этот commit нет, или (б) прошло `REMOVE_CONFIRM_WINDOW` = 24 ч без жалобы. До подтверждения повторный вход удалённого устройства получает `CONFLICT` (S4 Н4), кроме пары Remove + Add возврата (§2.11). Жалоба на commit отменяет «выполнено» и ведёт к пересозданию, где устройство исключено из состава (§2.10.3).

### 2.9 Жалоба на commit

Клиент подаёт жалобу, когда не может принять commit другого участника на своей текущей эпохе по причине из таблицы, или когда Welcome не прошёл проверки §1.8:

`POST /mls/groups/{group_id}/disputes {seq, reason}` → `202`.

| `reason` | Что не так |
|---|---|
| `DISPUTE_REASON_DELTA_MISMATCH` | `RosterDelta` не совпадает с действием commit-а или флагами |
| `DISPUTE_REASON_MISSING_REMOVE` | нет объявленного сервером Remove |
| `DISPUTE_REASON_UNAUTHORIZED_ADD` | Add не прошёл `CredCheck` или не от сервера |
| `DISPUTE_REASON_LEAF_CREDENTIAL_CHANGED` | UpdatePath или Update сменили credential или ключ подписи листа |
| `DISPUTE_REASON_FORBIDDEN_PROPOSAL` | GroupContextExtensions (кроме §2.12), PSK, ReInit, ExternalInit, предложение участника |
| `DISPUTE_REASON_UNDECRYPTABLE` | клиент обработал все предыдущие handshake группы, а commit его эпохи не расшифровывается или не проходит проверки MLS («мусорный commit», ADR-0016 п. 4) |
| `DISPUTE_REASON_ROSTER_MISMATCH` | состав после merge или из Welcome не совпадает с картой DS |
| `DISPUTE_REASON_BINDING_MISMATCH` | `group_binding`, `external_senders` или `required_capabilities` не те |
| `DISPUTE_REASON_KEY_PACKAGE_EXPIRED` | срок пакета в Add истёк, хотя commit моложе `HORIZON` |
| `DISPUTE_REASON_RECREATION_INVALID` | новая группа не прошла проверки §2.10.6 |

- **Жалоба или возврат.** Если клиенту не хватает состояния — пропуск в журнале, срок пакета в commit-е старше `HORIZON`, потерянная локальная база, — это не жалоба, а запрос возврата (§2.11).
- **DS принимает жалобу**, если подавшее устройство было в карте состава в базовой эпохе commit-а (или адресат Welcome этого commit-а), не является автором, не имеет ожидающего Remove и не превысило `DISPUTE_RATE`. Иначе — `NOT_GROUP_MEMBER`, `REMOVAL_PENDING` или `RATE_LIMITED`.
- **Действие DS:** заморозить группу и начать пересоздание (§2.10) в пределах `RECREATION_LIMIT`. DS не решает, кто прав: пересоздание безопасно при любом исходе, потому что новичков в новой группе проверяют все (§2.10.6).
- **Злоупотребление.** Любой участник может вызвать пересоздание, но не чаще лимитов. DS записывает жалобы с устройствами в журнал инстанса; ответ модерации — исключить участника. Это принятый риск доступности, не конфиденциальности (§8).

### 2.10 Пересоздание группы

Единственный способ устранить рассинхрон в 1.0 (ADR-0019 п. 5). Канал получает новую MLS-группу с новым `group_id`; история продолжается, потому что ключи истории принадлежат каналу (ADR-0015, §6).

#### 2.10.1 Когда

- DS принял жалобу (§2.9);
- DS потерял хвост журнала группы (восстановление из резервной копии) — замораживаются все затронутые группы.

Других поводов нет: DS не пересоздаёт группу по своей инициативе и не чаще `RECREATION_LIMIT` (§2.10.8). Группы звонков пересоздаются той же процедурой, без `continuity_tag` (у звонка нет ключей истории).

#### 2.10.2 Заморозка

DS в одной транзакции под блокировкой строки группы:
- ставит `Group.state = GROUP_STATE_FROZEN`;
- фиксирует последнюю согласованную эпоху `E_a`: базовая эпоха спорного commit-а, а при потере журнала — последняя эпоха в журнале;
- перестаёт принимать handshake и сообщения (`GROUP_FROZEN`) и публиковать предложения;
- рассылает членам группы `MlsGroupFrozen{group_id, channel_id}`.

Клиенты показывают `Banner` «Не можем зашифровать: ждём обновления ключей канала…», поле ввода неактивно (SCREENS/08 §8). История читается — ключи истории у клиентов есть. Очередь неотправленных копится локально (§2.11.4).

#### 2.10.3 Целевой состав

DS вычисляет целевой состав `R` новой группы:

```text
R = карта(E_a)
  − устройства, для которых опубликован Remove (ожидающий в E_a или любой после E_a, включая «выполненный» спорным commit-ом)
  − устройства с отменённым входом
  − устройства, чьи пользователи потеряли доступ к каналу, и удалённые устройства
  + устройства с действующей заявкой на вход (включая добавленные спорным commit-ом)
```

**Инвариант I11:** устройство с опубликованным Remove или отменённым входом в старой группе не входит в начальный состав новой. Изменения спорного commit-а, кроме этого правила, отбрасываются: его Remove выполняются (устройства не попадают в `R`), его Add снова становятся заявками.

#### 2.10.4 Кто создаёт новую группу

DS назначает создателя `MlsUpdateRequested{REASON_RECREATE, designated_device_id}`: устройство из `R`, бывшее в карте в эпохе `E_a`, в сети, принадлежащее пользователю, отличному от автора спорного commit-а; в первую очередь — подавшее жалобу. Нет ответа за `RECREATE_DESIGNATION_TIMEOUT` = 30 с — следующий кандидат. Нет кандидатов в сети — группа ждёт в заморозке, пока кто-то из них не появится.

Создатель:

1. `GET /mls/groups/{old}/recreation` → `RecreationPlan{old_group_id, channel_id, kind, last_agreed_epoch, history_key_generation, target_device_ids[]}`.
2. `POST /mls/groups/{old}/recreation/key-packages` → по одному зарезервированному пакету на каждое устройство из `R`, кроме себя; `exhausted_device_ids` — у кого пакетов нет.
3. Проверяет каждый пакет: `CredCheck` (§1.3) и фильтр коммитера (§2.7). Негодные и отсутствующие пакеты не мешают: такие устройства станут заявками в новой группе.
4. Генерирует новый `group_id` (UUIDv7) и создаёт группу с расширениями §1.6: `group_binding{channel_id, kind, predecessor_group_id = old, predecessor_epoch = E_a, continuity_tag}`, где

   ```text
   struct {
       opaque label<V> = "bebeberloga/v1 recreation";
       opaque channel_id[16];
       opaque predecessor_group_id[16];
       uint64 predecessor_epoch;
       opaque group_id[16];
   } ContinuityInput;

   continuity_tag = HMAC-SHA256(K_g0, ContinuityInput)
   ```

   `K_g0` — ключ истории канала поколения `RecreationPlan.history_key_generation`, действовавшего в эпохе `E_a` (§6); его имеет каждый участник канала того времени, а у DS его нет. Тег доказывает, что новую группу создал участник канала, а не сервер. Для групп звонков тег пуст.
5. Собирает **один** commit, добавляющий всех из `R` с годными пакетами (предложения по значению), с `RosterDelta` и Welcome.
6. `POST /mls/groups {channel_id, kind, group_id, ciphersuite, predecessor_group_id, initial_commit, welcomes[], history_key_bundle}` — одним запросом, атомарно.
7. `201` → применяет свой commit. `GROUP_FROZEN` с `successor_group_id` — группу уже создал другой; свою выбрасывает. Другой отказ — выбрасывает и ждёт нового назначения.

#### 2.10.5 Ровно одна новая группа на канал

DS обрабатывает `POST /mls/groups` с `predecessor_group_id` в одной транзакции:
1. блокирует строку старой группы (`FOR UPDATE`);
2. проверяет: группа заморожена, преемника нет, запрашивающее устройство — из `R` и было в карте в `E_a`. Если преемник уже есть — `GROUP_FROZEN{successor_group_id}`;
3. проверяет начальный commit: `PrivateMessage` эпохи 0 новой группы от листа 0 = запрашивающего устройства; `RosterDelta.removed` пуст; добавленные устройства ⊆ `R`; адресаты Welcome — ровно добавленные устройства по пакетам, зарезервированным в п. 2 §2.10.4 (`BAD_WELCOME`); лимит листьев;
4. создаёт новую группу в эпохе 1 с картой состава, ставит старой `GROUP_STATE_SUPERSEDED` и `successor_group_id`, переключает `Channel.mls_group_id`;
5. удаляет заявки и недоставленные Welcome старой группы; устройства из `R`, не вошедшие в начальный commit, становятся заявками на вход в новую группу и публикуются сразу (§2.7).

После фиксации DS рассылает `MlsGroupFrozen{group_id = old, successor_group_id}` членам старой группы, `MlsWelcome` адресатам и `ChannelUpdated` видящим канал. Два одновременных создателя не создают двух групп: второй получает `GROUP_FROZEN` с преемником.

#### 2.10.6 Как клиент проверяет законность новой группы

Перед тем как войти по Welcome в группу с непустым `predecessor_group_id`, клиент проверяет всё из §1.8 и дополнительно:

1. **Привязка к каналу.** `group_binding.channel_id` = канал, `kind` = роль группы; `predecessor_group_id` = группа, которую клиент знает для этого канала (если знает); DS показывает её `SUPERSEDED` с `successor_group_id` = эта группа.
2. **Точка согласия.** Текущая эпоха клиента в старой группе ≤ `predecessor_epoch` + 1: новая группа не может отменить commit-ы, которые клиент уже принял сверх спорного.
3. **Тег непрерывности.** Если у клиента есть `K_g0`, `continuity_tag` проверяется; если тег пуст у группы чата или не сходится — отказ. Новое устройство без `K_g0` полагается на остальных.
4. **Состав.** `CredCheck` каждого листа; хэш состава = хэш DS для эпохи 1 новой группы.
5. **Удалённые не вернулись** (I11 на клиенте). Ни один лист не принадлежит устройству, для которого клиент видел опубликованный сервером Remove в старой группе (ожидающий или включённый в commit), и удалённому устройству из `GET /users/{id}/devices`.
6. **Новые лица видны.** Устройства, которых не было в последнем известном клиенту составе старой группы, считаются добавленными: для них — та же политика и те же уведомления в интерфейсе, что для обычного Add (SCREENS/07 §8). Пересоздание не может тихо добавить устройство.
7. **Лимит частоты** — §2.10.8.

Отказ по пп. 1–6 — жалоба `DISPUTE_REASON_RECREATION_INVALID` на новую группу; клиент в неё не входит и остаётся в состоянии «ошибка ключей». После входа клиент удаляет состояние старой группы, ключи истории сохраняет.

#### 2.10.7 Старая группа

- `GROUP_STATE_SUPERSEDED`: DS отвергает в неё handshake и сообщения (`GROUP_FROZEN` с `successor_group_id`) и больше не публикует в ней предложений.
- Предложения сервера из старой группы в новой недействительны: подпись external sender покрывает `group_id` и эпоху (RFC 9420 §6.1), DS их не переносит, клиент очищает очередь вместе со старым состоянием.
- Сообщения, уже сохранённые на сервере, остаются и читаются по ключам истории (§6). Что с сообщениями, отправленными в спорной эпохе теми, кто принял спорный commit, — §6.

#### 2.10.8 Лимит частоты

`RECREATION_LIMIT`: не больше одного пересоздания канала в час и трёх за скользящие 24 ч.

- **DS** не начинает пересоздание сверх лимита: группа остаётся замороженной до освобождения окна.
- **Клиент** ведёт свой журнал принятых пересозданий по каналу и не входит в новую группу сверх лимита, даже если DS её создал. Это защищает от сервера, который пересоздаёт группу раз за разом. Welcome клиент хранит и обрабатывает, когда окно освободится.
- **Что видит пользователь при превышении:** то же, что в заморозке, — `Banner` «Не можем зашифровать: ждём обновления ключей канала…» и неактивное поле ввода (SCREENS/08 §8); история читается; очередь неотправленных ждёт.

#### 2.10.9 Цена при 5 000 листьях

Оценка по замерам S1 и S4. Размер листа с credential проекта — около 270 байт: в спайках лист занимал около 180 байт, credential проекта на ~90 байт длиннее.

| Что | Оценка | Источник |
|---|---|---|
| Начальный commit (4 999 Add по значению по ~380 байт + `RosterDelta` ~100 КБ) | ~2 МБ (меньше лимита handshake 4 МиБ) | KeyPackage 280 байт в S1 + credential |
| Welcome на одно устройство (дерево целиком) | 1–1,4 МБ (больше лимита события 256 КиБ — новички берут его через REST) | 100–180 байт на лист (S4, S1) + credential |
| Исходящий трафик DS на всех адресатов | 5–7 ГБ | 5 000 × размер Welcome |
| Сборка commit-а у создателя | ~1,3 с + ~0,8 с на проверку пакетов | 250 мс на 1 000 Add (S4), 0,16 мс на Add (S4) |
| Обработка Welcome у адресата | ~0,13 с на десктопе, до ~1,5 с на телефоне | ~25 мкс на лист (S4) |

Отсюда лимит частоты и правило «пересоздание только по жалобе». Отдельная раздача дерева уменьшила бы Welcome (ADR-0016 «Альтернативы»), но не общий объём: дерево нужно каждому.

### 2.11 Горизонт офлайна и возврат устройства

#### 2.11.1 Горизонт и срок KeyPackage

Получатель commit-а с Add проверяет срок пакета по своим часам в момент обработки (§1.5). DS гарантирует, что у каждого пакета в принятом commit-е остаток ≥ `KP_MIN_REMAINING` (§2.4, §2.7). Значит, устройство, обработавшее поток группы не позже чем через `KP_MIN_REMAINING` после commit-а, этот commit примет. Commit-ы, которые устройство пропустило, сделаны не раньше его последнего подключения. Отсюда:

```text
HORIZON = KP_MIN_REMAINING − 1 сут (запас на расхождение часов) = 30 сут
```

Устройство, отсутствовавшее меньше `HORIZON`, догоняет поток как обычно: DS хранит handshake и карту состава `HANDSHAKE_RETENTION` ≥ 31 сут.

#### 2.11.2 Кто применяет критерий

- **DS (основной).** При `Identify` новой сессии: если `now − Device.last_seen_at ≥ HORIZON` (`last_seen_at` — последняя аутентифицированная активность устройства), устройство «возвращается». `Ready.device_returning = true`; во всех группах устройства `MlsPending.returning = true`. DS публикует в каждой группе пару: Remove старого листа и Add со свежим пакетом (`ProposalAAD.device_id` одинаковый). Если у устройства пока нет свежих пакетов (DS удалил устаревшие), пара публикуется сразу после загрузки.
- **Клиент (запасной).** Если клиент не может обработать поток группы из-за нехватки состояния — `GET …/handshakes?after_seq=` вернул первый `seq` больше ожидаемого (журнал обрезан), срок пакета в commit-е старше `HORIZON` истёк, локальная база потеряна или восстановлена из копии, — он не пытается дальше и шлёт `POST /mls/groups/{id}/resync` (`RESYNC_RATE`). DS публикует ту же пару для этой группы.

Для неудачи на commit-е моложе `HORIZON` при полном состоянии клиента — жалоба, а не возврат (§2.9).

#### 2.11.3 Что делает возвращающееся устройство

1. Получив `device_returning`, клиент **не обрабатывает** старые handshake групп с `returning`. Их MLS-состояние он стирает; ключи истории и локальную историю сохраняет.
2. Сразу загружает свежие пакеты (§1.4).
3. Показывает в этих каналах «Подключаемся к каналу…» (SCREENS/08 §1, §8; FLOWS/02 «Возвращение после долгого перерыва»).
4. Входит по Welcome с проверками §1.8 и догружает пропущенную историю по ключам истории (§6).

Пара Remove + Add — одна операция DS «возврат»: Remove не заменяет заявку устройства на вход (в отличие от обычного Remove, S4), коммитер включает обе части в один commit (§1.7, §2.4), блокировка повторного входа до подтверждения Remove (§2.8) к ней не применяется. Коммитер — предпочтительно другое устройство того же пользователя (§2.6).

#### 2.11.4 Очередь неотправленных

Сообщения из очереди (FLOWS/06 ш. 4, FLOWS/02 «Возвращение» ш. 3) **шифруются в момент отправки, а не при постановке в очередь.** `id` (UUIDv7) присваивается при наборе, как в FLOWS/06 ш. 1; до отправки текст лежит в локальной зашифрованной базе (§7). Причины:
- к моменту отправки эпоха, ключ истории и даже группа канала могут смениться (возврат, пересоздание, ротация);
- шифртекст, собранный заранее, всё равно пришлось бы перешифровывать;
- открытый текст в очереди защищён так же, как вся локальная история.

Повтор после `EPOCH_MISMATCH` (FLOWS/06 ш. 4) тоже шифрует заново на текущей эпохе.

### 2.12 Ключ external sender инстанса

- **Закрепление.** Клиент получает ключ из `GET /instance` (`InstanceInfo.external_sender_key`) при первом входе на инстанс и закрепляет его вместе с адресом инстанса. Дальше он принимает только этот ключ или ключ, связанный с ним цепочкой замен.
- **Замена.** Новый ключ публикуется с записью `ExternalSenderKeyRotation{old_key, new_key, signature}`, где `signature = AppSign(old_sk, "external sender rotation", {old_key, new_key})`. `InstanceInfo.external_sender_rotations[]` — цепочка от первого ключа инстанса. Клиент проверяет цепочку от закреплённого ключа и закрепляет новый.
- **Перевод групп.** Клиент отвергает GroupContextExtensions от сервера (§1.7), поэтому группу переводит участник: DS шлёт назначенному устройству `MlsUpdateRequested{REASON_EXTERNAL_SENDER_ROTATION}`, оно делает commit с GroupContextExtensions по значению, где `external_senders = [новый ключ]`, а остальные расширения побайтно прежние, и ставит бит 0 в `RosterDelta.flags`. Получатели принимают такое предложение, только если бит стоит, меняется только `external_senders` и новый ключ связан цепочкой с закреплённым. DS по биту знает, что группа переведена, и дальше подписывает её предложения новым ключом.
- Пока группа не переведена, DS подписывает её предложения старым ключом; неактивные группы переводятся при первой активности. Старый закрытый ключ DS хранит, пока есть непереведённые группы.
- Загрузчик ключа DS отвергает известный тестовый ключ спайка S4 (ADR-0018). Хранение ключа и команда замены — B05 и B16.
- Компрометация ключа инстанса позволяет подписать замену; защита от этого — вне 1.0 (Key Transparency, ARCHITECTURE §4.10).
