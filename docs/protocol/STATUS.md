## Форма REST и состав Ready

- **REST.** Ресурсы — сущности GLOSSARY (`community`, `channel`, `role`, `invite`, `sound` …) в том виде, в каком их вводят FLOWS. Действия участника сообщества (выгнать, бан, роли) — подресурсы сообщества, потому что PERMISSIONS проверяет их правами уровня «Сервер» (§1, колонка «Уровень»); действия с содержимым канала (сообщения, закрепы, read-state, доступ, голос) — подресурсы канала, потому что права уровня «Канал» и состав MLS-группы привязаны к каналу. ЛС — тоже канал, чтобы история и закрепы адресовались одинаково. Методы — по семантике HTTP: `PUT/DELETE` для идемпотентных состояний (закреп, бан, блокировка), `POST` для команд (вступить, передать владение, mute по ответу владельца №4). Других источников формы нет.
- **Ready.** Состав выведен из того, что нужно экранам SCREENS/01–03 и 09 до первого REST-запроса: колонка «Зачем сразу» в `GATEWAY.md §3` даёт обоснование каждого поля. Всё, что открывается по действию пользователя (участники, история, приглашения, баны, звуки), в `Ready` не входит.

## Технические допущения (не из спецификации, можно пересмотреть)

- Серверный mute/deafen — `POST /channels/{id}/voice/members/{uid}/mute|deafen` с телами `{server_mic_off}` / `{server_sound_off}` + событие `VoicePresenceChanged` (OPEN-QUESTIONS №4, ответ владельца).
- Опрос статуса подтверждения email до входа — `GET /auth/register/status?registration_token=…`; FLOWS/01 ш. 4 допускает «событие или опрос», событий до входа нет.
- Повторный запрос подтверждения устройства после 10 минут — `POST /devices/me/verification/request`.
- Обмен коммитментами при подтверждении устройства — REST `POST /devices/{id}/verification/messages` → событие `DeviceVerificationMessage`; содержимое непрозрачно, формат задаёт B2.
- Сообщения о новых и удалённых устройствах и смене ключей создаёт клиент владельца устройства как зашифрованное сообщение `DeviceNoticeBody`; сервер чужим пользователям `DeviceAdded/Removed` не рассылает.
- `broadcast_mention` (`@все`/`@здесь`) передаётся открыто — иначе сервер не может проверить `chat.ping_all` и посчитать бейджи. Хинты ролей — `HMAC(секрет канала, role_id)`, каждый участник регистрирует хинты своих ролей `PUT /channels/{id}/mention-hints` (заменено B02: ключ HMAC — подключ поколения ключа истории, CRYPTO.md §6.4).
- `DeleteBody`/`PinBody` в группе дублируют REST-команды для офлайн-истории; модератор без текста удаляет только через REST; «убрать реакции у всех» — удаление сообщений-реакций по id.
- Незавершённое создание сообщества (FLOWS/03 ш. 5): клиент вызывает `DELETE /communities/{id}`; сервер дополнительно удаляет сообщества, у каналов которых за 1 час не появилось ни одной MLS-группы.
- ЛС — `Channel` типа `CHANNEL_TYPE_DM` с `participant_ids`, адресуется теми же `/channels/{id}/…`; `POST /users/me/dm-channels` идемпотентен для пары.
- Commit, Welcome и связка ключей истории идут одним запросом `POST /mls/groups/{id}/handshakes` (атомарно); GroupInfo не передаётся (ADR-0019).
- «🔒 закрытый для тебя»: владелец и администраторы получают `CommunitySnapshot.locked_channels` и событие `LockedChannelsUpdated`; самодобавление — `POST /channels/{id}/access/self`, участники канала видят системное сообщение `KIND_CHANNEL_SELF_JOINED`.
- «Тебя выгнали» после долгого офлайна: сервер хранит `CommunityRemoval` до подтверждения устройством (`Ready.community_removals`, `DELETE /users/me/community-removals/{community_id}`).
- Состояние «подключается» в голосе — `VoicePresence.connecting`: true после `voice/join`, false после подтверждения от медиасервера (webhook).
- Push-endpoint (S) — `PUT/DELETE /devices/me/push-endpoint`, реализация после 1.0.
- `PresenceSubscribe` — одно сообщество на соединение; присутствие участников сообщества приходит только для открытого сообщества, друзей — всегда.
- `PRESET_ROLE_IMMUTABLE` — отдельный код для попытки удалить или переименовать пресет (PERMISSIONS §2, SCREENS/11 §4.2); можно было бы обойтись `CONFLICT`, но клиенту нужен точный текст.
- Чужие устройства в профиле (`GET /users/{id}/devices`) отдаются как `PublicDevice` без города, времени входа и версии клиента.

## Технические решения B02 (в рамках ADR)

- Правила таблицы переходов `CRYPTO.md` §2.14, которых нет в ADR и которые не меняют поведения для пользователя: штраф «в конец очереди на 10 минут» — во всех группах и на пользователя; повтор принятого commit-а получает ответ первого раза в любом состоянии (e0); в группе-преемнике назначаются только создатель и принявшие Welcome; при ожидающем Remove — два кандидата разных пользователей; `R₀` сверяется на момент `POST /mls/groups`.
- `PERSONAL_RESTORE` после упрощения — только для устройства, восстановленного ключом восстановления, когда других устройств нет; личная группа, которую держит дефектный commit украденного устройства, — команда оператора или «Начать заново» (`CRYPTO.md` §8.2 п. 22).
- `GENERATION_JUMP_MAX` = 2¹⁶ — наибольший скачок номера поколения после потери журнала; `media_key_base` в `GroupBinding` — сдвиг индексов ключей медиа новой группы звонка на половину кольца.
- `device_id`, `group_id` и прочие id в криптографических структурах — 16 байт двоичного UUID, не строка (спайк S4 использовал строку UTF-8): фиксированная длина, нет вопроса регистра.
- Credential не содержит ключа идентичности: клиент всё равно сверяет его с известным ключом пользователя; так лист короче на 32 байта.
- KeyPackage загружает только подтверждённое устройство (credential несёт подпись ключом идентичности).
- При входе по Welcome проверка срока листьев дерева отключена (`JoinBuilder::skip_lifetime_validation`, openmls 0.9.2): иначе участник, добавленный больше 31 сут назад и не делавший commit-ов, закрыл бы вход всем новичкам (RFC 9420 §7.3). Срок пакета в Add проверяется при commit-е.
- Назначенный коммитер: вместо свободной гонки после 2–3 с (ADR-0018 п. 7) DS назначает следующее устройство через 3 с.
- Горизонт офлайна 30 сут = минимальный остаток срока KeyPackage 31 сут − 1 сут на часы.
- Ключ медиа — MLS-Exporter по `(device_id, класс трека, encryptor_id)`: ключ на экземпляр шифратора (Б-С4); стрим — отдельный класс, media-engine получает только ключи своих экземпляров.
- Файлы: один ключ на вложение и подключи по виду объекта (файл, превью, миниатюра) — так контракт B1 «миниатюра тем же ключом» выполняется без повторного использования ключа.
- Пароль устройства на Linux: Argon2id с 256 МиБ (больше, чем у ключа восстановления: пароль придумывает человек), случайный ключ базы обёрнут ключом из пароля.
- Ключ поколения истории — из MLS-Exporter эпохи начала поколения: участники получают его при merge без рассылки; связка хранит только головной ключ.
- Право устройства на историю выводит коммитер из своих наблюдений; `ProposalAAD.history_from_generation` сервера его только сужает (ADR-0020); один механизм моста покрывает №9, возврат после горизонта и чужой сброс.
- Ссылка цепочки хранит номер предыдущего поколения явно и проверяется в AAD; пересоздание группы — разрыв `break_recreate` без ссылки (Б-В1), поэтому ссылок между группами нет.
- HPKE (мост, копия личной группы) — DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-128-GCM: те же примитивы, что ciphersuite 0x0001.
- Паддинг сообщения — кратно 256 байтам; `max_past_epochs = 0`.
