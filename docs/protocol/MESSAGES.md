# Формат сообщений

Схема — [`proto/bebeberloga/v1/envelope.proto`](../../proto/bebeberloga/v1/envelope.proto) (зашифрованная часть) и [`message.proto`](../../proto/bebeberloga/v1/message.proto) (открытые метаданные). Криптографические детали — ключ сообщения, его обёртка ключом истории, вывод секрета канала для mention-hint — описывает `CRYPTO.md` (B2); здесь — структура и правила.

## 1. Два слоя

```
MessageMeta (открыто, хранит сервер)          MessageEnvelope (внутри шифртекста)
┌─────────────────────────────────┐           ┌───────────────────────────────┐
│ id (UUIDv7, от клиента)         │           │ message_id (= MessageMeta.id) │
│ channel_id, group_id, epoch     │           │ sent_at                       │
│ author_user_id, author_device_id│   MLS     │ body (oneof):                 │
│ created_at (сервер)             │ ◀──────── │   text | edit | delete |      │
│ ciphertext ──────────────────────────────▶  │   reaction | pin | file_key | │
│ wrapped_message_key, generation │           │   call_key | history_keys |   │
│ mention_hints[], broadcast      │           │   device_notice               │
│ attachments[] (id, size, hash)  │           └───────────────────────────────┘
│ size, pinned, deleted, system   │
└─────────────────────────────────┘
```

- `ciphertext` — MLS `PrivateMessage` (RFC 9420 §6.3) группы канала; внутри — сериализованный `MessageEnvelope`. Авторство гарантирует подпись MLS; сервер знает только устройство-отправитель.
- Внутри конверта повторяется `message_id`: клиент отбрасывает сообщение, если он не совпал с открытым `MessageMeta.id`, — сервер не может подменить шифртекст под другим id.
- `sent_at` — часы клиента, только для отображения «отправлено в …» при большом расхождении; порядок ленты задаёт UUIDv7 `id`.
- Системные сообщения сервера (`MessageMeta.system`: вступление участника, закреп, передача владения) шифртекста не имеют. Системные заметки, требующие знания о ключах («новое устройство», «ключи изменились», «больше не использует устройство»), создаёт **клиент** как обычное зашифрованное сообщение с телом `DeviceNoticeBody` — сервер о них не знает.

## 2. Типы тела

| Тип | Поля | Кто создаёт | Что делает получатель |
|---|---|---|---|
| `text` | `text`, `reply_to`, `reply_mention`, `mentions[]`, `attachments[]` (`FileRef`), `link_previews[]` (S) | Пользователь | Новое сообщение в ленте; цитата по `reply_to` из локальной базы, иначе «Исходное сообщение недоступно» |
| `edit` | `target_id`, `text`, `mentions[]`, `link_previews[]` | Автор `target_id` | Подменяет текст, ставит «(изменено)»; от чужого устройства-автора игнорируется |
| `delete` | `target_id` | Автор или модератор (вместе с REST `DELETE`) | Удаляет из локальной базы, даже если событие `MessageDeleted` не дошло |
| `reaction` | `target_id`, `emoji`, `on` | Пользователь | Агрегация на клиенте; оптимистичное отображение у отправителя |
| `pin` | `target_id`, `pinned` | Участник с `chat.moderate` (вместе с REST `PUT/DELETE …/pins`) | Локальная пометка закрепа для офлайн-истории; список закрепов — сервер |
| `file_key` | `target_message_id`, `file` (`FileRef`) | Отправитель вложения | Повторная выдача ключа вложения, если участник не смог расшифровать исходное |
| `call_key` | `channel_id`, `epoch`, `key_material` | Зарезервировано; основной путь — MLS exporter группы звонка | По CRYPTO.md |
| `history_keys` | `keys[]{generation, key, valid_from}` | Коммитящий клиент при вступлении или ротации ключа истории | Пополняет связку ключей истории (ADR-0015) |
| `device_notice` | `kind`, `user_id`, `device_name` | Устройство владельца при добавлении/удалении устройства или смене ключа идентичности | Системная строка в ЛС и группах ≤ 50 участников; в больших каналах не показывается (SCREENS/07 §8) |
| `poll_vote` | — | Опросы (C), поле зарезервировано | — |

`typing` не является телом сообщения: индикатор набора идёт открытой командой gateway `TypingStart`.

## 3. Лимиты

| Что | Лимит | Кто проверяет |
|---|---|---|
| `TextBody.text`, `EditBody.text` | 4 000 символов (code points) после нормализации NFC | Клиент до отправки; получатель обрезает с «…» при нарушении |
| Вложений в сообщении | 10 | Клиент и сервер (`attachment_ids`, `TOO_MANY_ATTACHMENTS`) |
| `FileRef.name` | 255 символов | Клиент |
| `FileRef.description` | 500 символов (STATUS.md) | Клиент |
| `FileRef.thumbnail` | ≤ 8 КиБ, WebP ≤ 64 px по большей стороне, зашифрована ключом файла | Клиент |
| Упоминаний в сообщении | 50 (STATUS.md) | Клиент; сервер ограничивает `mention_hints` 50 |
| Размер шифртекста (`MessageMeta.ciphertext`) | 128 КиБ: 4 000 символов × 4 байта + 10 вложений × (8 КиБ миниатюра + ~1 КиБ метаданных) ≈ 106 КиБ плюс накладные расходы MLS | Сервер (`PAYLOAD_TOO_LARGE`) |
| `ReactionBody.emoji` | Одна Unicode-последовательность эмодзи (с модификаторами), ≤ 32 байт (STATUS.md) | Клиент; получатель игнорирует иное |
| Размер файла вложения | Лимит инстанса (`InstanceLimits.max_file_size`) | Сервер при `POST /files` |

## 4. Упоминания и mention-hint

- Внутри конверта упоминания перечислены явно (`Mention`: пользователь, роль, канал, «@все», «@здесь»). Клиент подсвечивает их в тексте и решает, упомянут ли он сам.
- Снаружи, для сервера, отправитель добавляет в `MessageMeta`:
  - `mention_hints[]` — по одному хинту на упомянутого пользователя и каждую упомянутую роль: `HMAC(секрет канала, id)`; секрет канала выводится из MLS exporter группы (контекст и длина — CRYPTO.md). Порядок хинтов перемешивается;
  - `broadcast_mention` — `BROADCAST_MENTION_ONLINE` для «@здесь», `BROADCAST_MENTION_ALL` для «@все», иначе `BROADCAST_MENTION_NONE`.
- Каждый участник заранее регистрирует свои хинты `PUT /channels/{id}/mention-hints {epoch, hints[]}`: хинт своего id и хинты своих ролей. Сервер сравнивает хинты сообщения с зарегистрированными и так узнаёт, **кому** ставить бейдж упоминания и слать адресный push, не узнавая, кто упомянут посторонним. Сервер видит число упоминаний в сообщении — это принятая утечка (ARCHITECTURE.md §8).
- Право `chat.ping_all` нужно для `broadcast_mention ≠ NONE` и для хинтов ролей; без права сообщение проходит, но уведомления и бейджи по этим упоминаниям не выставляются (PERMISSIONS.md §4). Флага «упоминаемая роль» в 1.0 нет (C, OPEN-QUESTIONS №8).
- Упоминание канала (`#канал`) хинта не создаёт.
- Когда меняется секрет канала (смена эпохи с новым exporter-секретом — правило в CRYPTO.md), клиент заново регистрирует хинты с новой `epoch`; сервер держит хинты двух последних эпох.

## 5. Семантика правки, удаления, реакций, закрепов

- **Правка** — новое сообщение с `EditBody`; применяется, только если `author_user_id` совпадает с автором цели. Несколько правок применяются в порядке `id` (UUIDv7). Срок правки не ограничен.
- **Удаление** — команда `DELETE /channels/{id}/messages/{mid}` (сервер: tombstone, `MessageDeleted`) **и** сообщение `DeleteBody` в группе, чтобы офлайн-участники убрали сообщение из локальной базы при догоне истории. Модератор, не имеющий текста, удаляет по id только через REST — тогда `DeleteBody` не отправляется, участники полагаются на `MessageDeleted` и флаг `deleted` в истории.
- **Реакции** — малые сообщения `ReactionBody`; агрегация и дедупликация (одна реакция одного эмодзи от пользователя) на клиенте. «Убрать реакции у всех» модератором: снять чужую реакцию от чужого имени нельзя, поэтому модератор удаляет сами сообщения-реакции по id через `DELETE …/messages/{mid}` (право `chat.moderate`; сервер видит их как обычные сообщения). Id реакций клиент модератора знает из расшифрованной истории.
- **Закреп** — `PUT /channels/{id}/pins/{mid}` (сервер хранит id, рассылает `MessageUpdated{pinned}` и создаёт системное сообщение) плюс `PinBody` в группе для локальной истории.
- **Ответ** — `TextBody.reply_to`; если оригинал удалён — «Исходное сообщение удалено»; если не расшифрован или ещё не загружен — «Исходное сообщение недоступно».

## 6. Проверки на приёме

Клиент отбрасывает (и пишет в журнал) сообщение, если:
- `MessageEnvelope.message_id ≠ MessageMeta.id`;
- `EditBody`/`DeleteBody` ссылаются на чужое сообщение, а отправитель — не его автор (для `DeleteBody` допускается участник с `chat.moderate` по правам на момент получения);
- конверт не разбирается или `body` не задан (неизвестный тип из будущей версии — показывается «Сообщение из новой версии клиента», не отбрасывается);
- в `TextBody` больше 10 вложений или текст пустой при отсутствии вложений.

Если сообщение не удалось расшифровать (нет ключа эпохи), клиент показывает заглушку «ждём ключ» и хранит шифртекст 24 часа для повторной попытки (SCREENS/08 §10).

## 7. Что определяет B2 (CRYPTO.md)

Ключ сообщения и его связь с MLS; обёртка ключом истории и формат `history_key_bundle`; вывод секрета канала для mention-hint; схема шифрования файла чанками и nonce; ключ к зашифрованному GroupInfo; содержимое `CallKeyBody`; когда и как клиент шлёт `HistoryKeysBody`; число KeyPackage в пачке.
