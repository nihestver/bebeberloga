# Формат сообщений

Схема — [`proto/bebeberloga/v1/envelope.proto`](../../proto/bebeberloga/v1/envelope.proto) (зашифрованная часть) и [`message.proto`](../../proto/bebeberloga/v1/message.proto) (открытые метаданные). Криптографические детали — ключ сообщения, его обёртка ключом истории, вычисление mention-hint — описывает `CRYPTO.md` (B2, B21); здесь — структура и правила.

## 1. Два слоя

```
MessageMeta (открыто, хранит сервер)          SealedMessage → MessageEnvelope + подпись
┌─────────────────────────────────┐           ┌───────────────────────────────┐
│ id (UUIDv7, от клиента)         │  ключ     │ message_id (= MessageMeta.id) │
│ channel_id, group_id, epoch     │ сообщения │ sent_at                       │
│ author_user_id, author_device_id│ ◀──────── │ body (oneof):                 │
│ created_at (сервер)             │           │   text | edit | delete |      │
│ ciphertext ──────────────────────────────▶  │   reaction | pin | file_key | │
│ wrapped_message_key, generation │           │   device_notice |             │
│ mention_hints[], broadcast,     │           │   personal_sync               │
│ author_can_ping_all (сервер)    │           ├───────────────────────────────┤
│ attachments[] (id, size, hash)  │           │ подпись устройства-отправителя│
│ size, pinned, deleted, system   │           │                               │
└─────────────────────────────────┘           └───────────────────────────────┘
```

- `ciphertext` — `SealedMessage` (CRYPTO.md §6.2): сериализованный `MessageEnvelope` и подпись ключом подписи устройства-отправителя, зашифрованные XChaCha20-Poly1305 случайным ключом сообщения; длина кратна 256 байтам. Это **не** MLS-сообщение: ключ сообщения лежит только в `wrapped_message_key` под подключом поколения ключа истории (ADR-0020). Подпись и AAD привязаны к каналу, `id`, отправителю и поколению — авторство проверяется и в истории, где MLS-подписи нет; подписи делают сообщения неотрицаемыми для всех, кто видит историю.
- Внутри конверта повторяется `message_id`: клиент отбрасывает сообщение, если он не совпал с открытым `MessageMeta.id`. Перенос шифртекста под другой `id` ловят и AAD с подписью.
- `sent_at` — часы клиента, только для отображения «отправлено в …» при большом расхождении; порядок ленты задаёт UUIDv7 `id`.
- Системные сообщения сервера (`MessageMeta.system`: вступление участника, закреп, передача владения) шифртекста не имеют. Системные заметки, требующие знания о ключах («новое устройство», «ключи изменились», «больше не использует устройство»), создаёт **клиент** как обычное зашифрованное сообщение с телом `DeviceNoticeBody` — сервер о них не знает.

## 2. Типы тела

| Тип | Поля | Кто создаёт | Что делает получатель |
|---|---|---|---|
| `text` | `text`, `reply_to`, `reply_mention`, `mentions[]`, `attachments[]` (`FileRef`), `link_previews[]` (S) | Пользователь | Новое сообщение в ленте; цитата по `reply_to` из локальной базы, иначе «Исходное сообщение недоступно» |
| `edit` | `target_id`, `text`, `mentions[]`, `link_previews[]` | Автор `target_id` | Подменяет текст, ставит «(изменено)»; от чужого устройства-автора игнорируется |
| `delete` | `target_id` | Автор или модератор (вместе с REST `DELETE`) | Удаляет из локальной базы, даже если событие `MessageDeleted` не дошло |
| `reaction` | `target_id`, `emoji`, `on` | Пользователь | Агрегация на клиенте; оптимистичное отображение у отправителя |
| `pin` | `target_id`, `pinned` | Участник с `chat.moderate` (вместе с REST `PUT/DELETE …/pins`) | Локальная пометка закрепа для офлайн-истории; список закрепов — сервер |
| `file_key` | `target_message_id`, `file` (`FileRef`) | Отправитель вложения | Повторная выдача ключа вложения, если участник не смог расшифровать исходное |
| `call_key` | `channel_id`, `epoch`, `key_material` | Не используется в 1.0: ключи медиа — из MLS-Exporter группы звонка (CRYPTO.md §5.5), `deprecated` | Игнорирует |
| `history_keys` | `keys[]{generation, key, valid_from}` | Не используется в 1.0: ключ поколения выводится из exporter, через разрыв — мост (CRYPTO.md §6.6), `deprecated` | Игнорирует |
| `personal_sync` | `verification[]{user_id, identity_key, verified, at}`, `trusted_domains[]{domain, trusted}`, `recovery_key{device_id, created_at}` | Устройство пользователя, только в его личном канале (CRYPTO.md §6.5) | Принимается только в своём личном канале и только от своего пользователя; обновляет статусы проверки и доверенные домены; действует последнее по `id` в пределах окна CRYPTO.md §6.2.8, не по времени приёма (CRYPTO.md §6.5) |
| `device_notice` | `kind`, `user_id`, `device_name` | Устройство владельца при добавлении/удалении устройства или смене ключа идентичности; принимается только от пользователя `user_id` | Системная строка в ЛС и группах ≤ 50 участников; в больших каналах не показывается (SCREENS/07 §8) |
| `poll_vote` | — | Опросы (C), поле зарезервировано | — |

`typing` не является телом сообщения: индикатор набора идёт открытой командой gateway `TypingStart`.

## 3. Лимиты

| Что | Лимит | Кто проверяет |
|---|---|---|
| `TextBody.text`, `EditBody.text` | 4 000 символов (code points) после нормализации NFC | Клиент до отправки; получатель обрезает с «…» при нарушении |
| Вложений в сообщении | 10 | Клиент и сервер (`attachment_ids`, `TOO_MANY_ATTACHMENTS`) |
| `FileRef.name` | 255 символов | Клиент |
| `FileRef.description` | 500 символов (STATUS.md) | Клиент |
| `FileRef.thumbnail` | ≤ 8 КиБ, WebP ≤ 64 px по большей стороне, зашифрована ключом файла | Клиент |
| Упоминаний в сообщении | 50 (STATUS.md) | Клиент; сервер принимает 0, 1, 2, 4, 8, 16, 32 или 50 хинтов по 16 байт (`VALIDATION_FAILED`) |
| Размер шифртекста (`MessageMeta.ciphertext`) | 128 КиБ: 4 000 символов × 4 байта + 10 вложений × (8 КиБ миниатюра + ~1 КиБ метаданных) ≈ 106 КиБ плюс накладные расходы MLS | Сервер (`PAYLOAD_TOO_LARGE`) |
| `ReactionBody.emoji` | Одна Unicode-последовательность эмодзи (с модификаторами), ≤ 32 байт (STATUS.md) | Клиент; получатель игнорирует иное |
| Размер файла вложения | Лимит инстанса (`InstanceLimits.max_file_size`) сравнивается с размером blob-а — файла, дополненного до выровненной длины (CRYPTO.md §7.2) | Клиент до загрузки; сервер при `POST /files` |

Markdown-подмножество 1.0 (жирный, курсив, зачёркнутый, код, блок кода, цитата, спойлер) — FEATURES 3.4; грамматика и тестовый корпус — ARCHITECTURE.md §6.4, задаёт B9/B3. Текст хранится как написан, без предварительного рендера.

## 4. Упоминания и mention-hint

Сервер не узнаёт, кого упомянули: хинты сопоставляет клиент получателя (ADR-0027). Формула хинта и порядок действий — CRYPTO.md §6.4; здесь — что лежит в сообщении и кто что делает.

- **Внутри конверта** упоминания перечислены явно (`Mention`: пользователь, роль, канал, «@все», «@здесь»). По ним клиент подсвечивает текст.
- **Снаружи**, в `MessageMeta`, отправитель оставляет:
  - `mention_hints[]` — по одному хинту на каждого упомянутого пользователя и каждую упомянутую роль: 16 байт HMAC подключом поколения ключа истории от вида цели, id цели и `id` этого сообщения. Автор сообщения, на которое отвечают, — тоже цель, если стоит `reply_mention`;
  - хинты-пустышки — случайные 16 байт — до ближайшего числа из ряда 1, 2, 4, 8, 16, 32, 50. Сообщение без упоминаний хинтов не несёт. Порядок хинтов случайный;
  - `broadcast_mention` — `BROADCAST_MENTION_ONLINE` для «@здесь», `BROADCAST_MENTION_ALL` для «@все», иначе `BROADCAST_MENTION_NONE`.
- **Сервер** хинты хранит и отдаёт, но ни с чем не сравнивает: регистрации хинтов нет. При приёме он ставит на сообщение отметку `author_can_ping_all` — было ли у отправителя право `chat.ping_all` в этом канале; в ЛС и групповом чате отметка стоит всегда. Сообщение без права проходит (PERMISSIONS.md §4).
- **Получатель** считает хинты своего id и своих ролей для этого сообщения и сравнивает. Совпадение со своим id — упоминание. Совпадение с ролью и «@все» засчитываются, только если стоит `author_can_ping_all`. «@здесь» — при той же отметке и только на устройстве, которое получило сообщение, пока было на связи. Затем клиент применяет настройки уведомлений (SCREENS/10 §4).
- **После офлайна.** `Ready` несёт по каждому каналу `ReadState.mention_candidate_count` — число непрочитанных чужих сообщений с хинтами или широким упоминанием. Клиент забирает кандидатов (`GET /users/me/mention-candidates`: id, канал, поколение, хинты, `broadcast_mention`, отметка права — без шифртекста) и считает упоминания сам. Пока не посчитал, канал показывает обычный бейдж непрочитанного (FLOWS/06).
- Упоминание канала (`#канал`) хинта не создаёт. Флага «упоминаемая роль» в 1.0 нет (C, OPEN-QUESTIONS №8).
- У правки (`EditBody`) свои хинты — от `id` самой правки.
- Сервер видит, что упоминания есть, и их число с точностью до ряда; кого упомянули и что два сообщения упоминают одного и того же — нет (ARCHITECTURE.md §8).

## 5. Семантика правки, удаления, реакций, закрепов

- **Правка** — новое сообщение с `EditBody`; применяется, только если `author_user_id` совпадает с автором цели. Несколько правок применяются в порядке `id` (UUIDv7). Срок правки не ограничен.
- **Удаление** — команда `DELETE /channels/{id}/messages/{mid}` **и** сообщение `DeleteBody` в группе. Сервер сразу стирает шифртекст, обёрнутый ключ сообщения, хинты и blob-ы вложений и оставляет отметку: `id`, канал и время удаления (ADR-0028 п. 3); затем `MessageDeleted`. `DeleteBody` нужен, чтобы офлайн-участники убрали сообщение из локальной базы при догоне истории. Модератор, не имеющий текста, удаляет по id только через REST — тогда `DeleteBody` не отправляется, участники полагаются на `MessageDeleted` и флаг `deleted` в истории.
- **Реакции** — малые сообщения `ReactionBody`; агрегация и дедупликация (одна реакция одного эмодзи от пользователя) на клиенте. «Убрать реакции у всех» модератором: снять чужую реакцию от чужого имени нельзя, поэтому модератор удаляет сами сообщения-реакции по id через `DELETE …/messages/{mid}` (право `chat.moderate`; сервер видит их как обычные сообщения). Id реакций клиент модератора знает из расшифрованной истории.
- **Закреп** — `PUT /channels/{id}/pins/{mid}` (сервер хранит id, рассылает `MessageUpdated{pinned}` и создаёт системное сообщение) плюс `PinBody` в группе для локальной истории.
- **Ответ** — `TextBody.reply_to`; если оригинал удалён — «Исходное сообщение удалено»; если не расшифрован или ещё не загружен — «Исходное сообщение недоступно».

## 6. Проверки на приёме

Клиент отбрасывает (и пишет в журнал) сообщение, если:
- не снимается обёртка ключа, не расшифровывается `SealedMessage` или паддинг ненулевой (CRYPTO.md §6.2.5);
- подпись не проверяется ключом подписи устройства-отправителя, или устройство не подписано ключом идентичности, действовавшим в момент `created_at`, или сообщение отправлено после удаления устройства (CRYPTO.md §6.2.5–§6.2.6);
- `MessageEnvelope.message_id ≠ MessageMeta.id`;
- `personal_sync` пришло не в свой личный канал или не от своего пользователя; `device_notice` пришло не от пользователя `DeviceNoticeBody.user_id` (CRYPTO.md §6.2.5 п. 6);
- `EditBody`/`DeleteBody` ссылаются на чужое сообщение, а отправитель — не его автор (для `DeleteBody` допускается участник с `chat.moderate` по правам на момент получения);
- конверт не разбирается или `body` не задан (неизвестный тип из будущей версии — показывается «Сообщение из новой версии клиента», не отбрасывается);
- в `TextBody` больше 10 вложений или текст пустой при отсутствии вложений.

Если нет ключа поколения ключа истории (ещё не пришли связка, ссылки или мост), клиент показывает заглушку «ждём ключ» и хранит шифртекст 24 часа для повторной попытки (SCREENS/08 §10). Сообщения поколений до права устройства (выключенная история, сброс ключей) не показываются вовсе.

## 7. Что определяет B2 (CRYPTO.md)

Определено в CRYPTO.md: формат `SealedMessage`, подпись и паддинг (§6.2); ключ сообщения и его обёртка подключом поколения ключа истории (§6.2.4); поколения, ссылки, связка `history_key_bundle` и мосты (§6.3); mention-hint и его сопоставление клиентом (§6.4); запись канала с названием и темой (§6.8); личный канал и `PersonalSyncBody` (§6.5); схема шифрования файла чанками и nonce (§7); число KeyPackage в пачке (§1.4). `CallKeyBody` и `HistoryKeysBody` в 1.0 не используются (§5.5, §6.6); GroupInfo не используется (ADR-0019).
