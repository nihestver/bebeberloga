# S2. Спайк: E2EE звонка в LiveKit с ключами из MLS

Запуск: `/prompt S2`. Фаза 0. Каталог: `spikes/02-livekit-e2ee/`. Зависит от S1 (можно начать с заглушки ключей).

## Роль
TypeScript/WebRTC-разработчик в проекте Bebeberloga. Действуют правила `CLAUDE.md`.

## Входные файлы
- docs/spec/ARCHITECTURE.md §4.6, §5
- docs/adr/0004-e2ee-mls-sframe.md, 0008-stream-media-engine.md
- docs/spec/FLOWS/07-voice.md

- spikes/01-openmls-ffi/REPORT.md (если готов)

## Задача
1. Локальный LiveKit server в Docker (dev-ключи) + Electron-приложение на `livekit-client` с E2EE и собственным KeyProvider. Docker — для функциональных проверок; замеры п. 4 — на нативном бинарнике LiveKit (`spikes/03-electron-capture/scripts/fetch-livekit.sh`), см. отчёт S3.
2. Ключ участника выводится из exporter-секрета MLS-группы звонка (из S1 через napi или заглушка с тем же интерфейсом); при смене эпохи — новый key index по `CRYPTO.md` §5.3 (получатель ставит ключ сразу, отправитель переключается по правилу §5.3, кадры с ещё неизвестным индексом удерживаются, а не отбрасываются), старый ключ принимается ещё 2 с.
3. Звонок на 10 участников: 2–3 реальных окна Electron + headless-участники (Playwright с фейковыми устройствами).
4. Замеры: пауза звука и фриз видео у остальных при входе и выходе участника (цель — ни того, ни другого); время от клика до первого звука у входящего (цель ≤ 1 с при RTT до сервера ≤ 100 мс, FLOWS/07); добавка E2EE к задержке кадра (цель < 2 мс, ARCHITECTURE §6.5); CPU на участника с E2EE и без.
5. Проверка на тест-SFU: в кадрах на SFU нет открытого медиа (заголовки SFrame/зашифрованная полезная нагрузка).
6. Качество под E2EE: работают simulcast и SVC с переключением слоёв на SFU, adaptive stream и dynacast, Opus FEC, RED и DTX, NACK/RTX, запрос ключевого кадра, аппаратное кодирование. Всё, что E2EE отключает или ухудшает, — в REPORT.md с обходом; молча снижать качество нельзя. Подтвердить пп. 1–6 `CRYPTO.md` §5.4.
