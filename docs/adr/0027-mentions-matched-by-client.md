# ADR-0027: Упоминания сопоставляет клиент: сервер не узнаёт, кого упомянули

- Статус: Принято 2026-11-15 (владелец; пересматривает его решение по К5 от 2026-11-03 — «сервер узнаёт, кого упомянули»)
- Дата: 2026-11-15
- Частично изменяет: [ADR-0020](0020-history-keys-message-format.md) п. 3 (регистрация хинтов и сопоставление сервером) и строку «ARCHITECTURE §8» его таблицы
- Связано: [ADR-0010](0010-mobile-after-1-0.md), [ADR-0026](0026-channel-names-encrypted.md), [ADR-0028](0028-server-data-minimization.md); `docs/spec/ARCHITECTURE.md` §4.4, §5.3, §8; `docs/spec/PERMISSIONS.md` §1 п. 8; `docs/spec/FLOWS/06-messages.md`; `docs/spec/SCREENS/03`, `10` §3–4; `docs/protocol/MESSAGES.md` §4 и `CRYPTO.md` §6.4, §6.7 (правит промпт B21)

## Контекст

- По ADR-0020 п. 3 каждый участник регистрирует на сервере хинты своего id и своих ролей, сервер сравнивает их с хинтами сообщения и узнаёт, кого упомянули в каком сообщении. Это нужно для адресного push и счётчика упоминаний на сервере.
- В 1.0 есть только desktop-клиент. Уведомление показывает сам клиент, когда получает сообщение через gateway (`FEATURES.md` 3.6); push — S, вместе с мобильными клиентами после 1.0. В 1.0 знание «кого упомянули» нужно серверу только для счётчика.
- «Кто к кому обратился в каком сообщении» — связь между людьми внутри канала, которой у сервера иначе нет: он знает автора и состав канала, но не адресата реплики.
- Хинт одного пользователя одинаков во всех сообщениях поколения: сервер видит повторы даже без регистрации.

## Решение

1. **Сервер хинты не сопоставляет.** Регистрации хинтов нет (`PUT /users/me/mention-hints` убирается из контракта), реестра хинтов участников на сервере нет.
2. **Хинт привязан к сообщению.** HMAC подключом `"mention"` поколения ключа истории от вида цели (пользователь или роль), id цели **и id сообщения**; 16 байт. У двух сообщений нет одинаковых хинтов: сервер не видит, что они упоминают одного и того же.
3. **Число хинтов выравнивается.** Отправитель добавляет случайные хинты-пустышки до ближайшего числа из ряда 1, 2, 4, 8, 16, 32, 50. Сообщение без упоминаний хинтов не несёт. Сервер видит: в сообщении есть упоминания, примерно столько.
4. **Сопоставляет клиент получателя.** Для сообщения с хинтами он вычисляет хинты своего id и своих ролей и сравнивает. По результату — уведомление, бейдж и вкладка «Упоминания».
5. **Догон после офлайна.** Сервер по запросу отдаёт по каналам непрочитанные сообщения, у которых есть хинты или широкое упоминание: id, поколение, хинты и отметки — без шифртекста. В `Ready` вместо числа упоминаний приходит число таких кандидатов. Точное число клиент считает сам; пока не посчитал, канал показывает обычный бейдж непрочитанного.
6. **«@все» и «@здесь»** остаются открытой отметкой `broadcast_mention`: она нужна серверу для проверки права 8. «@здесь» засчитывает устройство, которое получило сообщение, пока было на связи, и помнит это локально.
7. **Право 8 «Упоминать всех» для ролей.** Сервер не отличает хинт роли от хинта пользователя. Поэтому при приёме сообщения он ставит на него открытую отметку: было ли у отправителя право 8. Клиент получателя засчитывает совпадение с ролью и широкое упоминание, только если отметка стоит. Сообщение без права по-прежнему проходит, но без уведомлений (`PERMISSIONS.md` §4).
8. **Настройки уведомлений** («только @упоминания», «не уведомлять об @все и @здесь», «не уведомлять об упоминаниях ролей») по-прежнему хранятся на сервере ради синхронизации между устройствами; применяет их клиент.
9. **Push (S, после 1.0)** — отдельное решение вместе с мобильными клиентами (ADR-0010). Исходные варианты: (а) беззвучный push о кандидате, устройство само решает, показывать ли уведомление; (б) явное согласие пользователя «сервер знает мои упоминания» с регистрацией хинтов для его мобильных устройств. До этого решения модуль `push` хинты не использует.

## Последствия

- Сервер не знает, кого упомянули, и не связывает упоминания между сообщениями. Он видит: что упоминания есть, их примерное число, широкое упоминание и было ли у автора право 8.
- Сервер проще: нет реестра хинтов, пересчёта «задним числом» и хранения хинтов участников по поколениям.
- Бейдж упоминаний на новом устройстве и после долгого офлайна появляется после одного лёгкого запроса и локального подсчёта: один HMAC на кандидата для своего id и по одному на каждую свою роль.
- Вкладку «Входящие → Упоминания» строит клиент по кандидатам; сами сообщения он и так скачивает для показа.
- Устройство, у которого ещё нет ключа поколения (ждёт связку или мост), посчитает упоминания в этих сообщениях, когда ключ придёт.
- Серверная автоматика по упоминаниям (например, письмо о пропущенном упоминании) невозможна; в плане её и не было.
- Проверка: по полному журналу запросов и содержимому базы тестовый сервер не может отличить, кого упомянули, и связать два упоминания одного участника (B18).

## Рассмотренные альтернативы

- **Оставить по ADR-0020: сервер знает, кого упомянули.** В 1.0 это не нужно ни одной M-функции, а связь «кто к кому обращается» уходит оператору. Отклонено.
- **Убрать хинты совсем, клиент ищет упоминания в расшифрованном тексте.** Бейдж после долгого офлайна потребовал бы скачать всю непрочитанную историю. Отклонено.
- **Прежний хинт (без id сообщения), но без регистрации.** Сервер видит повторы и по ним группирует упоминания одного участника. Отклонено.
- **Скрыть и сам факт упоминания** (пустышки в каждом сообщении). Кандидатом становится каждое сообщение, догон теряет смысл. Отклонено.
