# ADR-0016: Результаты спайка S1 — OpenMLS через FFI

- Статус: Предложено
- Дата: 2026-11-02
- Связано: [ADR-0004](0004-e2ee-mls-sframe.md); `docs/spec/ARCHITECTURE.md` §4, §6.1, §6.4; отчёт [`spikes/01-openmls-ffi/REPORT.md`](../../spikes/01-openmls-ffi/REPORT.md); промпты B02, B03

## Контекст

ADR-0004 выбрал MLS через OpenMLS для всех групп, а сервер — как Delivery Service и external sender. До криптографического дизайна (B02) и crypto-core (B03) нужно было проверить на практике: закрывает ли текущий OpenMLS нужды проекта (ciphersuite 0x0001, Basic credential, предложения Add/Remove от сервера, exporter-секрет), подключается ли он к Electron через napi-rs и к Kotlin/Swift через uniffi, и как он ведёт себя на группах в 10, 100 и 1 000 устройств. Спайк S1 это проверил; числа — в отчёте.

## Решение

Предлагается зафиксировать для B02 и B03:

1. **Библиотека.** `openmls` 0.9.x с провайдером `openmls_rust_crypto` и `openmls_basic_credential`; версии закрепляются точно (`=`), обновление — отдельным коммитом с записью в `SECURITY-CHANGELOG.md`. Ciphersuite 0x0001, MLS 1.0, credential Basic — всё работает без доработок.
2. **Конфигурация группы.** `use_ratchet_tree_extension = true`: Welcome несёт дерево, и новому устройству не нужен отдельный запрос дерева у сервера. Политика формата — `PURE_CIPHERTEXT`: handshake-сообщения участников всегда зашифрованы. Предложения сервера приходят открытыми (`PublicMessage`), но входящая политика в openmls к внешним сообщениям не применяется, поэтому ослаблять её до `MIXED_*` не нужно — это лишь позволило бы участнику раскрыть серверу содержимое своих commit-ов. Режим один, без вариантов.
3. **Сервер как external sender и политика клиента.** В group context extension `external_senders` записывается подписывающий ключ сервера с Basic credential (индекс 0). Сервер подписывает предложения Add (с KeyPackage) и Remove как `PublicMessage`; первый активный участник коммитит их через `commit_to_pending_proposals`. OpenMLS проверяет **только подпись** отправителя; кто вправе менять состав, решает приложение. Внешние предложения клиент считает недоверенными и до постановки в очередь, а также до merge чужого commit-а, применяет политику:
   - предложение входа от не-участника (`NewMemberProposal`) отвергается всегда — openmls принимает его в любой группе, даже без `external_senders`, и без этой проверки любой, кто знает id группы и эпоху, входит в группу и получает её ключи и связку ключей истории;
   - от `Sender::External` принимаются только Add и Remove; GroupContextExtensions (например, подмена списка external senders), PSK и ReInit отвергаются; при входе по Welcome клиент сверяет `external_senders` с закреплённым ключом инстанса;
   - credential каждого добавляемого листа подписан ключом идентичности пользователя (cross-signing, ARCHITECTURE §4.2), и пользователь имеет доступ к каналу — как клиент это проверяет, описывает B02 (роль Authentication Service на клиенте);
   - Remove указывает на устройство, которое сервер назвал явно; участник опознаётся по проверенному ключу идентичности и leaf index, отображаемое имя — только для показа.
   Спайк реализует первые два пункта, остальные — B02/B03.
4. **Протокол Delivery Service.** Серверу для сериализации хватает заголовка сообщения (id группы и эпоха видны без ключей), но заголовок для сервера не аутентифицирован: проверить commit DS не может, а участник может «занять» эпоху мусорным commit-ом — B02 нужна процедура восстановления рассинхрона. Участник применяет свой commit (`merge_pending_commit`) только по явному подтверждению сервера; при отказе — `clear_pending_commit` и повтор в новой эпохе. Вернувшееся собственное зашифрованное сообщение (`OwnPrivateMessage`) только игнорируется — заявленный в заголовке лист не аутентифицирован; `OwnPendingCommit` при зашифрованных handshake недостижим. Предложения сервера живут одну эпоху: любой commit очищает очередь, поэтому устройство с ожидающим Remove могло бы первым закоммитить своё и остаться; DS хранит невыполненные Remove, повторяет их в каждой новой эпохе и не принимает commit от устройства с ожидающим Remove, а клиент не применяет commit, в котором нет объявленных сервером Remove (механизм — B02). Открытый вопрос: Remove-предложению нужен leaf index, а при зашифрованных commit-ах и зашифрованном GroupInfo (ARCHITECTURE §4.3) сервер дерева не видит и лимит листьев проверить не может — DS ведёт публичное дерево, Add идут только по предложению сервера или цель Remove задаётся идентификатором устройства, который клиент сверяет с credential листа; решают B02 и S4. В спайке индекс берётся из состояния участника.
5. **FFI.** Electron — napi-rs: `.node` собирается без `@napi-rs/cli`, и один и тот же файл работает в Node 22 и в main-процессе Electron 33 (внутри Node 20 — Node-API не зависит от ABI). Android и iOS — uniffi 0.32 через proc-macro без `core.udl`: сигнатуры живут в одном месте, в Rust; объект `Device` держит состояние под `Mutex`, байты передаются как `Vec<u8>`. Упоминание `core.udl` в `ARCHITECTURE.md` §6.4 предлагается заменить на «публичный API описан макросами uniffi».
6. **Хранилище состояния.** В спайке — только память, причём `MemoryStorage` из `openmls_rust_crypto` держит ключи в `HashMap<Vec<u8>, Vec<u8>>` без `zeroize`. В crypto-core состояние MLS хранится через трейт `StorageProvider` поверх SQLCipher-базы клиента (ARCHITECTURE §4.9) с обнулением ключей в памяти (правило `CLAUDE.md`); выбор между собственной реализацией и `openmls_sqlite_storage` — в B03.
7. **Масштаб.** Группа в 1 000 устройств работает; состояние участника, Welcome и commit растут линейно (см. отчёт). Худший случай размеров — дерево с пустыми родительскими узлами после одного большого Add; регулярные self-update (суточная ротация эпохи по ADR-0004) его сглаживают. Для больших каналов B02 решает, оставлять ли дерево в Welcome или отдавать его отдельно с сервера.

## Последствия

- B02 описывает протокол DS по п. 3–4, проверку credential на клиенте и правила ротации; B03 реализует crypto-core на закреплённых версиях.
- CI crypto-core должен собирать `aarch64-linux-android` (Android NDK на хосте сборки) и `aarch64-apple-ios` (Xcode); привязки Kotlin/Swift генерируются при сборке и в git не хранятся. Без NDK собирается только `staticlib`. Разработка и проверка идут нативно на macOS; dev-контейнер не нужен.
- `openmls` 0.9.2 вышла за 11 дней до спайка: нужно следить за patch-релизами и записями безопасности. В графе зависимостей есть `crypto-bigint` 0.5 с advisory о timing (через P-256, который ciphersuite 0x0001 не использует) — B03 отслеживает обновление `hpke-rs`.
- Web-fallback через `wasm-bindgen` спайком не проверялся — отдельная проверка в B03.
- Требования к crypto-core из security-ревью спайка: свой `StorageProvider` с обнулением значений (`zeroize`) и SQLCipher `secure_delete`; `Zeroizing` для секретов в API и запрет сырого exporter в renderer (только фиксированный список меток); у объектов с ключами нет `Debug`; стабильные коды ошибок без фрагментов входа, отдельный код для дубликата; недоверенный вход из FFI копируется; `cargo fuzz` для разбора сообщений, Welcome, KeyPackage и `external_senders`; клиент и DS ограничивают `Lifetime` KeyPackage сверху; паддинг application message (`padding_size`) — решение B02.
- Первая запись `crypto-core/SECURITY-CHANGELOG.md` в B03 ссылается на этот ADR и отчёт спайка; для `spikes/` журнал не ведётся.
- Electron 33 к концу 2026 вне поддержки: продукт берёт поддерживаемую ветку (ADR-0007 допускает «33+»); npm-зависимости демо закрепляются lockfile.

## Рассмотренные альтернативы

- `MIXED_CIPHERTEXT` (входящие открытые handshake от участников): проверено, что для предложений сервера не нужна; только расширяет, что сервер может увидеть. Отклонено.

- `openmls` 0.8.3: трейты провайдера 0.5, в спайке не собиралась; взята актуальная линия 0.9, на которой будет жить crypto-core.
- Open handshake-сообщения всегда (`MIXED_PLAINTEXT`): проще для DS, но раскрывает серверу состав предложений участников. Отклонено; открытыми остаются только предложения самого сервера.
- UDL-файл для uniffi: второй источник правды для сигнатур. Отклонено в пользу proc-macro.
- Дерево без ratchet tree extension (новичок запрашивает дерево у сервера): уменьшает Welcome, но добавляет запрос и состояние на сервере. Решение отложено до B02.
