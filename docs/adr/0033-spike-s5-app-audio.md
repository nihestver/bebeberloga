# ADR-0033: Результаты спайка S5 — звук приложения и захват видео

- Статус: Черновик (ждёт прогонов на стенде pc-stand под Windows и Linux)
- Дата: 2026-11-24
- Связано: [ADR-0008](0008-stream-media-engine.md), [ADR-0009](0009-platform-minimums.md); `docs/spec/ARCHITECTURE.md` §6.5; `docs/spec/FLOWS/08-stream.md`; `docs/spec/SCREENS/05-voice-and-stream.md` §4; отчёт [`spikes/05-app-audio/REPORT.md`](../../spikes/05-app-audio/REPORT.md); вопросы №70 и №71 в `docs/spec/OPEN-QUESTIONS.md`; промпты S6, B12, B13

## Контекст

ADR-0008 выбрал для стрима собственный захват: звук процесса и всех его дочерних процессов, видео по цепочке методов ОС. ADR-0009 задал минимальные версии ОС. Спайк S5 проверяет это на трёх ОС: кто попадает в звук приложения, есть ли пропуски за 10 минут, каков рассинхрон звука и видео по единой шкале времени.

На момент черновика проверены macOS (MacBook Pro M4 Pro, macOS 26.4.1), звук на Linux в контейнере без железа (PipeWire 1.4.2) и Windows на стенде pc-stand пробным прогоном (основной сценарий 30 с). Полный прогон Windows и Linux на железе впереди: пункты, которые от них зависят, помечены.

## Решение

Для S6, B12 и B13 фиксируется:

1. **macOS, звук приложения — ScreenCaptureKit с фильтром по окну**, одним потоком со звуком и видео, с исключением собственного процесса. Фильтр «дисплей + приложение» даёт тот же состав звука, но требует второго потока для видео окна. За 10 минут — ни разрыва шкалы времени, ни потерянного сэмпла; формат — 48 кГц, стерео, float32.
2. **macOS, новый процесс приложения — второй поток и склейка.** Состав процессов поток определяет при запуске: процесс, появившийся позже, в звук не попадает, обновление фильтра на ходу этого не меняет. Клиент сам перезапускает захват звука (ответ владельца на вопрос №71): запускает второй поток, не останавливая первый, и стыкует их по меткам времени. Провала при этом нет; простой перезапуск дал бы 120–145 мс тишины. Как media-engine узнаёт о новом процессе — решает B12.
3. **Клиент не даёт экрану гаснуть, пока идёт стрим** (ответ владельца на вопрос №70). При выключенном дисплее macOS не отдаёт кадры захвата совсем, звук при этом идёт. Если экран всё же выключился (блокировка, закрытая крышка), зрители видят заглушку «Стрим приостановлен», звук продолжается.
4. **Linux, чей узел — по двум свойствам.** PID берётся из свойства узла `application.process.id`, а если его нет — из `pipewire.sec.pid` клиента узла. У клиентов через слой ALSA и у клиентов самого PipeWire первого свойства нет; у клиентов протокола PulseAudio второе указывает на службу `pipewire-pulse`.
5. **Linux, захват — собственный узел PipeWire без автоподключения**, связи с узлами нужных процессов создаёт media-engine по событиям реестра, сопоставляя порты по имени канала. Узел, появившийся во время стрима, подключается так же, как существовавший при старте.
6. **Метки времени — от ОС, на одной монотонной шкале для звука и видео.** Критерий рассинхрона — 95-й процентиль модуля не больше 40 мс. На macOS метка звука стабильно позже метки видео примерно на 25 мс; постоянный сдвиг media-engine вычитает, его величина измеряется для каждой ОС.
7. **Тишина и разрывы определяются по меткам времени буферов**, а не по счёту сэмплов: так стык двух потоков и пропуск видны одинаково на всех ОС.
8. **macOS, частота кадров.** ScreenCaptureKit с пределом 60 к/с отдаёт 90–98 % кадров источника, с пределом 120 к/с — повторы. Отбор кадров под целевую частоту делает media-engine; способ выбирает S6.
9. **Windows, звук приложения — WASAPI process loopback с деревом процессов.** По пробному прогону на стенде: звук снимается до регулятора громкости (полный уровень при mute и при громкости 0); процесс, запущенный во время захвата, попадает в звук без перезапуска, но поток в этот момент замирает на 15–19 мс без флага разрыва. Запасных ступеней две: система без собственного процесса (тот же API) и loopback устройства вывода — он зависит от громкости, молчит при mute, окрашен обработкой драйвера и своего процесса не исключает. Видео: WGC отдаёт 94–97 % кадров при 60 к/с, DXGI и GDI — 99,7 %; координаты и размеры — в физических пикселях. Пункт уточняется после полного прогона.
10. **Linux на железе** — после прогона на стенде: видео через портал в сеансах Wayland и X11, список окон X11, звук со звуковой картой.

## Последствия

- `ARCHITECTURE.md` §6.5, `FLOWS/08-stream.md` и `SCREENS/05-voice-and-stream.md` требуют правок по ответам на №70 и №71 и по пункту 4; список — в отчёте спайка, раздел «Что передать дальше». Правки вносятся отдельным PR после спайка.
- B12 получает три обязанности сверх плана: следить за новыми процессами приложения на macOS, удерживать экран на время стрима, склеивать потоки звука по меткам времени.
- B13 показывает зрителям заглушку «Стрим приостановлен».
- Лицензия «Apache-2.0 WITH LLVM-exception» разрешена только у `target-lexicon` — зависимости времени сборки привязок PipeWire (`LICENSING.md`, решение владельца от 2026-11-24).
- Linux без PipeWire (monitor-источник PulseAudio) спайк не проверял: fallback из ADR-0009 остаётся непроверенным допущением.

## Рассмотренные альтернативы

- macOS, обновление фильтра работающего потока: состав звука не меняет.
- macOS, остановка и повторный запуск того же потока: работает, но даёт провал звука 120–145 мс; по ответу на №71 допустима только как запасной вариант.
- Linux, поиск узлов только по `application.process.id`: не находит узлы клиентов ALSA и PipeWire.
- Linux, решение «моно или стерео» по числу портов узла: порты приходят по одному, получаются лишние связи.
