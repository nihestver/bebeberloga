# ADR-0033: Результаты спайка S5 — звук приложения и захват видео

- Статус: Черновик (ждёт прогона на стенде pc-stand под Linux)
- Дата: 2026-11-25
- Связано: [ADR-0008](0008-stream-media-engine.md), [ADR-0009](0009-platform-minimums.md); `docs/spec/ARCHITECTURE.md` §6.5; `docs/spec/FLOWS/08-stream.md`; `docs/spec/SCREENS/05-voice-and-stream.md` §4; отчёт [`spikes/05-app-audio/REPORT.md`](../../spikes/05-app-audio/REPORT.md); вопросы №70–72 в `docs/spec/OPEN-QUESTIONS.md`; промпты S6, B12, B13

## Контекст

ADR-0008 выбрал для стрима собственный захват: звук процесса и всех его дочерних процессов, видео по цепочке методов ОС. ADR-0009 задал минимальные версии ОС. Спайк S5 проверяет это на трёх ОС: кто попадает в звук приложения, есть ли пропуски за 10 минут, каков рассинхрон звука и видео по единой шкале времени.

На момент черновика полными прогонами (основной сценарий — 10 минут) проверены macOS (MacBook Pro M4 Pro, macOS 26.4.1) и Windows (стенд pc-stand: Windows 11 Pro, NVIDIA, экран 60 Гц, масштаб 125 %); звук на Linux — в контейнере без железа (PipeWire 1.4.2). Linux на железе впереди: пункт, который от него зависит, помечен.

## Решение

Для S6, B12 и B13 фиксируется:

1. **macOS, звук приложения — ScreenCaptureKit с фильтром по окну**, одним потоком со звуком и видео, с исключением собственного процесса. Фильтр «дисплей + приложение» даёт тот же состав звука, но требует второго потока для видео окна. За 10 минут — ни разрыва шкалы времени, ни потерянного сэмпла; формат — 48 кГц, стерео, float32.
2. **macOS, новый процесс приложения — второй поток и склейка.** Состав процессов поток определяет при запуске: процесс, появившийся позже, в звук не попадает, обновление фильтра на ходу этого не меняет. Клиент сам перезапускает захват звука (ответ владельца на вопрос №71): запускает второй поток, не останавливая первый, и стыкует их по меткам времени. Провала при этом нет; простой перезапуск дал бы 120–145 мс тишины. Как media-engine узнаёт о новом процессе — решает B12.
3. **Клиент не даёт экрану гаснуть, пока идёт стрим** (ответ владельца на вопрос №70). При выключенном дисплее macOS не отдаёт кадры захвата совсем, звук при этом идёт. Если экран всё же выключился (блокировка, закрытая крышка), зрители видят заглушку «Стрим приостановлен», звук продолжается.
4. **Linux, чей узел — по двум свойствам.** PID берётся из свойства узла `application.process.id`, а если его нет — из `pipewire.sec.pid` клиента узла. У клиентов через слой ALSA и у клиентов самого PipeWire первого свойства нет; у клиентов протокола PulseAudio второе указывает на службу `pipewire-pulse`.
5. **Linux, захват — собственный узел PipeWire без автоподключения**, связи с узлами нужных процессов создаёт media-engine по событиям реестра, сопоставляя порты по имени канала. Узел, появившийся во время стрима, подключается так же, как существовавший при старте.
6. **Метки времени — от ОС, на одной монотонной шкале для звука и видео.** Критерий рассинхрона — 95-й процентиль модуля не больше 40 мс. На macOS метка звука стабильно позже метки видео примерно на 25 мс; постоянный сдвиг media-engine вычитает, его величина измеряется для каждой ОС. На Windows метка звука process loopback на 35 мс позже момента воспроизведения, а метка кадра WGC — планируемый момент показа; между собой они расходятся в среднем на 9 мс при p95 17 мс. Рассинхрон измеряется на отрезке в несколько минут: за полминуты положение кадра относительно развёртки экрана не успевает измениться.
7. **Тишина и разрывы определяются по меткам времени буферов**, а не по счёту сэмплов: так стык двух потоков и пропуск видны одинаково на всех ОС.
8. **macOS, частота кадров.** ScreenCaptureKit с пределом 60 к/с отдаёт 90–98 % кадров источника, с пределом 120 к/с — повторы. Отбор кадров под целевую частоту делает media-engine; способ выбирает S6.
9. **Windows, звук приложения — WASAPI process loopback с деревом процессов.** За 10 минут — ни разрыва шкалы времени, ни потерянного сэмпла; формат — 48 кГц, стерео, float32, буферы по 10 мс. Звук снимается до регулятора громкости: полный уровень при mute и при громкости 0. Процесс, запущенный во время захвата, попадает в звук без перезапуска; поток в этот момент замирает на 11–19 мс без флага разрыва, в одном прогоне из трёх при этом потерян буфер 10 мс — media-engine закрывает такой разрыв по меткам времени (пункт 7).
10. **Windows, запасные ступени звука — две.** Первая — система без собственного процесса: тот же API с исключением дерева своего процесса. Вторая — loopback устройства вывода: он зависит от громкости, молчит при mute, окрашен обработкой драйвера и своего процесса не исключает — в стрим попал бы и звук звонка. Использовать ли вторую ступень и что при этом видит стример — вопрос №72; до ответа media-engine её не включает.
11. **Windows, видео — цепочка WGC → DXGI → GDI работает**, координаты и размеры — в физических пикселях. WGC отдаёт 94–97 % кадров при 60 к/с (одиночные пропуски) и все кадры при 30 к/с; DXGI и GDI — все. Наименьший интервал обновления WGC остаётся по умолчанию: значение 1 мс недобор не убирает. Отбор кадров под целевую частоту — в media-engine (S6). У окна без собственной иконки берётся иконка исполняемого файла.
12. **Linux на железе** — после прогона на стенде: видео через портал в сеансах Wayland и X11, список окон X11, звук со звуковой картой.

## Последствия

- `ARCHITECTURE.md` §6.5, `FLOWS/08-stream.md` и `SCREENS/05-voice-and-stream.md` требуют правок по ответам на №70 и №71 и по пунктам 4, 9 и 10; список — в отчёте спайка, раздел «Что передать дальше». Правки вносятся отдельным PR после спайка.
- B12 получает три обязанности сверх плана: следить за новыми процессами приложения на macOS, удерживать экран на время стрима, склеивать потоки звука по меткам времени.
- B13 показывает зрителям заглушку «Стрим приостановлен».
- Лицензия «Apache-2.0 WITH LLVM-exception» разрешена только у `target-lexicon` — зависимости времени сборки привязок PipeWire (`LICENSING.md`, решение владельца от 2026-11-24).
- Причина недобора кадров WGC при 60 к/с не установлена; S6 проверяет размер пула кадров и работу в обработчике кадра.
- Linux без PipeWire (monitor-источник PulseAudio) спайк не проверял: fallback из ADR-0009 остаётся непроверенным допущением.

## Рассмотренные альтернативы

- macOS, обновление фильтра работающего потока: состав звука не меняет.
- macOS, остановка и повторный запуск того же потока: работает, но даёт провал звука 120–145 мс; по ответу на №71 допустима только как запасной вариант.
- Windows, loopback устройства вывода как основной путь звука: зависит от громкости, молчит при mute и не исключает собственный процесс.
- Windows, наименьший интервал обновления WGC 1 мс: доля кадров не выросла.
- Linux, поиск узлов только по `application.process.id`: не находит узлы клиентов ALSA и PipeWire.
- Linux, решение «моно или стерео» по числу портов узла: порты приходят по одному, получаются лишние связи.
