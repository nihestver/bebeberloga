# ADR-0003: Лицензии компонентов

- Статус: Принято
- Дата: 2026-11-02
- Связано: PLAN.md разделы 2, 10; `LICENSING.md`

## Контекст

Проект open source. Нужно защитить две вещи: сервер — от закрытых SaaS-форков, клиенты — от закрытых сборок, в которых пользователь не может проверить E2EE. При этом crypto-core и SDK должны свободно встраиваться в чужие клиенты и боты. iOS-клиент распространяется через App Store, чьи условия конфликтуют с «чистой» GPL.

## Решение

| Компонент | Лицензия |
|---|---|
| Сервер, deploy | AGPL-3.0-or-later |
| Клиенты (web, desktop, android, ios) | GPL-3.0-or-later с дополнительным разрешением по §7 GPLv3 (App Store exception): разрешено распространение через App Store, Google Play и другие магазины, чьи условия добавляют ограничения. Текст — `clients/LICENSE-EXCEPTION`; SPDX: `GPL-3.0-or-later WITH LicenseRef-Bebeberloga-AppStore-exception` |
| crypto-core, media-engine, proto, sdk | Apache-2.0 |
| Документация | CC BY-SA 4.0 |

CLA не требуется — DCO (`Signed-off-by`). Автоматические проверки: REUSE-линт, `cargo deny`, `go-licenses`, `license-checker`.

## Последствия

- Без CLA переиздать клиенты под другой лицензией нельзя — поэтому исключение для магазинов добавляется сразу, а не потом.
- Меньше корпоративных контрибьюторов в клиенты; для библиотек это не так.
- Текст исключения нужно написать при создании репозитория.

## Рассмотренные альтернативы

- MIT/Apache-2.0 для всего: максимум распространения, но закрытый форк клиента может незаметно сливать ключи, и пользователь этого не проверит.
- MPL-2.0 для клиентов: компромисс, если GPL + исключение окажется неудобной для iOS.
- Apache-2.0 для сервера: шире принятие бизнесом, слабее защита от закрытых SaaS. Отклонено.
