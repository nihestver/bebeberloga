# ADR-0024: Результаты спайка S3 — Chromium-путь стрима в Electron

- Статус: Принято 2026-11-11
- Дата: 2026-11-11
- Связано: [ADR-0007](0007-desktop-shell-electron.md), [ADR-0008](0008-stream-media-engine.md), [ADR-0009](0009-platform-minimums.md); `docs/spec/ARCHITECTURE.md` §6.5; `docs/spec/SCREENS/05-voice-and-stream.md` §4; отчёт [`spikes/03-electron-capture/REPORT.md`](../../spikes/03-electron-capture/REPORT.md); промпты S6, B13

## Контекст

ADR-0008 оставил Chromium-путь (`desktopCapturer` + `getDisplayMedia` + `livekit-client`) запасным для всех платформ и основным для Windows с GPU AMD и Intel в 1.0. Спайк S3 проверил этот путь на Electron 45: список источников и захват, публикацию в LiveKit с E2EE кадров, задержку и нагрузку для 720p30, 1080p30 и 1080p60, поведение macOS без разрешения «Запись экрана» и Linux на Wayland. Числа и условия замеров — в отчёте; замеры сделаны на одной машине, без сети.

## Решение

Для S6 и B13 фиксируется:

1. **Путь пригоден как запасной.** На macOS (Apple M4 Pro) все три пресета держатся без фризов; задержка «экран → зритель» без сети — 44–66 мс в среднем. E2EE добавляет до 2,4 мс к средней задержке и до 1,5 % ядра стримеру и не снимает аппаратное кодирование. Числа E2EE — по 10 парам прогонов, сделанных подряд; 3 пары с повторёнными позже прогонами не учтены (отчёт, «Добавка E2EE»; все 13 пар — в `results/summary.md`).
2. **Выбор источника зависит от ОС.**
   - Windows и macOS 13–14 — собственная сетка по SCREENS/05 §4 на `desktopCapturer.getSources`.
   - macOS 15 и новее — системный пикер (`useSystemPicker`); решение владельца от 2026-11-10. Граница «с macOS 15» взята из документации Electron: спайк проверил пикер только на macOS 26.4.1 (выбор окна в пределах 10 с даёт поток 1920×1080 с E2EE). Как это соотносится с переключателем «использовать системный выбор источника захвата» (SCREENS/04, «Стриминг») и каково его значение по умолчанию, уточняет контур A в вопросе №31.
   - Linux на Wayland — только системное окно выбора (портал). `getSources` вызывается один раз по нажатию «Выбрать через систему»; обработчик `getDisplayMedia` берёт источник из полученного списка и не запрашивает список повторно.
3. **Обработчик `getDisplayMedia`** живёт в main-процессе: окно передаёт идентификатор выбранного источника, обработчик отвечает этим источником. Отмену выбора и 10-секундный таймаут системного пикера клиент отличает от сбоя захвата; что при этом видит пользователь — вопрос №33 в `docs/spec/OPEN-QUESTIONS.md`.
4. **Кодек на Chromium-пути.** H.264 в связке `livekit-client` + LiveKit согласуется с профилем `42e01f`, который Chromium на macOS кодирует программно; аппаратный энкодер берёт `42001f` и H.265. Причина одна — профиль: `scalabilityMode` для H.264 `livekit-client` 2.23 не задаёт (в его исходниках режим выставляется только VP9 и AV1), а значение `L1T1` в статистике сообщает сам программный энкодер. Временные слои (`L1T3`) увели бы H.264 на программный энкодер и при профиле `42001f`, поэтому S6, добиваясь `42001f`, не включает для H.264 `L1T3`. До решения S6:
   - H.265 — первым, если его декодируют все смотрящие (ARCHITECTURE §6.5, «Кодирование и транспорт», п. 2);
   - иначе H.264 программный. По FLOWS/08 («Начать стрим», п. 3) пресет по умолчанию без аппаратного кодирования — «Баланс 1080p30», а ARCHITECTURE §6.5 («Кодирование и транспорт», п. 1) требует для программного кодека автоматического понижения пресета: если критерий FLOWS/08 — фактическое аппаратное кодирование на выбранном пути, пресет по умолчанию здесь «Баланс», а не «Плавность» (уточняет S6 вместе с порогом автоснижения);
   - AV1 на этом пути не предлагается: с E2EE `livekit-client` его не публикует.
   S6 проверяет энкодер на Windows с AMD и Intel именно через `livekit-client` и решает, как согласовать `42001f`.
5. **Звук на Chromium-пути — только звук всей системы** (`audio: 'loopback'`); звук одного приложения остаётся за media-engine (ADR-0008 не меняется). Системный звук проверен на Linux и на macOS 26.4 в упакованном приложении с разрешением «Запись экрана и системного звука»: стерео 48 кГц, публикуется с E2EE. Клиент запрашивает дорожку без обработки и в стерео явными ограничениями и сразу проверяет её `readyState`: на macOS отказ выглядит как дорожка, пришедшая завершённой. **В системный звук попадает и звук самого клиента** — голоса звонка; без исключения собственного звука (ограничение `restrictOwnAudio`, проверяют S6 и B13) включать эту дорожку в стрим из звонка нельзя; что при этом видит пользователь — вопрос №35 в `docs/spec/OPEN-QUESTIONS.md`.
6. **Разрешение «Запись экрана» на macOS.** Статус читается до показа окна выбора; без разрешения сетки нет — только `EmptyState` с кнопкой настроек (SCREENS/05 §4.2). В спайке при выдаче разрешения система сама завершала и заново открывала приложение, и новый процесс стартовал без состояния прежнего. FLOWS/08 описывает перезапуск иначе (его предлагает клиент); что видит пользователь до и после перезапуска — вопрос №34 в `docs/spec/OPEN-QUESTIONS.md`, спайк поведения не назначает.
7. **Постоянная подпись сборок macOS; способ (Developer ID или иной) — решение B17 ч.2.** С подписью ad hoc каждая пересборка лишает приложение выданного разрешения, а переключатель в настройках этого не показывает. Для dev-сборок в документации разработчика — сброс записи через `tccutil reset`.
8. **Пресет — рамка, а не точный размер.** Разрешение пресета задаётся как максимум по ширине и высоте; кадр сохраняет пропорции источника. В статистике показывается фактическое разрешение отправки.

## Последствия

- B13 реализует три варианта выбора источника; сетка SCREENS/05 §4 на Wayland не показывается, на macOS 15+ её место занимает системный пикер (уточнение значения по умолчанию — вопрос №31).
- На Wayland панель стрима не получает ни названия окна, ни иконки приложения, а монитор не отличить от окна — вопрос №32 в `docs/spec/OPEN-QUESTIONS.md`.
- Формулировка ARCHITECTURE §6.5 о системном пикере «на 14+» требует правки для Chromium-пути — вопрос №31.
- Лицензия BlueOak-1.0.0 у транзитивных пакетов `@electron/packager` — вопрос закрыт решением владельца от 2026-11-11: вместе с CC-BY-4.0 она разрешена только у инструментов разработки и сборки (`LICENSING.md`, строка «только инструменты»; ADR-0023 п. 6).
- Довод ADR-0008 об аппаратном кодировании в Chromium на Windows остаётся непроверенным допущением до S6. Если профиль `42e01f` и там уходит на программный энкодер, основной путь для AMD и Intel в 1.0 нужно пересмотреть.
- Стрим на этом пути первые 12–15 с идёт в сниженном разрешении: S6 подбирает стартовый битрейт и режим деградации.
- B17 ч.2 выбирает способ постоянной подписи macOS-сборок и закладывает ключ `NSAudioCaptureUsageDescription` в `Info.plist`.
- Размер сборки подтверждает оценку ADR-0007: 114 МБ в zip, 252 МБ распакованной; код приложения — меньше 1 МБ.

## Не закрыто спайком

- Исключение собственного звука клиента из системного звука (`restrictOwnAudio`); появляется ли доступ к записи экрана без перезапуска; вариант без ключа `NSAudioCaptureUsageDescription`.
- Windows целиком; macOS 13–15 и Intel Mac; GNOME, X11 без Wayland и система без PipeWire; несколько мониторов.
- Задержка через сеть, потери, VMAF, 30 минут 1080p60.

## Рассмотренные альтернативы

- Собственная сетка на macOS 15+ вместо системного пикера: работает, но системный пикер даёт выбор «все окна приложения» и привычное пользователю окно. Решение владельца — системный пикер.
- Сетка на Wayland через повторные вызовы `getSources`: каждый вызов открывает системное окно. Отклонено.
- Режим X11 (`--ozone-platform=x11`) в сеансе Wayland, чтобы получить список окон: портал не обходит и добавляет ещё один запрос. Отклонено.
- VP9 на Chromium-пути: только программный, 53 % ядра на 1080p60 против 37 % у H.264. Отклонено.
- Правка профиля H.264 в клиенте через `setCodecPreferences`: в спайке не сработала; вопрос передан S6.
