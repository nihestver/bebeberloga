# ADR-0010: Мобильные клиенты — нативные, после 1.0

- Статус: Принято
- Дата: 2026-11-02
- Связано: PLAN.md разделы 1, 3.5–3.6, 6.3, 9

## Контекст

Ключевые функции MVP — E2EE, стрим с десктопа и soundboard — десктопные. Мобильный клиент не входит в MVP, но архитектура должна быть к нему готова. Выбор между нативными клиентами и единой кроссплатформенной базой (Flutter, React Native) влияет на размер команды и сроки.

## Решение

- В 1.0 мобильных клиентов нет. После 1.0: **Android** (Kotlin, Jetpack Compose, `livekit-android`, crypto-core через uniffi, Room/SQLCipher, UnifiedPush + FCM) — первым; **iOS** (Swift, SwiftUI, `livekit-swift`, CallKit/PushKit, Notification Service Extension) — следом, опционально.
- Архитектура остаётся готовой: crypto-core с uniffi-биндингами, общие Protobuf-схемы, протокол gateway без десктоп-специфики. Спайк 1 проверяет сборку crypto-core под Android и iOS только как переносимость.
- Функции, зависящие от мобильных клиентов (просмотр стрима на телефоне, push для Android, APNs), имеют приоритет S и реализуются вместе с клиентами.

## Последствия

- Дорожная карта до 1.0 сокращается до шести фаз (50–60 недель).
- Нативные клиенты дают лучший UX, фоновые звонки и расшифровку пушей, но удваивают мобильный код.

## Рассмотренные альтернативы

- Flutter + flutter_rust_bridge: одна база для всех платформ, есть Dart-биндинги OpenMLS; но нет веба как бонуса и сложнее плотные списки. Запасной вариант, если команда захочет одну базу.
- React Native + livekit-react-native: переиспользование TS-кода с веба; производительность длинных списков и мосты к Rust — риск.
- Kotlin Multiplatform для Android + iOS: возможно в v2, iOS-часть ещё сырая.
