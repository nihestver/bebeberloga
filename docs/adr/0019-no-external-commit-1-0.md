# ADR-0019: Без external commit в 1.0 — вход только через Add сервера, пересоздание группы при рассинхроне

- Статус: Принято 2026-11-03 (владелец, решение Р3 промпта B02); частично изменено ADR-0021
- Дата: 2026-11-03
- Частично изменяет: [ADR-0004](0004-e2ee-mls-sframe.md) п. 2, [ADR-0015](0015-history-visible-to-members.md) «Последствия», [ADR-0016](0016-spike-s1-openmls-ffi.md) п. 2–3, [ADR-0018](0018-spike-s4-mls-ds.md) п. 4, п. 7 и «Последствия»
- Связано: `docs/spec/ARCHITECTURE.md` §4.3, §5.1; `docs/spec/FLOWS/02-new-device.md`, `04-invite-join.md`; `docs/spec/SCREENS/08-messages.md` §1, §8; [`docs/protocol/CRYPTO.md`](../protocol/CRYPTO.md) §2

## Контекст

ARCHITECTURE §4.3 предусматривал внешний вход (external commit, RFC 9420 §12.4.3.2) для быстрого присоединения, когда никого из участников нет в сети: присоединяющийся коммитит сам по GroupInfo, который сервер хранит зашифрованным, а ключ к нему «раздаётся участникам канала». При проектировании `CRYPTO.md` (B02) выяснилось:

1. **Ключ к GroupInfo негде взять тому, кому вход нужнее всего.** Новый участник ещё не состоит ни в одной группе канала, поэтому ключа у него нет. Раздать ключ «участникам канала» вне MLS-группы можно только через сервер или ещё один секрет (например, в ссылке-приглашении), и оба пути не защищают от того, от кого шифрование GroupInfo должно было защищать.
2. **Шифрование GroupInfo почти ничего не даёт против сервера.** Сервер и так может добавить любое устройство Add-предложением как external sender (ADR-0004 п. 2). Клиент проверяет external commit и Add одинаково (credential, подпись ключом идентичности, доступ к каналу — ADR-0016 п. 3), а эти данные приходят от того же сервера. GroupInfo не содержит секретов эпохи: дерево и ключи листьев — открытые данные.
3. **Цена хранения.** Чтобы external commit был возможен, каждый commit должен выгружать новый GroupInfo с деревом — 100–180 байт на лист по замерам S1 и S4 плюс около 90 байт credential проекта (`CRYPTO.md` §1.3): порядка 1–1,4 МБ на commit в группе из 5 000 листьев.
4. **Поверхность атак.** External commit — ещё один путь входа со своей политикой, своим видом сообщения (`PublicMessage` от `new_member_commit`) и своими гонками с отменой входа и ожидающим Remove (находки S4 N5, Б11). Спайк S4 его по умолчанию не принимал; спайк S1 не проверял вовсе.
5. Возврат устройства, которое было офлайн дольше горизонта (ADR-0018 п. 4), и восстановление после рассинхрона (ADR-0016 п. 4, ADR-0018 п. 2) можно сделать без external commit — теми же Add/Remove сервера и пересозданием группы.

## Решение

1. **External commit в 1.0 не используется.** Клиент его не создаёт и не принимает; DS отвечает на `HANDSHAKE_KIND_EXTERNAL_COMMIT` кодом `EXTERNAL_COMMIT_UNSUPPORTED`.
2. **GroupInfo сервер не хранит и не публикует.** Поля и операции контракта для зашифрованного GroupInfo остаются в схемах с пометкой `deprecated` и «не используется в 1.0» (правило совместимости `buf breaking`).
3. **Любой вход в группу — Add-предложение сервера и commit онлайн-участника, которого назначает DS** (ADR-0018 п. 7). При подтверждении нового устройства DS в первую очередь назначает коммитером подтвердившее устройство того же пользователя (FLOWS/02 ш. 4.4). Если в группе сейчас никого нет в сети, вход ждёт; интерфейс показывает «Подключаемся к каналу…» (SCREENS/08 §1, §8; FLOWS/04 ш. 3).
4. **Устройство, не подключавшееся дольше горизонта офлайна, возвращается через Remove старого листа и Add со свежим KeyPackage** в одном commit-е; старые commit-ы оно не обрабатывает. Горизонт, его связь со сроком KeyPackage и запасной критерий на клиенте — `CRYPTO.md` §2.
5. **Рассинхрон устраняется по жалобе честного клиента, и сначала — самым дешёвым способом.** Личная жалоба (commit не расшифровался у одного клиента, срок пакета по его часам) и жалоба на commit, поверх которого группа уже ушла дальше, лечатся возвратом одного пожаловавшегося устройства — парой Remove + Add, без заморозки. Структурная жалоба на последний commit запускает проверку: DS приостанавливает handshake (не сообщения) и собирает мнения других пользователей. Если commit приняли другие, а жалуется один, — возврат пожаловавшегося; если жалуются несколько или группа маленькая (до 50 листьев), — **пересоздание группы канала** с новым `group_id`: DS замораживает старую группу, назначенный участник создаёт новую с составом по карте DS (все Remove и отменённые входы старой группы выполнены), остальные проверяют её законность и входят по Welcome. Сверх лимита пересозданий группа не замораживается: в состоянии «ошибка ключей» остаются только пожаловавшиеся. При потере журнала DS пересоздание допускает откат эпох, но каждый клиент проверяет, что в новую группу не вернулось ни одно устройство, которое он знает удалённым. Ключи истории привязаны к каналу, а не к группе (ADR-0015), поэтому история продолжается. Процедура, правила вердикта и лимиты — `CRYPTO.md` §2.9–§2.10.
6. **Связку ключей истории всегда обновляет автор commit-а** тем же запросом, что и commit (ADR-0015). Случая «участник добавил себя сам» в 1.0 нет.

## Последствия

- Новичок в канале, где сейчас никого нет в сети, ждёт первого вышедшего в сеть участника. Для каналов сообществ с живыми участниками и для нового устройства, подтверждённого с другого своего устройства, задержки нет: коммитит подтвердившее устройство.
- Новое устройство, подтверждённое ключом восстановления, когда других устройств нет в сети, подключает каналы и ЛС по мере появления их участников (FLOWS/02 ш. 5).
- DS проще: нет склада GroupInfo, нет второго вида входа, нет гонок external commit с отменой входа и с ожидающим Remove. Каждый commit не выгружает дерево.
- Пересоздание группы — самая дорогая операция протокола: при 5 000 листьях — около 2 МБ commit-а у создателя и 1–1,4 МБ Welcome на каждое устройство, 5–7 ГБ исходящего трафика DS на одно пересоздание (оценка — `CRYPTO.md` §2.10.9). Поэтому пересоздание идёт только по подтверждённой жалобе и с лимитом частоты на DS и на клиенте.
- **Принятый риск доступности** (`CRYPTO.md` §8.2 п. 1). Один злонамеренный участник при живых участниках, принимающих commit-ы, вызывает только возвраты своего устройства и паузы handshake до 30 с: не больше 24 в сутки на группу, сообщения не страдают. В большой группе, где сейчас больше никто не высказывается, или вдвоём со сообщником он может вызвать до 3 пересозданий в сутки на канал (до 15–21 ГБ исходящего трафика DS при 5 000 листьях). Сверх лимита канал не замораживается. Сообщник, подтвердивший дефектный commit, может оставить одного честного жалобщика в «ошибке ключей», но не заставить его принять дефект. Ответ на злоупотребление — журнал жалоб на DS и модерация.
- Контракт: `HANDSHAKE_KIND_EXTERNAL_COMMIT`, `Group.has_group_info`, `EncryptedGroupInfo`, `encrypted_group_info`, `GET /mls/groups/{id}/group-info`, `PUT /mls/groups/{id}/history-key-bundle` и `MlsUpdateRequested.REASON_HISTORY_BUNDLE` помечены `deprecated`; новый код `EXTERNAL_COMMIT_UNSUPPORTED`; добавлены назначенный коммитер, жалоба на commit, пересоздание и возврат устройства (`CRYPTO.md` §2, `REST.md`, `GATEWAY.md`).

## Условия пересмотра

Решение пересматривается, если:
- появятся мобильные клиенты (ADR-0010): телефоны реже бывают в сети, и ожидание входа станет заметнее;
- пользователи инстансов будут жаловаться на ожидание входа в каналы, где никого нет в сети.

Возврат external commit оформляется **отдельным ADR**: с источником ключа к GroupInfo для тех, кто ещё не в группе, политикой приёма на клиенте и DS, ценой выгрузки дерева и проверкой гонок с отменой входа и с ожидающим Remove (S4 N5).

## Рассмотренные альтернативы

- **External commit с ключом к GroupInfo, выведенным из ключа истории канала.** Работает только для тех, кто уже был участником (возврат устройства, рассинхрон), а новичкам, ради которых вход и задумывался, не помогает. Цена выгрузки дерева на каждом commit-е остаётся. Отклонено.
- **Секрет к GroupInfo в ссылке-приглашении (во фрагменте URL).** Не покрывает новые устройства, приглашения друзей в ЛС и вход по ролям; ссылка полупубличная, а политика приёма на клиенте всё равно опирается на данные сервера. Отклонено.
- **Открытый (незашифрованный) GroupInfo.** Против сервера не хуже зашифрованного (п. 2 «Контекста»), но сохраняет цену выгрузки дерева и второй путь входа со своими гонками. Отклонено для 1.0; остаётся кандидатом при пересмотре.
- **Восстановление рассинхрона откатом эпохи на DS.** Предложение сервера не привязано к GroupContext (RFC 9420 §6.1) и годится в любой ветке той же эпохи (ADR-0018 «Последствия», S4 Б12) — откат небезопасен. Отклонено в пользу пересоздания группы.
- **ReInit-предложение MLS (RFC 9420 §12.1.5).** Требует commit в той самой группе, которая рассинхронизирована. Отклонено.
