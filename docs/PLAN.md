# План разработки: self-hosted clean-room аналог Discord с E2EE

Версия плана: 2 ноября 2026. Источник правды — этот файл; изменения вносятся через ADR в `docs/adr/`.

## 1. Цели, границы и ограничения

Цель: open-source self-hosted платформа общения, функционально и визуально максимально близкая к Discord, с E2EE для всех текстов, файлов и звонков, реализованная строго по методу clean room. Объём версии 1.0 — MVP: похожий продукт без излишеств, в котором главное — E2EE для всего, включая стрим, стрим экрана/окна/приложения со звуком только этого приложения и задержкой до 1 с, и soundboard (приоритеты — раздел 3, техника стрима — раздел 6.5). Название проекта — **Bebeberloga** (решение — раздел 12); в коде, пакетах и бинарниках — `bebeberloga`.

**Что входит в v1.0**

- Сервер: (Go) для self-hosted развёртывания: один бинарник или Docker Compose.
- Desktop-клиент: Windows 10 21H2+ и 11, macOS 13+, Linux (Debian 12+ / Ubuntu 22.10+ с PipeWire: .deb, опционально: AppImage, Flatpak).
- Веб-клиент как побочный продукт desktop-кодовой базы (тот же UI, запускается в браузере).
- E2EE: личные сообщения, групповые DM, каналы серверов, файлы, голосовые/видео звонки, демонстрация экрана.
- Стрим экрана, окна или приложения (720p30–1080p60, стерео, задержка < 1 с, звук только из транслируемого приложения) и soundboard — ключевые функции 1.0.

**Что не входит в v1.0, но запланировано к реализации (отложено)**

- Bot SDK и webhooks, совместимые с E2EE (бот — полноправный участник шифрованной группы)
- Поддержка браузеров как основной платформы.
- Мобильные клиенты: нативный Android 10+ (Kotlin + Compose) первым после 1.0, затем опционально iOS (Swift + SwiftUI).

**Определения**

- *Clean room* — реализация по функциональной спецификации, написанной людьми, которые наблюдали только публичное поведение продукта, без доступа к его коду, минифицированным бандлам, утечкам, дизайн-файлам и ассетам.
- *E2EE* — ключи существуют только на устройствах пользователей; сервер хранит и маршрутизирует шифртекст и не может прочитать содержимое ни при каких условиях, включая компрометацию сервера.
- *Сервер (guild)*, *канал*, *роль*, *тред* — в своей терминологии: в интерфейсе — обычные слова «сервер», «канал», «роль», «ветка» (BRAND.md); в коде, API и схеме БД — community, channel, role, thread; внутренние имена не повторяют чужую публичную номенклатуру (Guild, Snowflake и т.п.), хотя сами паттерны данных допустимы.

**Ключевые ограничения, определяющие архитектуру**

1. E2EE делает невозможными серверные функции над содержимым: поиск, превью ссылок, automod по тексту, серверные боты «из коробки», индексация закрепов. Всё это переносится на клиент или в бота-участника (раздел 8).
2. Новый участник канала не видит историю по умолчанию (свойство forward secrecy). Нужен явный механизм «поделиться историей» (раздел 4).
3. Групповые звонки E2EE требуют SFU, который не расшифровывает медиа: шифрование кадров (SFrame) поверх SRTP, ключи раздаются через MLS-группу.
4. Один пользователь = много устройств; каждое устройство — отдельный криптографический участник. Это усложняет модель данных и верификацию.
5. Ограничение масштаба E2EE-группы: в v1 целевой предел ~5 000 устройств на канал; это ограничение выражается в продукте как лимит участников канала (по умолчанию 2 000), без режима без E2EE (раздел 12).
6. Discord сам не шифрует текст end-to-end (только голос/видео через DAVE), поэтому «полная идентичность» в части серверных функций над текстом недостижима в принципе — проект здесь выходит за рамки оригинала.

## 2. Clean-room процесс

Clean room защищает от претензий по авторскому праву на код и ассеты; он **не** защищает от претензий по товарным знакам и trade dress (узнаваемый внешний вид). Поэтому процесс ниже разделён на две части: изоляция реализации от исходников и осознанное дистанцирование от бренда.

**Две роли и «стена»**

| Роль | Что разрешено | Что запрещено |
| --- | --- | --- |
| Аналитик (spec team) | Пользоваться Discord как обычный пользователь; читать публичную справку (support.discord.com), публичные блоги и whitepaper DAVE; описывать поведение своими словами; делать схемы экранов в словах и wireframe-ах | Декомпилировать/читать минифицированный JS клиента, читать утечки исходников, копировать тексты UI, CSS, иконки, звуки, шрифты, скриншоты в спецификацию |
| Разработчик (impl team) | Читать только спецификацию проекта, RFC, документацию open-source библиотек | Открывать Discord (даже как пользователь) на время разработки; читать docs.discord.com (API-схемы — тоже объект авторского права); использовать код из репозиториев Discord (libdave и др.), даже под MIT |

При работе с ИИ-агентами «стена» воспроизводится промптами: промпт-аналитик пишет спецификацию, промпт-разработчик получает только спецификацию и явный запрет упоминать или воспроизводить оригинал. В монопольной разработке (один человек) правило мягче: сначала полностью пишется спецификация, затем начинается реализация, и к оригиналу больше не возвращаются; журнал процесса (кто, когда, что смотрел) хранится в `docs/cleanroom/LOG.md`.

**Артефакты спецификации** (всё в `docs/spec/`)

1. `FEATURES.md` — инвентарь функций (раздел 3), с пометкой «наблюдаемое поведение» для каждой.
2. `FLOWS/` — пользовательские сценарии по одному файлу на поток (регистрация, создание сообщества, приглашение, звонок и т.д.).
3. `SCREENS/` — текстовые описания экранов: зоны, элементы, состояния; без пикселей и цветов оригинала.
4. `PERMISSIONS.md` — модель прав в собственной формулировке.
5. `GLOSSARY.md` — собственная терминология (раздел 1) и таблица соответствия для аналитика (не для разработчика).

**Что обязательно отличается от оригинала**

- Название, логотип, маскот, домены, звуки уведомлений, название файлов и пакетов.
- Цветовая палитра: не использовать фирменный синий `#5865F2` и серые тона оригинала как есть; палитра проекта выбирается отдельно (раздел 7).
- Иконки: только open-source наборы (Lucide, Tabler, Phosphor) или собственные.
- Шрифт: открытый (Inter, IBM Plex Sans, Source Sans 3); не `gg sans`.
- Тексты интерфейса, тон сообщений, микрокопирайт, easter eggs.
- Публичный API и имена полей: собственная схема; совместимость с Discord API не является целью (это ещё и аргумент clean room).

**Что допустимо воспроизводить**

- Паттерны раскладки (колонка сообществ → каналы → лента → участники), поведение функций, горячие клавиши как идея, модель ролей/прав как концепция, Markdown-подмножество, интерфейс с настройками.
- Общеизвестные протокольные идеи: шлюз на WebSocket с heartbeat/resume, SFU, MLS — всё описано в открытых RFC и статьях.

**Лицензии проекта**: сервер — AGPL-3.0 (защищает от закрытых SaaS-форков); клиенты — GPL-3.0 с дополнительным разрешением по §7 GPLv3 (App Store exception: разрешено распространение через App Store, Google Play и другие магазины, чьи условия добавляют ограничения на использование); crypto-core и Bot SDK — Apache-2.0 (чтобы их можно было встроить куда угодно); документация — CC BY-SA 4.0. Все зависимости проверяются на совместимость (REUSE/SPDX-заголовки, `cargo deny`, `go-licenses`).

## 3. Функциональный анализ и приоритеты v1.0

Версия 1.0 — MVP на четырёх столпах: E2EE для всего, включая стрим, без режима отката; стрим экрана/окна/приложения с задержкой до 1 с и звуком только из транслируемого приложения; soundboard; минимальные сообщества и сообщения. Приоритет: **M** — обязательно в 1.0, **S** — v1.x, **C** — v2+; ничто, кроме M, не блокирует релиз. Колонка «E2EE-влияние»: *нет* — обычная серверная логика; *клиент* — функция переносится на клиент; *конфликт* — раздел 8.

**3.0 Столпы v1.0 и критерии приёмки**

| Столп | Что именно | Критерий приёмки |
| --- | --- | --- |
| E2EE | DM, каналы, файлы, голос, камера, стрим — всегда, одним режимом, без отката на транспортное шифрование | Тест подтверждает, что сервер и SFU хранят и передают только шифртекст; в UI одно состояние замка. При нехватке ресурсов клиент снижает пресет качества стрима (1080p60 → 1080p30 → 720p30), шифрование не отключается никогда |
| Стрим | Весь экран / монитор, отдельное окно, приложение; в режиме окна/приложения звук берётся только у этого приложения; 720p30, 1080p30, 1080p60; стерео 48 кГц; задержка < 1 с (цель ≤ 300 мс) | Уровень 1 (блокеры релиза): обновлённая Windows 10 21H2+ и Windows 11 на GPU NVIDIA, AMD, Intel; macOS 13+ на Apple Silicon и Intel. Уровень 2: Debian 12+ и Ubuntu 22.10+ с PipeWire; измеренная задержка «экран → зритель» на локальной сети ≤ 300 мс, через интернет < 1 с; на эталонном железе (6.5) 1080p60 с E2EE держится 30 минут без дропов |
| Soundboard | Звуки сообщества (загружают администраторы) и личные; воспроизведение у всех в голосовом канале; громкость, горячие клавиши; право «использовать soundboard» | Нажатие → звук у всех участников за ≤ 200 мс; медиа не передаётся, каждый клиент играет локальную копию |
| Минимум сообществ и сообщений | Регистрация, простой профиль, сообщества, каналы, инвайты, роли-пресеты, текст с вложениями и реакциями | Все строки с M в таблицах 3.1–3.8 |

**3.7 Настройки клиента**: тёмная тема, горячие клавиши (PTT, mute, deafen, soundboard, старт/стоп стрима), выбор аудио/видео-устройств, язык RU/EN, диагностика — M; светлая тема, масштаб, плотность — S.

**3.9 Открытые API**: REST и WebSocket-шлюз существуют по построению и описываются OpenAPI/Protobuf — M как артефакт; Bot SDK — C.

**3.10 Вне v1.0 (C)**: боты и webhooks, stage, форумы, Rich Presence, совместные активности, платные подписки, discovery между инстансами, серверные подписки, стрим с мобильных.

## 4. E2EE: модель угроз и криптографический дизайн

Основа — MLS (RFC 9420) для всех групп (DM, групповые DM, каналы, звонки) через библиотеку [OpenMLS](https://github.com/openmls/openmls) (Rust, поддерживается Phoenix R&D и Cryspen; собирается под Linux/Windows/macOS/Android/iOS/wasm). Медиа — SFrame-шифрование кадров поверх SRTP, ключи выводятся из MLS-группы звонка. Это та же схема, что у [DAVE](https://daveprotocol.com/) (MLS + WebRTC encoded transforms), но реализованная независимо по RFC и распространённая на текст и файлы.

**4.1 Модель угроз**

| Противник | Защищаем | Не защищаем (принимаем) |
| --- | --- | --- |
| Оператор сервера / взломанный сервер | Содержимое сообщений, файлов, реакций, медиа, названий приватных веток | Метаданные: кто с кем, когда, размеры, состав групп, названия каналов, присутствие |
| Сетевой наблюдатель | Всё (TLS + E2EE) | Факт соединения с инстансом |
| Бывший участник группы | Сообщения после его удаления (PCS) | Сообщения, которые он уже получил |
| Будущий компрометатор устройства | Прошлые сообщения, если локальное хранилище зашифровано и эпохи ротированы (FS) | Содержимое, кэшированное в открытом виде (например, локальный поисковый индекс — поэтому он тоже шифруется) |
| Злонамеренный участник | Подделку авторства (подписи MLS) | Утечку содержимого «скриншотом» — неустранимо |

**4.2 Идентичность и устройства**

- Пользователь имеет долгоживущий **ключ идентичности** (Ed25519), создаваемый на первом устройстве; его публичная часть публикуется на сервере.
- Каждое устройство — отдельный **MLS-клиент** с собственным signature key и набором одноразовых KeyPackages, которые загружаются на сервер (сервер = Delivery Service + Authentication Service в терминах RFC 9420 Architecture).
- Ключ устройства подписывается ключом идентичности (cross-signing); добавление нового устройства требует подтверждения с существующего (QR/короткий код) или ввода **ключа восстановления**.
- Верификация пользователей: сравнение safety number (хэш обоих ключей идентичности) или сканирование QR; статус «верифицирован» отображается в UI, смена ключа подсвечивается.
- Ciphersuite v1: `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (0x0001); credential — Basic; в v2 рассмотреть гибридный X-Wing после стандартизации.

**4.3 Группы и сервер как Delivery Service**

- Одна MLS-группа на: DM, групповой DM, текстовый канал, приватную ветку, активный звонок (отдельная короткоживущая группа). Публичная ветка наследует группу канала.
- Сервер сериализует handshake-сообщения (Proposal/Commit) по каждой группе: принимает commit только для текущей эпохи, отвергает конкурентные (клиент повторяет на новой эпохе). Это стандартная роль DS.
- Добавление участника в канал: сервер (как *external sender*) публикует Add-proposal с KeyPackage новых устройств; первый активный участник коммитит. Удаление/бан/выход из сообщества — Remove-proposal от external sender. Так состав группы следует за правами, которыми управляет сервер, но ключи он не получает.
- Внешний вход (external commit) используется для быстрого присоединения, когда никто из участников не онлайн: присоединяющийся сам коммитит по опубликованному GroupInfo (GroupInfo публикуется зашифрованным, ключ к нему раздаётся участникам канала).
- Ротация эпохи: при каждом изменении состава плюс не реже раза в сутки на активной группе (обновление ключей ради FS/PCS).
- Лимит v1: 5 000 листьев (устройств) на группу; сервер применяет его как лимит участников канала (по умолчанию 2 000, настраивается) и отклоняет вход сверх него с сообщением о лимите участников.

**4.4 Формат сообщений**

- Application message MLS содержит Protobuf-конверт: тип (text, edit, delete, reaction, pin, poll-vote, file-key, call-key, history-keys, typing не шифруется), id сообщения (UUIDv7, генерируется клиентом), ссылка на отвечаемое, содержимое, список упоминаний.
- Сервер хранит: id, автора (устройство), группу, эпоху, время, размер, шифртекст и ключ сообщения, обёрнутый ключом истории канала (раздел 4.7). Для уведомлений об упоминании клиент отправителя добавляет в открытые метаданные **mention-hint**: HMAC(id упоминаемого, секрет канала из MLS exporter) — сервер сравнивает с хинтами, заранее присланными каждым участником, не узнавая, кто упомянут посторонним.
- Редактирование и удаление — новые MLS-сообщения, ссылающиеся на id; сервер ставит tombstone на шифртекст по команде автора или модератора (модератор не видит текст, но может удалить по id).

**4.5 Файлы и медиа-вложения**

- Клиент генерирует случайный ключ, шифрует файл XChaCha20-Poly1305 (чанками по 1 МиБ для стриминга), загружает в S3-совместимое хранилище по presigned URL; ключ + хэш + размер отправляются в MLS-сообщении.
- Превью изображений/видео генерируются клиентом отправителя и загружаются как второй зашифрованный blob.
- Аватары, иконки сообществ, эмодзи, стикеры — публичные для участников, не шифруются.

**4.6 Звонки**

- SFU: [LiveKit](https://docs.livekit.io/transport/encryption/) (Go, Apache-2.0) с включённым E2EE: шифрование кадров AES-GCM в клиентских SDK (JS, Android, Swift, Flutter, React Native, Rust), собственный KeyProvider.
- Ключи: при входе в голосовой канал клиент вступает в MLS-группу звонка; из её epoch secret через MLS exporter выводится per-sender media key, который передаётся в KeyProvider LiveKit. Ротация ключа при каждой смене состава (новая эпоха → новый key index).
- Сигналинг LiveKit (кто в комнате, треки) сервер видит — это метаданные. Серверный mute реализуется запретом публикации трека на SFU.
- Демонстрация экрана — ещё один трек, шифруется так же. Stage-каналы (много слушателей, спикеров мало) — E2EE через ту же группу; лимит участников тот же.

**4.7 История и несколько устройств** (ADR-0015)

- История канала, ЛС и группового чата видна каждому, кто сейчас видит канал: новым участникам, вернувшимся участникам и новым устройствам — сразу и целиком, с подгрузкой порциями и поиском.
- **Ключи истории**: содержимое сообщения и ключи вложений шифруются ключом сообщения; он идёт в MLS-сообщении и дополнительно хранится на сервере, обёрнутый ключом истории канала. Ключ истории сменяется при удалении участника или устройства и раз в 30 дней. Связка ключей истории хранится на сервере зашифрованной для текущей эпохи MLS-группы; её обновляет клиент, делающий commit. Новичок после вступления в группу расшифровывает связку и читает историю с сервера.
- Настройка канала «Новые участники видят историю» включена по умолчанию; при выключенной новичок получает ключи истории только с момента вступления.
- Отдельной резервной копии истории в 1.0 нет: новое устройство пользователя получает историю тем же путём. Ключ восстановления нужен для подтверждения нового устройства без старого.
- Сервер не получает ни ключей истории, ни открытого текста. Плата — слабее forward secrecy для истории: ключи истории канала открывают всю его историю на сервере.

**4.8 Push-уведомления**

- Push никогда не содержит текста: только id группы и id сообщения (UnifiedPush/FCM/APNs). Клиент по пушу забирает шифртекст, расшифровывает и показывает уведомление локально. На iOS — Notification Service Extension с доступом к ключам через Keychain/App Group.

**4.9 Локальное хранилище**

- База сообщений — SQLite с SQLCipher (ключ в Keychain/Keystore/Secret Service/DPAPI); поисковый FTS5-индекс внутри той же зашифрованной базы; MLS-state — в хранилище OpenMLS поверх той же базы.

**4.10 Проверяемость**

- Воспроизводимые сборки клиентов, публикация хэшей; опциональный Key Transparency лог (v2) для обнаружения подмены ключей сервером; внешний аудит crypto-core до релиза 1.0.

## 5. Архитектура системы

Сервер — модульный монолит на Go (один бинарник, модули с явными границами, позже выделяемые в сервисы); медиа — отдельный процесс LiveKit; весь криптографический слой живёт в клиентах в общей Rust-библиотеке.

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ КЛИЕНТЫ — у каждого Rust crypto-core (OpenMLS, ключи SFrame, SQLCipher)  │
│  Desktop и Web: Electron + React/TS   │  Android / iOS (после 1.0)       │
│  media-engine (Rust): стрим           │  Боты: Bot SDK Go/TS (после 1.0) │
└───────────────┬───────────────────────────────────────────┬──────────────┘
                │ HTTPS и WSS — только шифртекст             │ SRTP + SFrame
                ▼                                           ▼
┌───────────────────────────────────────────────┐   ┌──────────────────────┐
│ СЕРВЕР — Go, модульный монолит, один бинарник │   │ LiveKit SFU (Go)     │
│  REST API · Gateway (WSS) · MLS Delivery      │──▶│ пересылает SFrame-   │
│  Auth и права · Сигналинг · Push и файлы      │   │ кадры, ключей нет    │
└───┬──────────────┬──────────────┬─────────┬───┘   │ TURN: coturn         │
    ▼              ▼              ▼         ▼       └──────────────────────┘
 PostgreSQL      Valkey         NATS      S3 (MinIO / Garage)
 метаданные,     кэш, presence, шина      зашифрованные blob-ы
 шифртекст       сессии         событий
```

Открытый текст существует только внутри клиентов. Push (UnifiedPush / FCM / APNs) несут только id группы и сообщения.

Все стрелки к серверу несут шифртекст и метаданные; расшифровать их могут только устройства из тонированной зоны.

**5.1 Модули сервера** (пакеты Go в одном репозитории, общение через интерфейсы; NATS — только для fan-out между инстансами gateway)

1. `identity` — пользователи, устройства, ключи идентичности, сессии, 2FA, passkeys, OIDC-вход.
2. `community` — сообщества, каналы, категории, роли, права, инвайты, баны, аудит.
3. `messaging` — приём и выдача шифртекста (пагинация по UUIDv7), tombstones, read-state, закрепы (id), реакции (как сообщения).
4. `mls` — Delivery Service: склад KeyPackages, GroupInfo, сериализация Proposal/Commit по эпохам, external-sender-предложения на вход/выход, Welcome-доставка.
5. `gateway` — WebSocket-шлюз: аутентификация, подписки, heartbeat, resume по последовательному номеру, сжатие (zstd), шардинг по пользователю.
6. `media` — выдача токенов LiveKit с правами (publish/subscribe по ролям), приём webhooks (участник вошёл/вышел) → триггер смены эпохи звонка.
7. `files` — presigned URL на загрузку/скачивание, квоты, антивирус (ClamAV, опционально, только по заголовкам/размеру — содержимое недоступно).
8. `push` — реестр устройств, UnifiedPush/FCM/APNs, батчинг, rate limit.
9. `admin` — конфигурация инстанса, политика регистрации, метрики (Prometheus), бэкапы, CLI.

**5.2 Протокол реального времени**

- Транспорт: WSS, кадры Protobuf (JSON-режим для отладки). Клиент после `Identify` получает `Ready` (снимок сообществ, каналов, непрочитанных, присутствия друзей) и далее события с монотонным `seq`.
- Разрыв → `Resume(seq)`: сервер досылает пропущенные события из буфера Valkey (окно 5 минут), иначе — полный `Ready`.
- События: сообщение создано/изменено/удалено (шифртекст), MLS-handshake, присутствие, набор текста, состояние голосового канала, изменения сообществ.
- REST — для всего, что не нужно мгновенно: CRUD сообществ, история сообщений, загрузка KeyPackages, инвайты, настройки. Контракт пишется первым: `docs/protocol/openapi.yaml` (B1) — источник правды; Go-обработчики и TS-клиент генерируются из него (`just gen`), CI проверяет, что сгенерированный код не устарел.

**5.3 Модель данных (ядро)**

| Таблица | Ключевые поля | Примечание |
| --- | --- | --- |
| users | id, username, display_name, identity_pubkey, flags | аватар — в S3, публичный |
| devices | id, user_id, signature_pubkey, name, last_seen | одна запись = MLS-leaf |
| key_packages | device_id, ciphersuite, blob, consumed_at | одноразовые |
| communities | id, owner_id, name, settings_json | «сервер» в терминах оригинала |
| channels | id, community_id, type, parent_id, position, mls_group_id | текстовые → группа |
| mls_groups | id, epoch, group_info_blob, external_sender_key | DS-состояние |
| mls_handshakes | group_id, epoch, seq, blob | упорядоченные commit/proposal |
| messages | id (uuidv7), channel_id, device_id, epoch, ciphertext, size, flags, deleted_at | партиционирование по времени |
| mention_hints | message_id, hmac | для адресных пушей |
| attachments | id, message_id, s3_key, size, ciphertext_hash | ключ — в сообщении |
| roles, members, overwrites, invites, bans, audit_log, read_states, relationships, push_endpoints, history_key_bundles |  |  |

**5.4 Хранилища**: PostgreSQL 16 (схема с миграциями `goose`; партиции `messages` по месяцу; при росте — вынос `messages` в ScyllaDB за интерфейсом репозитория); Valkey (сессии, присутствие, буфер resume, rate limits); NATS JetStream (события между репликами gateway и воркерами push); S3-совместимое хранилище (MinIO или Garage) для blob-ов; LiveKit + coturn.

**5.5 Развёртывание**: `docker compose up` для малых инстансов (всё в одном); Helm-чарт с HPA для gateway и воркеров; единый бинарник `bebeberloga-server` с подкомандами `serve`, `migrate`, `admin`; конфигурация через YAML + env; автоматический TLS (Caddy или встроенный ACME).

**5.6 Масштабирование**: gateway горизонтально за NATS; API stateless; MLS-очередь — одна горячая точка на группу (сериализация по group_id в Postgres advisory lock или Valkey lock); LiveKit — multi-node через свой Redis-протокол.

## 6. Технологический стек

Решения ниже — рекомендация по умолчанию; каждое фиксируется как ADR в `docs/adr/` и может быть пересмотрено по результатам спайков фазы 0 (раздел 9). Главный принцип: один Rust crypto-core для всех клиентов, Go на сервере, веб-технологии для desktop (так проще всего добиться визуальной идентичности), нативные мобильные клиенты поверх того же ядра.

**6.1 Итоговый выбор**

| Слой | Выбор | Почему |
| --- | --- | --- |
| Сервер | Go 1.23+, `net/http` + `chi` (или Connect-RPC), `pgx`, `sqlc`, `goose`, `nats.go`, `valkey-go`, `zerolog`, OpenTelemetry | Основной стек разработчика; единый статический бинарник; LiveKit тоже на Go |

**6.2 Почему Electron, а не Tauri (ключевое решение)**

Tauri легче и ближе к FOSS-духу, но на Linux использует WebKitGTK, в стандартных сборках которого WebRTC отключён ([tauri#2600](https://github.com/tauri-apps/tauri/issues/2600), [WebKit Bugzilla 274711](https://www2.webkit.org/show_bug.cgi?id=274711)). Голос — ядро продукта, а Linux — обязательная платформа, поэтому в v1 выбран Electron. Для 1.0 решение окончательное; к Tauri возвращаемся после 1.0, если WebKitGTK получит WebRTC в стандартных сборках. Альтернативный план тогда — Tauri с нативным медиа через LiveKit Rust SDK (сложно: рендер видео в webview через shared texture).

**6.3 Матрица альтернатив для клиентов**

| Вариант | Платформы | Плюсы | Минусы | Вердикт |
| --- | --- | --- | --- | --- |
| Electron + React (выбран) | Win/macOS/Linux + Web | Идентичный UI через CSS; стабильный WebRTC и E2EE кадров; огромная экосистема | ~150 МБ, память; нужен отдельный мобильный код | v1 desktop |

| Flutter + flutter_rust_bridge | Все 5 платформ | Одна кодовая база; `livekit-flutter` с E2EE; готовые Dart-биндинги OpenMLS | Нет веба как бонуса; Rich text/markdown-редактор и плотные списки сложнее; размер команды должен владеть Dart | Запасной «одна база для всего» |

**6.4 Общий код между клиентами**

- `crypto-core` (Rust): MLS-сессии, ключи устройств, шифрование файлов, вывод SFrame-ключей, хранилище состояния, ключи истории. Публичный API — ~40 функций, описанных в `core.udl`.
- `protocol` (Protobuf): схемы gateway-событий, конвертов сообщений, REST-моделей; кодогенерация в Go/TS/Kotlin/Swift.
- `design-tokens` (JSON): цвета, типографика, отступы, радиусы, тени, иконки → генерируются в CSS-переменные, Compose `MaterialTheme`, SwiftUI.
- Markdown-подмножество описано грамматикой (PEG) и тестовым корпусом, который прогоняется на всех платформах (парсер на TS для web, Kotlin, Swift — или один Rust-парсер в crypto-core через FFI; предпочтительно последнее).

**6.5 Стрим: архитектура по модели Discord Go Live**

Стрим строится так же, как публично описывает свой Go Live Discord: [собственный нативный захват и кодирование, интегрированные с ОС и видеодрайверами, а WebRTC — только транспорт](https://discord.com/blog/from-blocky-to-brilliant-improving-video-quality-on-discord-go-live-on-amd-gpus); [цепочка методов захвата с автоматическим fallback, звук процесса и всех его дочерних процессов, аппаратные энкодеры, ретрансляция только тем, кто смотрит](https://discord.com/blog/how-it-all-goes-live-an-overview-of-discords-streaming-technology). Это архитектурные принципы из открытых инженерных публикаций (вход аналитика по разделу 2); код и протоколы Discord не используются.

**Платформенные уровни.** Windows 10 21H2+/11 и macOS 13+ — уровень 1: блокеры релиза, полная тестовая матрица (NVIDIA, AMD, Intel; Apple Silicon и Intel Mac). Linux (Debian 12+, Ubuntu 22.10+) — уровень 2: та же функциональность, но регрессия не блокирует релиз, если есть рабочий fallback.

**Два пути публикации стрима**

1. **Основной для Windows с NVIDIA, macOS и Linux — нативный `media-engine`** (Rust, утилитарный процесс Electron через `napi-rs`): захват → аппаратное кодирование → E2EE кадров → отправка через libwebrtc ([LiveKit Rust SDK](https://github.com/livekit/client-sdk-native)). Стример подключается к комнате звонка вторым, отдельным участником «стрим» — как отдельное стрим-соединение у Go Live; голос не страдает при перегрузке стрима.
2. **Запасной — Chromium** (`desktopCapturer` + `getDisplayMedia` + `livekit-client`): в 1.0 это основной путь на Windows с GPU AMD и Intel (Chromium кодирует через Media Foundation на всех трёх вендорах); для остальных включается автоматически, если нативный путь не стартовал или упал; звук приложения в этом режиме по-прежнему идёт из `media-engine`.

Путь выбирается по GPU при старте стрима. В v1.x AMD и Intel переводятся на нативный путь через энкодеры FFmpeg (h264_amf, h264_qsv, h264_mf) с настройками по образцу OBS и Sunshine. Запасной план, если LiveKit Rust SDK упрётся в ограничения, — GStreamer ([livekitwebrtcsink](https://GStreamer.freedesktop.org/documentation/rswebrtc/index.html)); при этом заранее учесть, что его [wasapi2src скрывает захват звука процесса на сборках ниже 20348](https://GStreamer.freedesktop.org/documentation/wasapi2/wasapi2src.html), а E2EE в формате LiveKit там нужно писать самим.

Зритель всегда смотрит в Chromium: `livekit-client`, аппаратное декодирование (D3D11, VideoToolbox, VAAPI), E2EE через encoded transforms.

**Захват видео: цепочка с fallback**

| ОС | Методы по порядку | Примечания |
| --- | --- | --- |
| Windows | Windows Graphics Capture (окно/монитор) → DXGI Desktop Duplication (монитор) → GDI BitBlt (крайний случай) | Кадры остаются на GPU (D3D11-текстура → энкодер, zero-copy); захват и энкодер на одном адаптере (важно для ноутбуков с двумя GPU); захват игр через DLL-инъекцию — после 1.0 из-за риска с античитами |
| macOS | ScreenCaptureKit: окно, приложение, дисплей | IOSurface → VideoToolbox без копий; на 14+ системный пикер, на 13 — собственный |
| Linux | xdg-desktop-portal ScreenCast → PipeWire (Wayland и X11) → XComposite/XShm (X11 без портала) | DMA-BUF → VAAPI/NVENC без копий, где драйвер позволяет |

**Захват звука: процесс и все его дочерние процессы**

| ОС | Метод | Минимум |
| --- | --- | --- |
| Windows | WASAPI process loopback с `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` по PID окна ([Microsoft](https://learn.microsoft.com/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-audioclient_activation_type)); в UI — опция «добавить процесс», если звук идёт из соседнего процесса (лаунчеры) | Обновлённая Windows 10 21H2+; при ошибке API — звук системы без нашего процесса |
| macOS | ScreenCaptureKit `capturesAudio`, звук всего приложения ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10155)); `excludesCurrentProcessAudio = true`, чтобы голоса собеседников не попадали в стрим | macOS 13+ |
| Linux | Как у Discord на Linux: PipeWire-клиент захвата, к которому линкуются аудиоузлы выбранного приложения и его дочерних процессов по `application.process.id` (схема [OBS PipeWire Audio Capture](https://github.com/dimtpap/obs-pipewire-audio-capture)); узлы, появившиеся во время стрима, подключаются автоматически; собственный процесс исключается | PipeWire 0.3.62+ с WirePlumber; без PipeWire — звук всей системы через PulseAudio monitor с предупреждением |

**Кодирование и транспорт**

1. Аппаратный энкодер первым: NVENC; на Windows для AMD и Intel в 1.0 кодирует Chromium (Media Foundation), в v1.x — FFmpeg в нативном пути; VideoToolbox на macOS; VAAPI/NVENC на Linux. Программный OpenH264/libvpx — только как fallback с автоматическим понижением пресета.
2. Кодек согласуется по зрителям: H.264 — всегда; HEVC и AV1 — только если все смотрящие умеют их декодировать; пересогласование при входе и выходе зрителя.
3. Энкодер управляется оценкой полосы WebRTC (GCC/TWCC): при перегрузке сначала сбрасываются кадры, потом снижается битрейт, потом пресет. Буферизации «на секунды ради качества» нет.
4. Ключевые кадры: смена параметров энкодера не сбрасывает его в ключевой кадр; запросы PLI/FIR от зрителей ограничены (не чаще 1 раза в секунду), при входе нового зрителя — один ключевой кадр.
5. Simulcast из двух слоёв (выбранный пресет + 540p30), чтобы слабый зритель не опускал качество для всех; dynacast: слой, который никто не смотрит, не кодируется.
6. Профили: «Игра/видео» — приоритет частоты кадров (`maintain-framerate`), «Текст/код» — приоритет чёткости (`maintain-resolution`, `contentHint: detail`).
7. Звук стрима: Opus 48 кГц стерео 128–256 kbps, без шумоподавления, AGC и эхоподавления, DTX выключен, in-band FEC включён.
8. SFU пересылает стрим только тем, кто нажал «Смотреть» (подписка на треки экрана не автоматическая); если смотрящих нет — стример не кодирует вовсе. IP участников скрыты за SFU.
9. Звук и видео — отдельные RTP-потоки, синхронизация на приёме по RTCP SR; со звонком стрим не синхронизируется, но задержка держится ниже заметного порога.
10. E2EE кадров (AES-GCM) выполняется после кодирования: < 2 мс на кадр и доли процента CPU, на задержку не влияет.

**Бюджет задержки** (цель ≤ 300 мс в локальной сети, < 1 с через интернет): захват ≤ 16 мс + кодирование 5–15 мс (аппаратное) + E2EE < 2 мс + сеть 20–100 мс + SFU < 5 мс + jitter-буфер 50–150 мс + декодирование и рендер ≤ 20 мс.

**Метрики качества** (как у Discord: частота кадров, равномерность кадров, задержка, качество VMAF, загрузка сети, CPU/GPU): собираются локально и показываются в оверлее «Статистика стрима»; отправка в телеметрию инстанса — только с согласия пользователя. В e2e-тестах — VMAF и glass-to-glass задержка на эталонных конфигурациях.

**Эталонное железо для приёмки**: Windows 11 — ПК с 4-ядерным CPU 2018 года и GPU каждого вендора (NVIDIA GTX 16xx, AMD RX 6000, Intel Arc/Xe iGPU); macOS — MacBook Air M1 и Intel Mac 2019; Linux — Ubuntu 24.04 с AMD (VAAPI) и NVIDIA. При нехватке ресурсов клиент снижает пресет (1080p60 → 1080p30 → 720p30) и показывает это в UI; E2EE не отключается.

## 8. Конфликты E2EE с функциями Discord и принятые компромиссы

Discord отказался от E2EE текста именно потому, что многие функции построены на серверном доступе к содержимому ([heise, 2026](https://heise.de/-11300185)). Ниже — каждая такая функция и выбранная замена. Правило: сервер никогда не получает ключ «ради удобства»; если функцию нельзя сделать на клиенте или ботом-участником, она упрощается или исключается.

| Функция | Проблема при E2EE | Решение в проекте | Цена |
| --- | --- | --- | --- |
| Стрим 1080p60 со звуком приложения | Шифрование кадров добавляет CPU и исключает SVC; SFU не может подстраивать качество, кроме выбора simulcast-слоя | E2EE всегда; simulcast из двух слоёв; аппаратное кодирование обязательно; при нехватке ресурсов клиент снижает пресет качества, а не шифрование | Нет SVC и серверной подстройки качества; слабое железо стримит в 720p30 |
| Soundboard | Звук не должен идти через медиапоток и микрофон отправителя | Звуки — публичные ассеты сообщества и пользователей; команда «сыграть» идёт через сервер (gateway): сервер проверяет право 14, присутствие в голосовом канале и кулдаун 2 с и рассылает событие участникам канала; каждый клиент играет локальную копию | Сервер знает, кто, какой звук и когда проиграл, — метаданные того же уровня, что состояние голоса (ADR-0013 п. 17) |
| Поиск по сообщениям | Сервер не может индексировать | Локальный FTS5-индекс в SQLCipher на каждом устройстве; фильтры «автор:», «канал:», «с:», «до:»/«после:» (`SCREENS/10`) работают локально | Поиск только по истории, загруженной на устройство; на новом устройстве индекс строится в фоне по мере загрузки истории |
| Превью ссылок (embeds) | Сервер не видит URL | Клиент отправителя забирает OpenGraph-данные (напрямую или через прокси инстанса, чтобы скрыть IP) и вкладывает превью в шифртекст | Превью фиксируется на момент отправки; получатель не раскрывает свой IP |
| Automod | Сервер не видит текст | (а) Клиентские правила: клиент модератора/любого участника с ролью «страж» проверяет входящие сообщения и отправляет команду удаления по id; (б) бот-участник с автомод-плагином; (в) серверные правила только над метаданными (частота, размер вложений, новые аккаунты) | Проверка выполняется после доставки, а не до; требует онлайн-клиента или бота |
| Боты, слэш-команды, webhooks | Бот должен читать/писать в группу | Бот = пользователь с устройствами и crypto-core; вступает в MLS-группы каналов, куда допущен ролями. Webhook = легковесный бот, которому инстанс выдаёт ключи на сервере-мосте, явно помеченном «webhook видит открытый текст» | Боты сложнее писать (SDK скрывает крипто); входящие webhooks требуют доверенного моста |
| История для новых участников и устройств | Forward secrecy | Ключи истории канала, связка обновляется при каждом commit (раздел 4.7, ADR-0015) | Ослабление FS для истории: ключи истории открывают всю историю канала на сервере; по умолчанию включено, отключается в настройках канала |
| Закрепы, список вложений, галерея медиа | Сервер знает только id | Сервер хранит список id закрепов и id вложений; клиент собирает содержимое | Галерея доступна только для расшифрованной истории |
| Модерация содержимого (удаление, жалобы) | Модератор может не быть в группе | Модератор — участник группы по правам роли (видит текст как любой участник); жалоба прикладывает расшифрованный фрагмент с подписью MLS как доказательство авторства | Модераторы инстанса, не состоящие в сообществе, видят только метаданные |
| Уведомления с текстом (push) | Push-шлюзы Google/Apple видят payload | Push без содержимого + локальная расшифровка | На iOS требуется Notification Service Extension; на Android без FCM — UnifiedPush |
| Упоминания и «только @» уведомления | Сервер не знает, кто упомянут | mention-hint HMAC (раздел 4.4) | Утечка факта «кого-то упомянули», но не кого |
| Stage-каналы с тысячами слушателей | Размер MLS-группы, частые join/leave | E2EE через общую группу до лимита; выше лимита — предупреждение и запрет (нет «тихого» отключения E2EE) | Stage ограничен ~5 000 устройств; в v1.0 не входит |
| Публичные сообщества 50 000+ | Коммиты при каждом входе/выходе, размер дерева | Канал = группа; «тихие» каналы коммитят лениво (батчинг proposal-ов раз в N секунд); лимит участников на группу | Лимит участников канала (по умолчанию 2 000); каналы крупнее не поддерживаются |
| Серверные интеграции (YouTube/Twitch, Spotify-статусы) | Не зависят от содержимого | Реализуются как обычно (метаданные) | — |
| GIF-пикер, стикеры-магазин | Внешние запросы | Через прокси инстанса, без логов | — |
| Экспорт/архив сообщества админом | Сервер не может | Экспорт выполняет клиент любого участника с правом «экспорт» | Нет централизованного архива |
| Юридические запросы к оператору | Нет содержимого | Оператор выдаёт только метаданные | Это цель проекта |

## 9. Дорожная карта

Шесть фаз от спецификации до 1.0 (мобильные клиенты — после него); каждая закрывается проверяемым критерием, а E2EE строится с первой фазы, а не «накладывается» потом.

| Фаза | Содержание | Срок | Ворота (критерий выхода) |
|---|---|---|---|
| 0 — Фундамент и спайки | Репозиторий, CI, clean-room спецификация, ADR; спайки 1–6 | 6–8 нед. | Спецификация и спайки приняты, E2EE-стрим измерен |
| 1 — Ядро | Сервер: identity, MLS Delivery, messaging, сообщества и каналы; desktop: регистрация, профиль, DM, каналы, инвайты | 10–12 нед. | E2EE-сообщения между двумя устройствами в канале |
| 2 — Голос, стрим, soundboard | LiveKit + SFrame из MLS, PTT, RNNoise, стрим окна/приложения со звуком приложения, soundboard | 12–14 нед. | Стрим 1080p60 < 1 с со звуком приложения на 3 ОС |
| 3 — Сообщения и сообщества: минимум v1.0 | Роли-пресеты, кик/бан, реакции, вложения, упоминания, уведомления, desktop-сборки для 3 ОС | 8–10 нед. | Все M-функции разделов 3.3–3.4 закрыты |
| 4 — Администрирование | CLI и политика инстанса, лимиты стрима и soundboard (история и ключи истории — в фазе 1) | 6–8 нед. | Публичная beta на трёх и более инстансах |
| 5 — Hardening и 1.0 | Внешний аудит crypto-core, reproducible builds, нагрузочные тесты, документация | 8 нед. | Аудит закрыт → релиз 1.0 |
| После 1.0 | FFmpeg-энкодеры AMD/Intel в нативном пути, Android, затем iOS, боты | — | — |

Итого 50–60 недель для команды из 2–3 инженеров с ИИ-ассистентами. Ворота — критерий, без которого следующая фаза не начинается.

Порядок фаз отражает приоритеты MVP: стрим и soundboard идут сразу после ядра, а полнота сообществ и сообщений — после них. Мобильные клиенты вынесены за 1.0: Android — первый пункт v1.x, iOS — следом; они опираются на стабильный API crypto-core и gateway, зафиксированный к фазе 2.

**Спайки фазы 0** (каждый — отдельный репозиторий-прототип с отчётом в ADR):

1. **OpenMLS FFI** — одна Rust-библиотека собирается и вызывается из Electron (napi-rs); сборка под Android (uniffi/Kotlin) и iOS (uniffi/Swift) — только проверка переносимости для будущих клиентов; группа на 100 устройств с замером времени commit и размера состояния.
2. **LiveKit E2EE** — собственный KeyProvider, ключ из MLS exporter, ротация при смене эпохи, звонок на 10 участников в Electron на трёх ОС.
3. **Desktop-оболочка** — Electron: захват экрана со звуком на Windows/Linux (PipeWire)/macOS, encoded transforms, размер и память.
4. **MLS Delivery Service** — Go-прототип сериализации commit-ов и external-sender-предложений; тест на 1 000 одновременных входов в группу.
5. **Звук приложения на трёх ОС** — Rust-модуль `media-engine`: WASAPI process loopback с деревом процессов, ScreenCaptureKit, PipeWire; цепочка захвата видео WGC → DXGI → GDI; сопоставление окна с PID и аудио-узлами; стерео 48 кГц без дропов 10 минут подряд; измерение рассинхрона с видео.
6. **E2EE-стрим 1080p60** — нативный конвейер media-engine против запасного Chromium-пути на эталонном железе из 6.5 (Windows: NVIDIA, AMD, Intel; macOS: M1 и Intel): задержка «экран → зритель», загрузка CPU/GPU с E2EE и без; результат задаёт пресеты качества по умолчанию для слабого железа; отдельно — качество и задержка Chromium-пути на AMD и Intel, основного для них в 1.0.

**Что считается релизом 1.0**: все M-функции раздела 3 на desktop (Windows/macOS/Linux); стрим окна/приложения со звуком приложения и задержкой < 1 с на всех трёх desktop-ОС; soundboard; сервер с Docker Compose и Helm; закрытый внешний аудит crypto-core и протокола; документация администратора. Мобильные клиенты (Android, затем iOS) и боты — после 1.0.

## 10. Репозиторий, лицензии, качество, безопасность

Монорепозиторий с независимыми сборками по каталогам; один тег версии на всё, чтобы клиент и сервер всегда тестировались в одной связке.

```
bebeberloga/
├── docs/
│   ├── spec/            # clean-room спецификация (FEATURES, FLOWS, SCREENS, PERMISSIONS, GLOSSARY)
│   ├── adr/             # архитектурные решения (MADR)
│   ├── protocol/        # описание gateway, REST, MLS-профиля, формата сообщений
│   ├── cleanroom/       # LOG.md, политика, чеклисты ревью
│   └── admin/ dev/      # руководства
├── proto/               # Protobuf-схемы (общие для всех)
├── crypto-core/         # Rust: MLS, ключи, файлы, SFrame-ключи, бэкап; uniffi/napi/wasm биндинги
├── media-engine/        # Rust: захват экрана/окна/звука, аппаратное кодирование, публикация стрима (napi-rs)
├── server/              # Go: cmd/, internal/{identity,community,messaging,mls,gateway,media,files,push,admin}
├── clients/
│   ├── web/             # React + TS (используется и в desktop)
│   ├── desktop/         # Electron-оболочка, сборки
│   ├── android/         # Kotlin + Compose
│   └── ios/             # Swift + SwiftUI (позже)
├── sdk/
│   ├── bot-go/
│   └── bot-ts/
├── design/              # токены, иконки, Penpot-экспорт, Storybook
├── deploy/              # docker-compose, helm, ansible-пример
└── tools/               # скрипты, кодогенерация, lint-конфиги
```

**Лицензии**: AGPL-3.0 (server), GPL-3.0 + App Store exception (clients; текст исключения — в clients/LICENSE-EXCEPTION, ссылка на него в SPDX-заголовке каждого файла как GPL-3.0-or-later WITH LicenseRef-Bebeberloga-AppStore-exception), Apache-2.0 (crypto-core, proto, sdk), CC BY-SA 4.0 (docs); CLA не требуется, достаточно DCO (`Signed-off-by`). Автоматические проверки: `cargo deny`, `go-licenses`, `license-checker` (npm), REUSE-линт.

**Качество кода**

- Go: `golangci-lint`, `go test -race`, интеграционные тесты через `testcontainers-go` (Postgres, Valkey, NATS, MinIO, LiveKit).
- Rust: `clippy -D warnings`, `cargo audit`, `cargo fuzz` для парсеров конвертов и Markdown, Miri для unsafe-FFI-границ, property-тесты (`proptest`) для MLS-сценариев.
- TS: `eslint` + `typescript-eslint` strict, `vitest`, Playwright e2e с двумя браузерными контекстами (две «пользователя» обмениваются E2EE-сообщениями), визуальная регрессия.
- Kotlin: `detekt`, JUnit5, Compose UI tests; Swift: SwiftLint, XCTest.
- Протокольные тесты совместимости: один тест-корпус (JSON-фикстуры шифртекстов, MLS-сообщений, Markdown) прогоняется всеми клиентами и ботами.
- Покрытие: не менее 85 % в crypto-core и `server/internal/mls`.

**Безопасность**

- Threat model (раздел 4.1) — живой документ; каждый PR, меняющий `crypto-core` или `mls`, требует двух ревью и записи в `SECURITY-CHANGELOG`.
- Серверная сторона: Argon2id (m=64 MiB, t=3), rate limiting по IP и аккаунту, CSRF/CSP, подписанные presigned URL с коротким TTL, аудит зависимостей (Dependabot/Renovate), SBOM (CycloneDX) в каждом релизе.
- Клиенты: ключи в OS-хранилищах; память с ключами — `zeroize`; защита от повторного воспроизведения по epoch+generation; запрет скриншотов на Android для настраиваемых каналов (FLAG_SECURE), опционально.
- Reproducible builds для desktop и Android (F-Droid-совместимо); подписи релизов (Sigstore/cosign), минимальный SLSA level 2.
- Внешний аудит crypto-core и MLS-профиля перед 1.0; bug bounty после 1.0; `SECURITY.md` с PGP-ключом.

**Документация и релизы**: Conventional Commits, `CHANGELOG.md` автоматом, semver; `goreleaser`/`electron-builder`/Gradle публикуют артефакты; nightly-сборки; docs-сайт из `docs/`.

## 11. Разбивка на промпты для разработки

Промпты делятся на два контура по clean-room-стене: **A — аналитика** (видит оригинал, пишет спецификацию) и **B — реализация** (видит только спецификацию). Каждый промпт контура B получает один и тот же *context pack* плюс свою задачу; ни один промпт B не содержит слов «Discord» и описаний оригинала.

**11.1 Context pack (общая преамбула для всех промптов B)**

1. Цель проекта и границы (раздел 1, без упоминания оригинала: «self-hosted платформа сообществ с текстом, голосом, видео и E2EE»).
2. Глоссарий (`GLOSSARY.md`) и правила именования.
3. Ссылки на файлы спецификации, релевантные задаче (не вся спецификация целиком — только нужные FLOWS/SCREENS).
4. ADR-ы, затрагивающие задачу (стек, протокол, формат сообщений).
5. Protobuf-схемы и публичный API crypto-core.
6. Правила кода: язык, линтеры, структура каталогов, лицензионные заголовки, требования к тестам, запрет копирования чужих ассетов и кода, DCO.
7. Формат результата: список файлов, команды сборки и тестов, что считать готовым (definition of done), что вынести в открытые вопросы.

**11.3 Как писать каждый промпт B** (шаблон)

```markdown
# Роль
Ты — <роль: Rust-криптограф / Go-бэкендер / React-разработчик>, работаешь в open-source проекте Bebeberloga.

# Контекст
<context pack: пункты 1–6, вставлены или приложены файлами>

# Задача
<одна связная часть системы, 1–3 дня работы человека; критерии готовности списком>

# Ограничения
- Только спецификация в приложении; не воспроизводить сторонние продукты, их тексты, стили и API.
- Лицензии зависимостей: только <список>; каждая новая зависимость — обоснование.
- Тесты обязательны: <какие>; команда проверки: <cmd>.

# Формат ответа
1. Краткий план (до 10 пунктов) и открытые вопросы — ДО кода.
2. Файлы с полными путями.
3. Команды сборки/тестов и ожидаемый вывод.
4. Что сознательно отложено.
```

**11.4 Правила декомпозиции**

- Один промпт = один модуль с проверяемым выходом; не «сделай сервер», а «реализуй пакет `mls` по `docs/protocol/MLS.md` с тестами T1–T9».
- Сначала контракты (B1, B2, B8), потом реализации — так параллельные промпты не расходятся.
- Каждый промпт заканчивается обновлением ADR/документации; следующий промпт получает актуальные файлы, а не пересказ.
- Для длинных задач — цепочка промптов с явной передачей состояния: `STATUS.md` в каталоге модуля (что сделано, что сломано, что дальше).
- Ревью-промпт после каждого модуля: отдельный агент проверяет соответствие спецификации, лицензии и отсутствие заимствований (чеклист из `docs/cleanroom/`).

## 12. Риски и открытые вопросы

Все девять решений до старта фазы 1 приняты и отмечены; остальное — риски с планом реакции.

**Решения, которые нужны от владельца проекта**

- [x] **Название и бренд.** Решено: Bebeberloga. Точных совпадений в USPTO, WIPO и Роспатенте нет (строгий поиск); TMview не проверен, в Роспатенте 43 записи «Берлога» без проверки классов. Домен — bebeberloga.com, пока не куплен. Перед покупкой домена и публикацией показать название юристу по интеллектуальной собственности.
- [x] **E2EE для стрима.** Решено: E2EE для стрима всегда, одним режимом, без отката; при нехватке ресурсов клиент снижает пресет качества (1080p60 → 1080p30 → 720p30). Спайк 6 задаёт пресеты по умолчанию.
- [x] **Большие публичные сообщества.** Решено: жёсткий лимит участников канала — по умолчанию 2 000 (≈ 5 000 устройств), настраивается администратором инстанса. При достижении UI просто сообщает «В канале достигнут лимит участников», без упоминания E2EE. Режима без E2EE для больших каналов нет.
- [x] **История для новых участников** Решено (ADR-0015, заменил ADR-0006): как в привычном продукте — вся история канала видна каждому, кто видит канал, включая новых участников и новые устройства; механизм — ключи истории канала. Настройка канала может это выключить.
- [x] **Минимальная версия Windows.** Решено: минимум — обновлённая Windows 10 21H2 (сборка 19044) и Windows 11. Уточнение: сборка 20348 в документации Microsoft — это Windows Server 2022, а на практике process loopback работает на обновлённых Windows 10 начиная с 2004 (так его использует OBS), поэтому звук приложения доступен на всех поддерживаемых Windows. Если активация API всё же не удалась — fallback на звук всей системы с предупреждением; проверяется в спайке 5.
- [x] **Linux без PipeWire.** Решено: на системах без PipeWire режим «окно/приложение» транслирует звук всей системы через monitor-источник PulseAudio; в диалоге выбора источника — предупреждение «звук только приложения требует PipeWire». Рекомендация: fallback с предупреждением.
- [x] **Desktop-оболочка**: Electron по умолчанию. Решено: Electron для 1.0; Tauri пересматривается после 1.0, если WebKitGTK получит WebRTC в стандартных сборках.
- [x] **Мобильная стратегия**: нативные Kotlin + Swift (рекомендация). Решено: нативные клиенты, но вне MVP — в 1.0 мобильных клиентов нет; Android (Kotlin + Compose) — первым после 1.0, iOS (Swift + SwiftUI) — следом. Архитектура (crypto-core с uniffi, общий Protobuf) остаётся готовой к ним.
- [x] **Лицензия сервера**: AGPL-3.0 (рекомендация). Решено: AGPL-3.0 — любой, кто запускает изменённый сервер для других, обязан опубликовать изменения; совпадает с разделами 2 и 10.
