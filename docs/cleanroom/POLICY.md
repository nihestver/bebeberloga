# Политика clean room

Решение: [ADR-0001](../adr/0001-clean-room-process.md). Clean room защищает от претензий по авторскому праву на код и ассеты; он **не** защищает от претензий по товарным знакам и trade dress — поэтому отдельно требуется дистанцирование от бренда оригинала (см. ниже и `BRAND.md`).

## Два контура и стена

| Контур | Кто | Разрешено | Запрещено |
|---|---|---|---|
| **A — аналитика** | Автор спецификации; промпты A1–A5 | Пользоваться оригинальным продуктом как обычный пользователь; читать публичную справку, публичные инженерные блоги и whitepaper-ы; описывать поведение своими словами; делать wireframe-ы в словах | Декомпилировать или читать минифицированный JS клиента; читать утечки исходников; копировать тексты UI, CSS, иконки, звуки, шрифты, скриншоты в спецификацию |
| **B — реализация** | Разработчики; Claude Code с `CLAUDE.md`; промпты B1–B20 | Читать только `docs/` этого репозитория, RFC и документацию open-source библиотек | Открывать оригинальный продукт на время разработки; читать его документацию для разработчиков (схемы API — тоже объект авторского права); использовать код из его репозиториев и SDK даже под свободной лицензией; употреблять слова из запретного списка `docs/spec/GLOSSARY.md` |

Инженерные публикации конкурентов — вход контура A: из них берутся архитектурные принципы (как в `docs/PLAN.md` раздел 6.5), но не код, не протоколы и не форматы.

## Режим одного человека

1. Сначала целиком пишется спецификация (`docs/spec/`), затем начинается реализация.
2. После старта реализации к оригиналу не возвращаются. Если нужно уточнить поведение — записать вопрос в `docs/spec/OPEN-QUESTIONS.md`, ответить на него отдельной «аналитической» сессией, не трогая код в тот же день, и записать это в `LOG.md`.
3. Каждое обращение к оригиналу (когда, зачем, что смотрели, какие файлы спецификации изменены) фиксируется в `LOG.md`.
4. В ИИ-сессиях контуры не смешиваются: сессия с промптом A не пишет код, сессия с промптом B не получает ссылок на оригинал.

## Что обязательно отличается от оригинала

- Название, логотип, маскот, домены, звуки уведомлений, имена файлов и пакетов.
- Палитра (`BRAND.md`): не фирменный сине-фиолетовый оригинала и не его серые тона.
- Иконки: только open-source наборы (Lucide, Tabler, Phosphor) или собственные.
- Шрифты: Unbounded и Nunito (SIL OFL), JetBrains Mono для кода.
- Тексты интерфейса, тон сообщений, микрокопирайт, пасхалки.
- Публичный API, имена полей и событий; совместимость с API оригинала не является целью.

## Что допустимо воспроизводить

- Паттерны раскладки (рейл сообществ → каналы → лента → участники), поведение функций, горячие клавиши как идею, модель ролей и прав как концепцию, Markdown-подмножество.
- Общеизвестные протокольные идеи: WebSocket-шлюз с heartbeat/resume, SFU, MLS, SFrame — всё описано в открытых RFC и статьях.

## Артефакты спецификации (`docs/spec/`)

1. `FEATURES.md` — инвентарь функций с наблюдаемым поведением и приоритетом.
2. `FLOWS/` — пользовательские сценарии, по файлу на поток.
3. `SCREENS/` — текстовые описания экранов: зоны, элементы, состояния; без пикселей и цветов оригинала.
4. `PERMISSIONS.md` — модель прав в собственной формулировке.
5. `GLOSSARY.md` — собственная терминология и запретный список для контура B.

## Ревью

После каждого модуля — ревью по `REVIEW-CHECKLIST.md` отдельным человеком или отдельным ИИ-агентом, не видевшим процесс написания кода.
